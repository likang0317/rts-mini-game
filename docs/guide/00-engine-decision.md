# 00 引擎与打包路线：先决断，再动手

## 结论

**继续用仓库现有的 Phaser 3.90 + TypeScript + Vite，用 Capacitor 打成 Android APK。**

这不是"先用着看看"。它附带一个明确的换引擎闸门，闸门数字写在本章最后。闸门没触发之前，不要迁引擎；触发了，就迁 **Godot 4**，不是 Unity，也不是 Cocos。

先把另一句话也说明白：**如果你的目标是"商业发行、300 单位同屏稳定 60fps、长期更新三年"，正确答案是 Godot 4。** 以你现在的处境（独立开发、前端背景、玩法没验证、只有 280 行骨架），现在迁 Godot 是拿两周到一个月去换一个还没被证明值得做的性能上限。顺序错了。

## 这不是"各有利弊"

判断依据只有一条：**你现在最该降低的风险是什么。**

不是"引擎性能不够"，是"玩法在手机上根本不好操作"。这件事和引擎无关——桌面右键、拖拽框选、滚轮缩放在触屏上全部失效，换 Godot 也一样要从零设计触屏交互（见第 04 章）。先用最熟的工具把"手机上能不能玩"验证掉，再谈性能上限。

所以路线是：

1. 用 Phaser + Capacitor 把第一个可玩包装到手机上（第 13、16 章）。
2. 在真机上量出单位数、帧率、输入延迟。
3. 如果撞到闸门，把纯逻辑层搬到 Godot，重写渲染和输入（第 03 章的分层就是为这一步留的门）。

## 四条路线摊开对比

下表的体积和性能数字分两类：**有来源的**标了链接和查证日期；**没有可靠来源的**明确标"经验值"或"推测"。不要把我的经验值当成厂商承诺。

| 维度 | Phaser 3 + Capacitor | Godot 4.7 | Unity 6 LTS | Cocos Creator 3.8 |
| --- | --- | --- | --- | --- |
| 空包 APK 体积 | **6-9MB**（本项目实测估算：`dist` JS 1.49MB + WebView 壳 3-5MB，见第 13 章） | 调试空包约 **20MB**，release 更小；社区有 <15MB 成品案例（来源见下） | 不拆分包约 **20-30MB**（经验值）；官方文档：拆分后仅可执行代码的 APK 约 10MB | hello world 三 ABI **30MB**，只勾一个 ABI **8MB**（官方论坛实测） |
| 中低端机 2D 性能上限 | 100-200 单位 / 30-60fps，取决于 DPR、图集、绘制调用（**推测**，必须真机实测） | 原生渲染，2D 上万 sprite 是常规量级（**经验值**，仍受填充率限制） | 原生，性能最强，但 2D RTS 用不到它的上限 | 原生，2D 强，性能接近 Godot |
| 触屏输入原生支持 | 有 Pointer Events 抽象，**没有 RTS 手势**，框选/长按/双指要自己写 | `InputEventScreenTouch/Drag`，同样没有 RTS 手势库 | Input System + UGUI，触屏事件完整，仍需自己写 RTS 逻辑 | 节点事件系统，触摸完整，编辑器里配 UI 最省事 |
| 2D RTS 的寻路/选择/UI | 全部自己写。A* 约 200 行，选择与命令卡要自己搭 DOM 或 Phaser 对象 | 内置 `AStarGrid2D`、`Navigation2D`；UI 用 Control 节点 | NavMesh（3D 向）、Tilemap、UGUI 全，但 RTS 网格寻路仍要自己接 | 无内置网格 A*；UI 用编辑器搭，改布局要点鼠标 |
| 中文文档与社区 | 官方英文为主，中文资料零散；Phaser 论坛可用 | 官方中文文档完整，社区比 Unity 小 | 中文资料最多，教程/插件/外包生态最全 | 中文文档与社区最好，国内小游戏链路顺 |
| 你上手到"能装包" | **1-2 天**（已有骨架） | 1-2 周（学 GDScript + 节点 + 导出模板） | 2-4 周（C# + 编辑器 + 构建链） | 2-3 周（编辑器工作流是主要成本） |
| 现有代码复用率 | **100%** | 0%（`src/game` 抽出来后，逻辑可 1:1 重写） | 0% | 0%（TS 能写，但编程模型不同） |
| 长期更新方式 | 重新构建 APK 覆盖安装；也可做资源热更（不建议，见第 14 章） | 重新导出 APK | APK/AAB，生态成熟 | APK/AAB，国内发行链路成熟 |

- Godot 空 APK 约 20MB 为社区回答，不是官方数字。来源：[Godot 论坛](https://forum.godotengine.org/t/how-to-check-how-big-my-game-is/125163)

- Phaser 官方在 2025 年的优化文章与 v4 RC 说明中提到移动端批处理与滤镜缓冲的改进；本项目锁在 3.90，不适用 v4 的收益。来源：[Phaser 优化文章](https://phaser.io/news/2025/03/how-i-optimized-my-phaser-3-action-game-in-2025)、[Phaser v4 RC4](https://phaser.io/news/2025/05/phaser-v4-release-candidate-4)

**没有查到可靠数字的，不要信我的估计。** 尤其"100-200 单位"这一格，必须用你自己的目标机型跑出来才算数（第 12 章给了测法）。

## 为什么不是 Godot（现在）

Godot 4 是这四条里最适合"个人做 2D"的：轻、快、2D 原生、内置网格寻路、导出 APK 只要装 export template。如果这个项目从零开始，我会直接让你用 Godot。

不选它的理由只有一个，但很硬：**你现在有一份能跑的骨架、一套设计文档、一套 UI 高保真稿，换 Godot 意味着这些代码映射全部作废，UI 还要在 Control 节点里重搭一遍。** 而你要验证的"手机操作链"换引擎并不会自动解决。

投入产出比：两周起步，换来的是你目前还用不到的性能余量。

## 为什么不是 Unity

Unity 做 2D RTS 完全没问题，工具链最全。但它对你是三重负担：C#、编辑器工作流、构建时间（IL2CPP 一次 5-15 分钟，经验值）。

你现在要的是"手机上装个包，验证 10 分钟一局好不好玩"。用 Unity 是拿卡车送外卖。等你确定要做 3D 表现、上 Steam、或者需要成熟的商业插件生态，再考虑它。

## 为什么不是 Cocos

Cocos Creator 用 TypeScript，中文文档最厚，原生打包成熟，看起来技能迁移最顺。两个坑：

- **它是编辑器驱动的。** 场景、节点树、预制体、动画都在编辑器里搭，代码只是挂在上面的脚本。你现在"代码生成一切"的思路要整个换掉。
- **它的强项是国内小游戏发行**，不是 RTS。你不上架、不做小游戏，这部分优势用不上。

顺带一个反直觉的点：**"都会 TypeScript"不等于迁移成本低。** 编程模型（节点树 vs 场景类、生命周期、资源加载）完全不同，语言相同只省了语法学习。

## 选 Phaser 的真实代价

不是"WebView 慢"这种空话，是四件一定会遇到的事。

### 1. 填充率（fill rate）先崩，不是逻辑先崩

手机 DPR 普遍 2.75-3。`1920×1080` 的 Canvas 按 DPR 3 渲染，等于 5760×3240 的像素量，中端机 GPU 直接跪。**第一优先级永远是把 DPR 压到 2 甚至 1.5**（第 13 章给代码）。

### 2. 绘制调用与纹理切换

Phaser 对**同纹理**的 Sprite 会自动批处理。你现在用 `this.add.rectangle`（`MainScene.ts:100-102`），它们共享 Phaser 内置白纹理，能批处理，这点比 `Graphics` 好——`drawMap()` 里的 `Graphics`（`MainScene.ts:68`）是独立绘制，但它只画一次，静态开销可以接受。

真正的问题是以后换成每单位一张图：纹理一换，批次就断。**所有单位最终必须进同一张图集**（第 12 章）。

### 3. 后台节流

Android WebView 切到后台后 `requestAnimationFrame` 会停。你的采集、建造、祭祀读条如果按真实时间算，切出去 5 分钟回来会全部错乱。对策：用逻辑帧计数（第 02 章），并在 `visibilitychange` 时**暂停**仿真，不要补帧。

### 4. 音频延迟

移动端 WebView 要求首次用户交互后才能播音频，部分机型有 100-300ms 延迟（经验值）。RTS 的点击音、攻击音延迟明显会显得"发虚"。对策：第一屏放「点击开始」，同时解锁 `AudioContext`。

## 一条纪律：把"能换引擎"当保险

> **`src/game/` 里不许出现任何 `Phaser` 的运行时引用**（类型可以用 `import type`）。

做到这条，将来迁 Godot 时，仿真核心可以按 1:1 重写成 GDScript，只重写渲染和输入。这条纪律在第 03 章展开，在这里它是你选 Phaser 的风险对冲。

## 换引擎闸门

在目标机型（你自己那台手机，不是模拟器）上，满足**任意一条**就启动迁移评估：

| 闸门 | 阈值 | 怎么测 |
| --- | --- | --- |
| 帧率 | 100 单位同屏、DPR 2、图集化之后，持续 10 秒低于 **30fps** | 第 12 章的帧率叠加层 |
| 输入延迟 | 点击到画面反馈 > **100ms** | 录屏逐帧数，或 `performance.now()` 打点 |
| 稳定性 | 30 分钟对局内 WebView 崩溃/OOM 一次以上 | `adb logcat` |
| 内容需求 | 必须稳定支持 **200+ 单位**同屏 | 你自己的设计目标 |

闸门前三条是"技术不行"，第四条是"需求超了"。**没触发就不要迁。** 迁移本身也是两周起步，别把时间花在没发生的问题上。

如果触发了，迁 **Godot 4**：它的 `AStarGrid2D`、`Control` UI、原生 2D 渲染正好对上你的需求；社区规模不如 Unity，但对单人 2D 项目够用。Unity 只有在你要做 3D 或重度商业化时才值得。

## 本章落到四件事

1. **先出包**：只有三个方块单位时就把 APK 装到手机上（第 13 章）。不要等做完。
2. **抽逻辑层**：建 `src/game/`，把状态和规则从 `MainScene` 里搬出去（第 03 章）。
3. **重写输入**：`MainScene.ts:106-149` 那套桌面输入在手机上全部作废（第 04 章）。
4. **不要升 Phaser 4**：仓库锁的 `3.90.0` 是稳定版，升级会和 Capacitor、现有 API 一起变成变量。等玩法定型再说。
