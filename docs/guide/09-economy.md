# 09 经济系统：采集回环与资源曲线

## 现在的经济是零

代码里没有资源，没有采集，没有建筑。`DESIGN-v2.md:3.1-3.4` 定义了四种资源 + 德望，但只有一张数值表，没有实现。

这一章讲两件事：**采集回环怎么写**，以及**文档里的数字到底能不能跑通**。后者比前者重要——我算完之后发现三处对不上，写在最后。

## 采集回环：一个状态机

农人的行为不是"每秒加资源"，是一个循环：

```
空闲 → 走向资源点 → 采集（耗时） → 走回交付点 → 卸货 → 走回资源点 → ...
```

用状态机写，不要用一堆 `if`：

```ts
// src/game/sim/gather.ts
export type GatherPhase = 'toNode' | 'harvesting' | 'toDropoff' | 'depositing';

export interface GatherOrder {
  kind: 'gather';
  nodeId: number;
  phase: GatherPhase;
  /** 当前这一趟已经采到的量 */
  carrying: number;
  /** 采集开始/结束的帧号 */
  phaseEndTick: number;
}
```

每个阶段只做一件事：

```ts
function updateGather(u: UnitState, g: GatherOrder, state: GameState): void {
  const node = state.nodesById.get(g.nodeId);
  if (!node || node.amount <= 0) {
    // 资源点枯竭：找最近的同类资源点，找不到就回空闲
    const next = findNearestNode(state, node?.kind ?? 'wood', u.x, u.y);
    if (next) g.nodeId = next.id;
    else { u.order = null; return; }
  }

  switch (g.phase) {
    case 'toNode':
      if (moveTo(u, node.x, node.y, 40, state)) {   // 40px 内算到达
        g.phase = 'harvesting';
        g.phaseEndTick = state.tick + HARVEST_TICKS;
      }
      break;

    case 'harvesting':
      if (state.tick >= g.phaseEndTick) {
        g.carrying = Math.min(node.amount, CARRY_AMOUNT[node.kind]);
        node.amount -= g.carrying;
        g.phase = 'toDropoff';
      }
      break;

    case 'toDropoff':
      if (moveTo(u, state.dropoff.x, state.dropoff.y, 48, state)) {
        g.phase = 'depositing';
        g.phaseEndTick = state.tick + 6;            // 0.1 秒卸货
      }
      break;

    case 'depositing':
      if (state.tick >= g.phaseEndTick) {
        state.resources[node.kind] += g.carrying;
        g.carrying = 0;
        g.phase = 'toNode';
      }
      break;
  }
}
```

几个必须处理的边界：

- **资源点被采空**：换最近同类；没有就空闲。
- **交付点被拆**：换最近的大邑/伐木场；没有就空闲（并且 HUD 提示）。
- **玩家中途下令**：直接打断 `GatherOrder`，清空 `carrying`（或者让农人先把这趟送回去，二选一，但要在 UI 上说清楚）。
- **多人采同一个点**：资源点储量扣减要在"采集完成"那一刻做，不是开始采的时候做，否则会出现负数。

## 农田是另一种行为

`DESIGN-v2.md:3.4`：农田是"站进范围持续产出，不来回搬运"。

所以农人有两个工作模式：

- **搬运型**（木/石/玉）：走 → 采 → 走回 → 卸。
- **驻留型**（谷）：走进范围 → 持续产出，直到被叫走。

驻留型简单得多：

```ts
function updateFarm(u: UnitState, state: GameState): void {
  const inRange = state.farms.some(f => dist(u, f) <= f.radius);
  if (!inRange) { /* 走向最近的农田 */ return; }
  if (state.tick % FARM_TICK_INTERVAL === 0) {
    state.resources.gu += FARM_YIELD_PER_TICK;
  }
}
```

**关键数字：`FARM_YIELD_PER_TICK` 文档没给。** 这是整个经济系统最重要、却缺失的一个数（见最后一节）。

## 资源点离交付点多远，是设计约束

文档说"单程约 3 秒"（木）、"约 4 秒"（石/玉）。单位速度是 140 px/s（`MainScene.ts:8`），所以：

- 木：`140 × 3 = 420px`，约 **8.75 格**。
- 石/玉：`140 × 4 = 560px`，约 **11.7 格**。

这不是"大概"，是硬约束。**如果你把林地放在离大邑 20 格远的地方，单程就是 6.9 秒，整条资源曲线都会慢一倍。**

地图是 40×30（1920×1440），大邑在 (8,22)。所以：

- 林地放在 8-9 格范围内（约 (16,22) 或 (8,14)）。
- 石场/玉山放在 11-12 格范围内（约 (20,22) 或 (8,10)）。

如果想让玩家"扩张"，就把远处的资源点做富矿（储量大/单趟多），近处做贫矿。这是 RTS 地图设计的基本手法，不是随便摆。

## 运输量决定 UI 的节奏

每次回环，资源是"跳"一下（+10），不是平滑增长。这带来两个后果：

- **HUD 数字每 8-10 秒跳一次**，玩家感知不到"正在赚钱"，会觉得经济停滞。
- **资源曲线是阶梯状**，倒推造价时要按"每趟时间"算，不是按"每秒"算。

缓解办法（选一个）：

1. HUD 显示"在途资源"（农夫身上背着的量），数字更连续。
2. 显示"预计 +10 木 / 8 秒"的速率提示。
3. 不做，接受阶梯感——很多经典 RTS 就是这样。

**建议 v0.1 选 3，v0.2 加 1。** 先把回环跑通，再优化感知。

## 资源曲线要倒推，不要正着堆

正确顺序是：

1. **定一局多长**：目标 10-15 分钟（`DESIGN-v2.md:10.2` M2 验收）。
2. **定第一个关键建筑什么时候出现**：祭坛在 2 分钟左右。
3. **定第一波兵什么时候出现**：4-5 分钟。
4. **反推需要多少采集效率**。
5. **最后才定造价和工期**。

现在文档是反的：先给了造价（3.3），没给产率，也没给建造时间。这样数值只能靠感觉。

### 用文档数字算一遍开局

假设（这两个是经验值，文档没给）：

- 采集动作耗时 **2 秒**。
- 卸货 **0.1 秒**。

| 资源 | 单趟 | 往返 | 采集 | 合计 | 每秒产出 |
| --- | --- | --- | --- | --- | --- |
| 木 | 10 | 6s | 2s | 8s | 1.25/s |
| 石 | 8 | 8s | 2s | 10s | 0.8/s |
| 玉 | 10 | 8s | 2s | 10s | 1.0/s |

开局 2 个农人，要造祭坛（120 谷 + 60 木 + 80 石 + 30 玉）：

- 谷：开局 200，够，不用采。
- 木：需要 60，`60 / 1.25 = 48 秒`（一个农人）。
- 石：需要 80，`80 / 0.8 = 100 秒`（一个农人）。
- 玉：开局 20，差 10，`10 / 1.0 = 10 秒`。

如果两个农人分工（一个木一个石），**材料齐大约 100 秒**；再算上在资源点之间走动、建造时间（文档没给），第一个祭坛大约在 **2-3 分钟**。这个节奏是合理的。

但注意：**这意味着开局两分钟里，玩家几乎没有决策**，就是看着两个农人搬东西。手机上这种"干等"体验很差。两个解法：

- 开局多给一个农人（3 个），或
- 降低祭坛的石头需求（80 石是最重的一项，`80 / 0.8 = 100 秒`，占了三分之二的时间）。

我倾向第二个：石从 80 降到 50，祭坛时间缩短到约 70 秒。**这是建议，不是文档结论。**

## 德望：算完之后发现不够

这一节是本章最重要的部分。`DESIGN-v2.md:5.3` 说：

- 德望来源：祭祀 +2、击败 +3（单次战斗上限 +9）、归附 +8、公共工程 +5。
- 归附阈值 50，禅让阈值 100，开局 20。
- 祭祀消耗：祈谷 20 玉、祈风 30 玉、祈雨 30 玉、告成 50 玉 + 100 谷（+10 德望）。

从 20 到 100，需要 **+80 德望**。

**路线一：全靠祈谷（+2 / 20 玉）**

- 40 次祭祀 × 20 玉 = **800 玉**。
- 一座玉山总储量正好 **800**（`DESIGN-v2.md:3.4`）。
- 还没算祭坛本身的 30 玉、祈风祈雨、精英单位的玉。
- 结论：**单座玉山不可能只靠祈谷走到禅让。**

**路线二：靠告成（+10 / 50 玉）**

- 8 次 × 50 玉 = **400 玉**，玉够了。
- 但告成冷却 **120 秒**，8 次 = **960 秒 = 16 分钟**。
- 再加 800 谷，以及前面采集、建造的时间。
- 结论：**理论可行，但最短 16 分钟，和 M2 验收的"10-15 分钟分出胜负"冲突。**

**路线三：混合**

- 归附 3 个部落：+24。
- 击败敌方部队：每次 +3，上限 +9/场，可重复。
- 加上 20 开局，靠战斗和归附补到 50，再用告成冲 100。
- 这条最接近设计意图，但**德望的主要来源变成了战斗**，和"不打也能赢"的卖点有张力。

**我的判断**：德望的数值需要改，至少改一处：

- 把禅让阈值从 100 降到 80（减少 20 点，约省 2 次告成 = 4 分钟），或
- 把告成冷却从 120 秒降到 60 秒（16 分钟减半），或
- 增加第二座玉山/提高玉的采集效率。

不改的话，"政治胜利"在单局时长内基本不可达——玩家会算出来"打架更快"，然后所有人都去打架，德望系统就白设计了。

## 一句话总结

**经济不是"加资源"，是"时间怎么花"。** 单趟时间、往返距离、交付点位置，这三个数决定了整局的节奏，比造价表重要得多。
