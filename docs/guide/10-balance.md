# 10 数值与平衡：从产出率推造价

## 平衡不是"调数字"

平衡是**让每一段时间的投入产出大致相等**。你不需要让所有单位一样强，你需要让玩家在"造农人还是造兵""采玉还是采木"之间真的需要想一下。

这一章给一套能落地的推法。所有具体数字都是经验值，方法比数字重要。

## 第一步：定"每秒产出"

平衡的基准不是造价表，是**一个农人每秒能产出多少资源**。

`DESIGN-v2.md:3.4` 给了单趟量和单程时间，但没给采集动作耗时。加上第 09 章假设的 2 秒采集，得到：

| 资源 | 每趟 | 周期 | 每秒 | 每分钟 |
| --- | --- | --- | --- | --- |
| 木 | 10 | 8s | 1.25 | 75 |
| 石 | 8 | 10s | 0.8 | 48 |
| 玉 | 10 | 10s | 1.0 | 60 |
| 谷（农田） | 持续 | —— | **0.8（假设）** | **48** |

**这四个数是你整套数值的地基。** 改一个，后面全变。把它们写在一个文件里，不要散落在代码里：

```ts
// src/game/data/economy.ts
export const INCOME = {
  wood: 1.25,
  stone: 0.8,
  jade: 1.0,
  grain: 0.8,     // 经验值，文档缺失，必须自己定
} as const;
```

## 第二步：从"回本时间"推造价

一个农人 50 谷，每秒产 0.8 谷，**回本时间 = 50 / 0.8 = 62.5 秒**。

这个数字意味着什么：造农人后 1 分钟开始纯赚。RTS 里这个值通常在 **60-90 秒**（经验值）：

- 低于 45 秒：农人太便宜，玩家会无脑爆农，前期没有决策。
- 高于 120 秒：农人回本太慢，玩家宁愿直接造兵，经济系统失去意义。

如果你想让回本时间变成 75 秒，造价应该是 `75 × 0.8 = 60 谷`。**这是一个可调的旋钮，不是拍脑袋。**

同样的方法推到兵：

- 族兵 60 谷，一个农人要 75 秒才能产出这 60 谷。
- 也就是说，**每造一个兵，你就少了一个农人 75 秒的产出**。
- 如果一局 10 分钟，2 个农人全力产谷 = 960 谷，够造 16 个族兵（不算其他开销）。这就是"兵力上限"的直觉来源。

## 第三步：训练时间与人口上限

训练时间决定"兵什么时候能出来"，人口上限决定"最多能有多少"。

`DESIGN-v2.md:3.3` 给了人口上限 12（基础）+ 4/民居（上限 24），但**没给训练时间**。

用"训练消耗速率"反推：

```
训练一个单位消耗资源的速率 = 单位造价 / 训练时间
```

如果大邑 12 秒造一个农人（50 谷），消耗速率是 `50 / 12 = 4.17 谷/秒`。

而一个农人产 0.8 谷/秒。所以：

> **要维持大邑不停造农人，需要 4.17 / 0.8 ≈ 5.2 个农人在种田。**

这是一个非常有用的结论：它告诉你"几个农人算够"。5 个农人 + 1 个造兵的建筑，就是经济饱和点；再多农人，谷会溢出，应该转去采木石玉。

同理，如果族兵 60 谷 / 18 秒，消耗速率 3.33 谷/秒，也需要约 4.2 个农人养着。

**建议首版训练时间（经验值）：**

| 单位 | 训练时间 | 消耗速率 | 需要农人 |
| --- | --- | --- | --- |
| 农人 | 12s | 4.17 谷/s | 5.2 |
| 族兵 | 18s | 3.33 谷/s | 4.2 |
| 弓手 | 20s | 3.5 谷/s + 0.5 玉/s | 4.4 + 玉 |
| 精英 | 30s | 3.33 谷/s + 0.83 玉/s | 4.2 + 玉 |

## 第四步：玉是四条线的共同瓶颈

这是本作最重要的数值结构。玉的用途：

- 祭坛 30（一次性）
- 弓手 10/个
- 精英 25/个
- 祭祀 20-50/次
- 图腾 20

而玉的产出只有 **1.0/秒/农人**，一座玉山 800。

一局 10 分钟，一个农人全程采玉 = 600 玉。这 600 玉要同时供给：

- 祭坛 30
- 2 个弓手 20
- 3 次祭祀 90
- 1 个精英 25
- 合计 165

看起来够，但如果你想要禅让（第 09 章算过要 400-800 玉），就必须**专门派 2-3 个农人长期采玉**，这会直接减少木石谷的采集。**这就是设计想要的张力**：经济、军事、政治三条线抢同一批农人。

**建议做一个"每分钟玉预算表"**，贴在平衡表旁边：

| 时间 | 玉收入 | 支出项 | 余额 |
| --- | --- | --- | --- |
| 0-2 min | 0（还没采） | 祭坛 30 | -30（靠开局 20 + 采集补） |
| 2-4 min | 120 | 祈谷 20 | 70 |
| 4-6 min | 120 | 弓手 20 + 祈谷 20 | 150 |
| ... | ... | ... | ... |

这张表能让你一眼看出"玉什么时候会断"，而不是等玩家打到一半发现造不起兵。

## 第五步：建造时间怎么定

文档只给了建筑造价，没给工期。两个经验规则：

1. **建筑工期 ≈ 单位训练时间 × 2-3**。祭坛是核心建筑，可以更长（45-60 秒）；民居短（15 秒）。
2. **造价越高，工期越长，但不是线性**。否则高价建筑会变成"等一辈子"。

一个可用的起步表（经验值）：

| 建筑 | 造价（文档） | 建议工期 | 理由 |
| --- | --- | --- | --- |
| 民居 | ——（文档没给） | 15s | 快速补人口 |
| 粟田 | —— | 20s | 经济建筑，不能太慢 |
| 伐木场/采石场 | 80 谷 + 60 木 + 20 石 / 80 谷 + 40 木 + 40 石 | 30s | 中期效率建筑 |
| 祭坛 | 120 谷 + 60 木 + 80 石 + 30 玉 | 45s | 核心建筑，值得等 |
| 图腾 | 80 谷 + 40 木 + 20 玉 | 30s | 前压建筑，太快会滚雪球 |

**注意**：建筑工期直接决定"防守方有没有时间反应"。祭坛 45 秒意味着进攻方拆它需要 45 秒以上的输出窗口，这个值要和部队 DPS 一起调。

## 平衡表怎么维护

不要用 Excel 手动同步。用**一个 TS 文件 + 一个 CSV 导出脚本**：

```ts
// src/game/data/balance.ts
export interface UnitBalance {
  id: string;
  hp: number;
  damage: number;
  armor: number;
  attackIntervalTicks: number;
  range: number;
  cost: Partial<Record<'grain' | 'wood' | 'stone' | 'jade', number>>;
  buildTicks: number;
}

export const UNITS: UnitBalance[] = [
  { id: 'peasant', hp: 40,  damage: 5,  armor: 0, attackIntervalTicks: 90, range: 48,
    cost: { grain: 50 }, buildTicks: 720 },
  { id: 'warrior', hp: 90,  damage: 16, armor: 3, attackIntervalTicks: 72, range: 48,
    cost: { grain: 60 }, buildTicks: 1080 },
  { id: 'archer',  hp: 55,  damage: 11, armor: 1, attackIntervalTicks: 90, range: 192,
    cost: { grain: 70, jade: 10 }, buildTicks: 1200 },
];
```

三条维护纪律：

1. **每个数字都要有理由**。在表旁边写一句"为什么是 90 血"——比如"族兵要能扛住 7 下同族攻击，TTK 8.4 秒"。没有理由的数字，下次你不敢改。
2. **一次只改一个数**。改完跑一局或跑一次脚本模拟，记录结果。一次改五个数，你不知道是哪个起了作用。
3. **保留历史**。`balance.v1.ts`、`balance.v2.ts`，或者 git 提交信息写清楚"为什么改"。RTS 的数值是长期调出来的，不是一次设计出来的。

## 什么时候不该调平衡

- **玩法循环还没跑通**：连"采集→建造→造兵→战斗"都没闭环，调数值没有意义。
- **只有你一个人玩**：你的操作水平会掩盖数值问题。至少要找 2-3 个人试玩。
- **没有测量手段**：你连"一局几分钟"都测不准，就没法调"节奏"。

先做第 15 章的测试和记录，再谈平衡。

## 一句话总结

**先定产出率，再定回本时间，最后才定造价。** 反过来做，你会得到一张看起来合理、实际跑不动的表。
