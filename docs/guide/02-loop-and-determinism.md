# 02 游戏循环与固定时间步长

> 本章用"按下右键"这类桌面操作举例，只是为了说明时钟问题；触屏上的等价操作见第 04 章。

## 先看你现在怎么写的

`src/scenes/MainScene.ts:246-264`：

```ts
private updateUnits(delta: number): void {
  const step = (UNIT_SPEED * delta) / 1000;
  ...
  unit.body.x += Math.cos(angle) * step;
  unit.body.y += Math.sin(angle) * step;
}
```

`delta` 是 Phaser 从 `requestAnimationFrame` 拿到的两帧间隔，单位毫秒。这段代码的意思是"每秒走 140 像素，这一帧占多少秒就走多少"，看起来完全正确，教科书也这么写。

问题在于它把一个**连续量**直接塞进了**离散仿真**。

## 为什么这在 RTS 里是致命的

先说后果，再说原理。

### 后果一：同一份操作，两台机器跑出两个世界

你按下右键的那一帧，单位目标点一致；但接下来 3 秒里，你的机器跑了 180 帧，朋友的机器掉帧跑了 155 帧。每一帧都"按实际时间补足位移"，理论上总位移一样 —— 但浮点加法**不满足结合律**：`(a+b)+c ≠ a+(b+c)` 在最后几位上是真会不一样的。于是 3 秒后两个单位的位置差了 0.0001 像素。这本来无所谓。

但一旦你开始做"两个单位贴到 22 像素内就互相阻挡""距离 48 内触发攻击"这种判定，0.0001 的差异就会在某个临界帧变成"我这打过、你那没打"，然后两边世界彻底分叉。

RTS 的联机几乎都是 **lockstep（帧同步）**：双方不传单位位置，只传你的操作指令，各自跑同样的仿真。这个模型的前提是**给定相同输入，必须得到逐位相同的结果**。`delta * speed` 从根上破坏这个前提。

### 后果二：掉帧时穿模

一帧卡 200ms，`step` 变成 28 像素。如果单位直径 26 像素、判定半径 22，这一帧直接从敌人身上跳过去了 —— 移动不发生碰撞反应，攻击判定被跳过。帧率越低，穿透越严重。

### 后果三：你没法做回放和自动化测试

想做"记录一局操作、重放验证 bug"，或者"用脚本模拟 10 分钟经济运营看曲线"，都需要确定性。带 `delta` 的仿真只能重放"操作"，不能重放"结果"。

## 正确做法：固定步长累加器

核心就三行：**逻辑永远按固定的 `1/60` 秒推进，跟渲染帧率脱钩**。

```ts
const SIM_DT = 1 / 60;          // 逻辑步长，秒
const MAX_STEPS_PER_FRAME = 5;  // 防止死亡螺旋
let accumulator = 0;

update(_time: number, delta: number): void {
  // 1. 把真实时间换算成"还剩多少逻辑时间要跑"，并夹住上限
  accumulator += Math.min(delta, 250) / 1000;

  // 2. 跑够整数个逻辑步
  let steps = 0;
  while (accumulator >= SIM_DT && steps < MAX_STEPS_PER_FRAME) {
    this.sim.step(SIM_DT);
    accumulator -= SIM_DT;
    steps++;
  }

  // 3. 剩下的零头留给下一帧，别丢
  if (steps === MAX_STEPS_PER_FRAME) accumulator = 0;

  // 4. 渲染层按仿真状态摆放，可以做插值
  this.render(accumulator / SIM_DT);
}
```

几个细节，都是踩过的坑：

- **必须夹 `delta`**（这里 250ms）。用户切走标签页再切回来，`delta` 可能是 30000ms。不夹的话你会一帧跑 1800 个逻辑步，浏览器直接假死。
- **必须限步数**（`MAX_STEPS_PER_FRAME`）。这是防"死亡螺旋"：仿真一帧要 30ms，而一帧只有 16.7ms，越跑越落后，最后彻底卡住。
- **零头不能丢**，否则当 60Hz 显示器和 60Hz 逻辑不对齐时，你会持续吞掉零点几毫秒，表现为"走位比预期慢 3%"。
- **渲染插值可以最后做**。先做"逻辑 60Hz、渲染每帧读最新状态"，画面会有最多 1 帧的抖动，肉眼几乎看不出来。等动作多了再插值。

改到你的代码上，`UNIT_SPEED` 仍然是 140，但每步位移恒等于 `140 / 60 ≈ 2.333px`，与帧率无关。

## 确定性：不止是"固定步长"

固定步长解决"帧数不一致"，但还不够。下面是 RTS 里真正会让你半夜起来查 bug 的几件事。

### 1. 三角函数和开方

`Math.sin / Math.cos / Math.atan2 / Math.sqrt` 在不同 JS 引擎（V8 / JSC / SpiderMonkey）和不同 CPU 上，**最后一位可能不同**。IEEE 754 只保证 `+ - * /` 精确。

`MainScene.ts:256-257` 现在每帧算一次 `atan2` 再算 `cos/sin`，这既慢又不确定。

实用解法（按成本从低到高）：

- **能不用就不用**。移动改成"目标点方向增量 = (dx, dy) 归一化"，用 `dx / len`、`dy / len`，只剩一次 `sqrt`；再狠一点用 1/len 的牛顿迭代近似，各平台一致。
- **查表**。预生成 4096 项 sin 表，用整数索引取，跨平台完全一致。
- **定点数**。位置用"千分之一像素"的整数存，全部整数运算。彻底确定，但写起来累，只在真要做联机时上。

先做前两条，够用很久。

### 2. 随机数

现在代码里没有随机数。**请保持这个习惯，或者一开始就用可播种的 PRNG**：

```ts
// mulberry32：32 位状态，跨平台逐位一致
function mulberry32(seed: number) {
  return function () {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

绝对不要用 `Math.random()` 做任何影响玩法的事（暴击、AI 决策、单位初始微偏移）。`Date.now()` 同理。渲染层（粒子、飘字）用 `Math.random()` 没关系，因为它不改状态。

### 3. 遍历顺序

`MainScene.ts:207-209` 用 `this.units.forEach` 做框选，`MainScene.ts:232` 用 `Array.from(this.selected)` 下令。数组顺序是稳定的，`Set` 在 V8 里也是插入序，所以现在没问题。

但一旦你把单位存进哈希表、按对象引用排序、或者用 `Map` 遍历后重建数组，顺序就可能变。**规则：仿真里所有"遍历所有实体"的地方，都按稳定的整数 id 升序**。别依赖容器实现细节。

### 4. 累加顺序

`for (const u of units) { 加血; 减血; }` 这种在一个循环里既读又写的写法，结果依赖顺序。先结算伤害、再统一扣血（两段式），顺序的影响就小得多。第 08 章会展开。

## 落到这个仓库：建议的重构形状

目标是让 `MainScene` 变成"输入采集 + 渲染"，仿真搬进纯逻辑层（第 03 章详述）：

```
src/
├── game/
│   ├── sim/
│   │   ├── GameState.ts     # 纯数据：units/资源/帧号
│   │   ├── step.ts          # step(state, commands, fixedDt) 纯函数
│   │   └── rng.ts           # 可播种 PRNG
│   └── ...
└── scenes/MainScene.ts      # 只负责：收集输入 → 调用 step → 把状态摆到 GameObject 上
```

`step` 里 **不许出现** `Phaser`、`Date`、`Math.random`、`window`。能做到这一条，后面所有测试和回放都是免费的。

## 自检清单

改完之后，用这三条验证：

1. 在 DevTools 里把 CPU 降速 6 倍（Performance 面板 → CPU throttling），单位走同样距离的时间应该基本不变（差在启动/停止的那一帧）。
2. 记录一串指令（右键坐标序列），用 `requestAnimationFrame` 模拟 30fps 和 144fps 各跑一次，最终位置逐位相同（浮点方案下要求 `< 1e-9`）。
3. 切到别的标签页停留 30 秒再切回来，游戏不能卡死、不能瞬移一大段。

## 一句话总结

**逻辑时钟和渲染时钟必须是两个时钟。** 渲染可以掉帧，逻辑不可以掉步。这是整份文档里唯一"晚改会痛不欲生"的一章。
