# 04 能力阶梯：入门、进阶、精通各自要交出什么

> 这一章不按“知识点”分，而按“你能独立交付什么”分。每一档都给三个东西：**要具备的能力、用本 RTS 项目做的练习、可观测的过关标准**。没有作品和测量，就不算过关。

## 分级原则

1. **以交付物为准，不以软件熟练度为准。** 会用 Figma 的全部功能，不等于能设计一个能打的 HUD。
2. **每一档都必须有“真机/真人”证据。** 截图、录屏、测试记录、性能数据，缺一不可。
3. **高级不是“会更多”，而是“能判断不做什么”。** 精通的分水岭是取舍，不是技巧。

先看一张总表，后面逐档展开。

| 能力 | 入门 | 进阶 | 精通 |
| --- | --- | --- | --- |
| 视觉基础 | 能复刻，比例/间距/色值准确 | 能建立层级，知道为什么这样排 | 能定义风格并让它可扩展 |
| 排版 | 会用字号阶梯 | 能处理中英混排、数字对齐、换行 | 能制定字体策略与授权方案 |
| 图标 | 能画统一规则的 24px 图标 | 能设计一套语义清晰的图标系统 | 能定义跨阵营/跨文化的符号体系 |
| 信息架构 | 能列出信息清单 | 能做频率×后果分级、渐进披露 | 能用信息架构改变玩法决策 |
| 交互 | 能画 3–5 个状态 | 能写状态机、手势冲突、误触防护 | 能设计一套可复用的交互模式 |
| 动效 | 能做 150–250ms 的状态反馈 | 能控制节奏、层级、动效预算 | 能用动效表达系统状态与叙事 |
| 适配 | 能在 2–3 种分辨率不溢出 | 能按 dp 布局、处理安全区/超宽屏 | 能制定适配策略并验证公平性 |
| 无障碍 | 知道对比度/色盲 | 能做色盲模拟、UI 缩放 | 能把无障碍纳入设计系统 |
| 工程 | 会切图、九宫格 | 会图集、字体子集、性能预算 | 能和程序共同制定管线与验收 |
| 协作 | 能按规范交付 | 能写状态矩阵、和程序对齐 | 能推动团队采用系统 |
| 研究 | 能找人看图 | 能做 5 人任务测试 | 能用数据驱动改版并复盘 |

## 第一档：入门——从“能画”到“能交付一个静态界面”

### 这一档要具备的能力

- 能看懂一个现有界面：哪些是容器、哪些是内容、哪些是状态。
- 能把设计稿还原到像素级：间距、字号、颜色、描边、圆角。
- 能建立最基础的组件意识：按钮、卡片、面板、图标。
- 知道触屏的最小尺寸、对比度下限、安全区这些硬约束。
- 能把一个静态界面在引擎/网页里跑起来，并在真机上截图。

注意：这一档不要求“原创风格”，要求“准确”和“可交付”。

### 练习 1：1:1 复刻资源栏

用 Figma 复刻 `docs/ui/ui-a.html` 里的资源栏（谷/木/石/玉/人口），不要自由发挥。

要求：

- 1920×1080 基准，资源栏尺寸、间距、字号与现有稿一致。
- 做 4 个状态：正常、某项不足、数值变化中、人口卡满。
- 图标用同一套 24×24 规则重画，不直接用原 SVG。

**过关标准（可观测）：**

- 与现有稿叠图，主要元素偏差 ≤2px；色值差 ΔE ≤3。
- 在 1920、1440、1280 三种宽度下不溢出、不换行。
- 把图标缩到 24px，找 5 个人看 3 秒，≥4 人能说出每一项是什么。
- 资源数字用等宽数字，数值从 9 变到 100 时，整行不左右跳动。

为什么是资源栏：它同时包含图标、数字、标签、状态、对齐，是 UI 基本功的浓缩。
常见错误：一上来就“重设计”，结果连原来的间距都没量准。

### 练习 2：手机横屏资源栏

把练习 1 的资源栏改成 640×360dp 的手机横屏版本。

要求：

- 5 项资源 + 人口，放在顶部；每项可点区域 ≥48dp。
- 数字 ≥14sp，标签 ≥11sp；标签可省略，但不能丢信息。
- 处理左右安全区（挖孔/手势条）。
- 提供中/英两版，英文不溢出。

**过关标准：**

- 在 640×360、800×360、1024×768 三种视口下无遮挡。
- 英文版最长的一项不换行、不截断。
- 5 个没玩过的人，能在 10 秒内指出“谷”的数量，≥4 人成功。
- 对比度：数字 ≥7:1，标签 ≥4.5:1。

为什么是手机版：同一组信息，在桌面和手机上需要不同的取舍。这一题考的是“压缩而不丢信息”。
常见错误：直接把桌面资源栏等比缩小；标签全删，只剩图标，结果分不清谷和木。

### 练习 3：德望面板的三个状态

给“德望”做三个状态：常态（20）、将满（80）、圆满（100）。

要求：

- 三个状态在 0.3 秒内可区分，但不能只靠颜色。
- 圆满状态要有“可受禅”的叙事感，但不能抢过战场。
- 数值变化有 200ms 的反馈，不滚动、不弹跳。

**过关标准：**

- 把三个状态随机打乱给 5 个人看，≥4 人能正确排序。
- 在灰度模式下仍能区分三个状态（靠形态/刻度/文案）。
- 面板面积不超过屏幕的 3%。
- 圆满状态不遮盖战场中心。

为什么是德望：它是本作最有特色的信息，既不是资源也不是数值，考的是“如何用形态表达叙事”。
常见错误：把德望做成第六个资源格；圆满时全屏金光，抢走战场注意力。

### 练习 4：12 个图标

画 12 个 24×24 图标：谷、木、石、玉、人口、耕作、伐木、采石、采玉、建造、祭祀、攻击。

要求：

- 统一网格、描边、透视、光源。
- 核心资源用通用符号；文化符号只用于祭祀/建筑。
- 每个图标在 24px 下能辨认。

**过关标准：**

- 5 人盲测，≥4 人能认出 ≥10 个。
- 放大到 96px 不糊，缩小到 20px 不糊。
- 线性/面性不混用；描边宽度误差 ≤0.5px。
- 导出 SVG，`viewBox` 统一，颜色用 `currentColor`。

### 练习 5：在引擎里跑起来

把资源栏做成一个可运行的页面（HTML/CSS 或 Phaser 均可），读取一份 JSON 假数据，数字每秒变化一次。

**过关标准：**

- 真机（或手机模拟器）截图，无横向滚动、无遮挡。
- 60fps；数字变化不引起布局抖动。
- 断网/刷新后状态可恢复（localStorage 即可）。
- 代码里没有魔法数字：颜色、字号、间距来自 token。

### 入门档的“过关”总结

你不需要有风格，但你必须能**准确复刻、按约束改造、在真机上跑起来**。三件事缺一不可。

常见卡点：

- 只会临摹，不会解释为什么。
- 只做静态图，不敢碰代码。
- 只在浏览器里看，不看真机。
- 过度追求“古风”，忽略可读性。

## 第二档：进阶——从“一个界面”到“一套能打的交互”

### 这一档要具备的能力

- 能做信息架构：频率×后果分级、常驻/情境/按需、渐进披露。
- 能设计状态机：默认/按下/禁用/冷却/不足/选中，以及状态之间的转换。
- 能控制动效节奏：不同反馈用不同时长，同屏主动画不超过 3 个。
- 能按 dp 布局，处理横屏、安全区、超宽屏、平板。
- 能做 5 人任务测试，并用数据改进。
- 能和程序对齐：状态矩阵、token、切图、性能预算。

### 练习 1：触屏指令盘

把现有的 5 个 96px 桌面按钮，重做成手机右下的触屏指令盘。

要求：

- 6 个命令：移动、攻击、停止、守卫、撤退、建造。
- 按钮 56–64dp，右下 3×2 网格；拇指不变换握姿可全部触达。
- 每个按钮有：默认、按下、禁用、不可用原因、冷却（至少一个）。
- “撤退”有二次确认或 1.5 秒撤销。
- 不依赖 hover。

**过关标准：**

- 5 个新手，在不看说明的情况下，30 秒内完成“选中单位 → 移动 → 攻击”。
- 连续点击 20 次，误触 ≤1 次。
- 单手（右手）能触达 ≥5 个按钮。
- 在 640×360 和 800×360 下不遮挡战场中心。
- 灰度模式下，禁用态与默认态仍可区分。

为什么是指令盘：它是 RTS 触屏化的核心，考的是布局、状态、误触、可达性。
常见错误：把 5 个按钮横排在屏幕正中；只做图标不做文字；禁用态只变灰不写原因。

### 练习 2：建造菜单的渐进披露

把“大邑/粟田/祭坛”三张卡改成两步式：先选类别，再选具体建筑。

要求：

- 第一步不超过 4 个类别；第二步不超过 6 个建筑。
- 每张卡显示：造价、建造时间、占地、前置条件、不可用原因。
- 资源不足时，明确显示“缺多少”，不要只变红。
- 支持中/英/德三版，不溢出。

**过关标准：**

- 新手在 60 秒内完成“造农人 → 采谷 → 造粟田”（从空镜开始）。
- 三语版本中，最长文案不换行超过两行、不截断。
- 不可用原因必须能被新手复述（测试后问“为什么不能造”）。
- 建造落位有 ghost + 取消。

为什么是建造菜单：它是“信息密度 + 状态 + 本地化”的综合题。
常见错误：一次铺 12 张卡；只写“资源不足”不写缺多少；卡片固定 178px 宽，英文直接溢出。

### 练习 3：战斗反馈链

为一次交战设计完整的反馈链，并写出时间轴：

```
选中 → 下令 → 接敌 → 受击 → 死亡 → 胜利/撤退
```

要求：

- 每个节点回答：发生了什么、对我有利吗、有多强、下一步。
- 用至少 2 个通道（视觉 + 音效/震动/数字）。
- 同屏飘字 ≤12 个；超出合并。
- 受攻击有方向提示；单位死亡有 0.3 秒的消散，不留尸体堆。

**过关标准：**

- 找 3 个没玩过的人，看 10 秒战斗录屏，≥2 人能说出“谁在打谁、谁占优”。
- 50 单位同屏，截图给 5 人看，≥4 人能指出敌方近战和友军远程。
- 战斗中没有超过 3 个同时播放的主动画。
- 受击/死亡反馈不遮挡相邻单位。

为什么是战斗链：它考的是“信息在时间上的组织”，不是单个动效好不好看。
常见错误：每个事件都弹大字；伤害数字不合并；死亡特效比单位还大。

### 练习 4：50 单位可读性测试

用现有地图，摆 50 个单位（25 友军、25 敌军，至少 3 个兵种），在远/中/近三个缩放级别截图。

要求：

- 敌我有颜色 + 形状双通道。
- 血条只在受伤/选中时显示。
- 远看能分辨兵种和阵营；近看能看清动作。
- 地形不与单位同明度。

**过关标准：**

- 5 人看远视图，≥4 人能数出敌方大致数量（±20%）。
- 5 人看中视图，≥4 人能指出“哪个是远程”。
- 色盲模拟（deuteranopia）下，仍能区分敌我。
- 截图缩到 50% 后，单位不糊成色块。

### 练习 5：六状态原型 + 两个状态落地

基于 `docs/ui` 的六状态，做一版可点击原型；选其中两个状态在 Phaser/HTML 里实现。

要求：

- 状态切换 ≤220ms，不闪白、不跳布局。
- 两个落地状态必须能读真实数据（假数据也行），不是贴图。
- 记录一次性能数据：帧率、UI 耗时、draw call（能测多少测多少）。

**过关标准：**

- 原型可演示 6 个状态，无死链。
- 落地状态在真机上 60fps，UI 帧耗时 ≤4ms（中端机）。
- 切换 20 次，无内存增长（DevTools Memory 粗测）。
- 代码里 token 与设计稿一一对应。

### 进阶档的“过关”总结

你必须能**独立负责一个完整界面系统**：从信息架构、状态、动效、适配，到真机落地和用户测试。

常见卡点：

- 会做漂亮静态图，但状态一多就乱。
- 只做“正常态”，不做禁用/冷却/不足/错误。
- 不做用户测试，靠自己的直觉。
- 不看性能，动画一多就掉帧。
- 不和程序对齐，交付物不可实现。

## 第三档：精通——从“做好一个界面”到“建立一套系统并影响决策”

### 这一档要具备的能力

- 能建立设计系统：token、组件、状态、文档、代码消费方式。
- 能做“减法”：在不降低任务成功率的前提下，减少 HUD 面积/元素/动效。
- 能设计可扩展的主题/阵营换肤，不复制组件。
- 能用数据驱动改版：定义指标、做实验、复盘。
- 能制定技术与性能预算，并说服团队接受取舍。
- 能判断“不做什么”，并说清楚失败条件。

### 练习 1：建立 UI 设计系统

为整个项目建立一套可被程序直接消费的系统。

要求：

- token：颜色、字号、间距、圆角、描边、阴影、动效时长/曲线。
- 组件：面板、按钮、卡片、资源项、徽记、进度条、提示条。
- 每个组件有完整状态矩阵，不只正常态。
- token 能导出为 JSON/CSS 变量/TS 常量，程序不手抄色值。
- 文档写清楚“什么时候用哪个组件、为什么”。

**过关标准：**

- 一个新人在 1 天内，仅凭文档做出一个合格的新界面。
- 改主色只改 1 个变量，所有界面同步更新。
- 组件状态覆盖 ≥6 种，且命名一致。
- 程序能在不问你色的情况下完成实现。

为什么是系统：精通不是“画得更好”，是“让别人也能做对”。
常见错误：把组件库当系统，只收集好看组件，没有规则和状态。

### 练习 2：做一次 30% 的减法

在不降低任务成功率的前提下，把常驻 HUD 的面积减少 30%。

要求：

- 先测量现状：HUD 占屏比、任务完成时间、误触率。
- 用折叠/情境/渐进披露减少常驻元素。
- 改完后重测同一批任务。
- 写一份复盘：减了什么、为什么、代价是什么。

**过关标准：**

- HUD 面积减少 ≥30%。
- 关键任务（造农人→采谷→造田）完成时间不增加超过 10%。
- 新手任务成功率不下降。
- 有 3 条明确的“我们决定不显示”的理由。

为什么是减法：RTS 的 UI 很容易越加越多；精通的设计师知道什么时候停。
常见错误：为了“简洁”把关键信息藏起来，结果新手完成时间翻倍。

### 练习 3：三阵营换肤

设计华夏/东夷/苗蛮三套 UI 主题，复用同一套组件。

要求：

- 只改 token（颜色、纹样、图标母题），不改布局和组件结构。
- 每个阵营有独立的识别色，但保留敌我语义色。
- 换肤后对比度、可读性仍达标。
- 图标母题变化不破坏 24px 可辨性。

**过关标准：**

- 换肤不需要复制组件，不需要改代码结构。
- 三套主题在灰度下仍能区分阵营（靠纹样/形状）。
- 对比度全部 ≥4.5:1。
- 新阵营接入时间 ≤1 天。

为什么是换肤：它检验系统是否真正“参数化”，而不是三套手抄。
常见错误：每个阵营一套独立组件，最后维护三倍。

### 练习 4：一次数据驱动的改版

选一个真实问题（比如“新手不知道怎么造田”），做一次完整改版。

要求：

- 定义指标：任务成功率、完成时间、误触率、求助次数。
- 找 5 个没玩过的人做基线测试。
- 改版，再测同一批任务。
- 记录失败的地方，不要只报喜。

**过关标准：**

- 指标有前后对比，且能解释变化原因。
- 至少 1 个假设被证伪，并写进复盘。
- 改版后没有引入新的可读性问题。
- 结论能指导下一个版本。

为什么是研究：精通的设计师不靠“我觉得”，靠“我测过”。
常见错误：只找朋友测试；只记录成功；把相关性当因果。

### 练习 5：技术选型与性能预算

写一份 UI 技术方案，覆盖：

- DOM/CSS vs Canvas vs 引擎 UI 的取舍。
- 图集、九宫格、字体子集、动效实现方式。
- Draw call、overdraw、纹理内存、UI 帧耗时的预算。
- 低端机降级策略。
- 验收方法与真机矩阵。

**过关标准：**

- 预算有数字：draw call < X、overdraw < Y、UI 帧耗时 < Z ms。
- 每个选择都有“代价”与“失败条件”。
- 能被程序复述并执行。
- 上线前有真机数据验证。

为什么是工程：UI 设计最终要在 60fps 的手机上跑；不懂代价的设计师只能做概念稿。

### 精通档的“过关”总结

你必须能**建立系统、做取舍、用数据证明、让团队执行**。这一档的标志不是作品更华丽，而是：

- 别人用你的系统能做对。
- 你能说出自己方案的失败条件。
- 你能为了可读性删掉自己喜欢的设计。

常见卡点：

- 把“风格强”当“水平高”。
- 只会加，不会减。
- 不做测量，靠审美权威。
- 系统只停在 Figma，落不到代码。
- 不考虑低端机和本地化。

---

## 怎么自评：三种证据

每一档的“过关”，都要同时具备：

1. **作品**：源文件 + 导出 + 真机截图。
2. **测量**：任务时间、成功率、误触率、对比度、帧耗时，至少两项。
3. **复盘**：为什么这样做、哪里失败、下次怎么改。

只有作品，是“会做图”；只有测量，是“会做实验”；只有复盘，是“会写文档”。三者都有，才是能力。

### 一个便宜的测试方法

- 找 5 个没玩过本作的人（同事/朋友/群友）。
- 给一个任务，不给说明，不提示。
- 录屏，记录：完成没有、用了多久、错了几次、在哪停住。
- 不要问“你觉得好看吗”，问“你刚才想做什么、为什么点这里”。

经验上，5 个人能暴露大部分严重可用性问题；这不是学术结论，是低成本的工程判断。

## 与项目里程碑的对应

| 阶段 | 对应能力档 | 该交出的 UI 成果 |
| --- | --- | --- |
| M1 主题化经济 | 入门 → 进阶 | 资源栏、德望、建造菜单、农人指令盘；手机横屏可玩 |
| M2 战斗与人心 | 进阶 | 战斗反馈链、多选、战报、警报、编队；50 单位可读 |
| M3 完整战役 | 进阶 → 精通 | 三阵营换肤、祭祀/外交/图鉴、本地化、无障碍、性能预算 |

不要把 M3 的“完整”当成 M1 的目标。UI 和玩法一样，先做能验证的最小闭环。

## 常见错误总表

1. 把“学完软件”当“入门”，没有交付物。
2. 只做正常态，不做禁用/冷却/不足/错误。
3. 只做静态稿，不做真机。
4. 只临摹，不解释为什么。
5. 追求视觉复杂度，忽略任务成功率。
6. 不做用户测试，靠自己和朋友的直觉。
7. 把设计系统做成“好看组件合集”，没有规则。
8. 只会加功能，不会做减法。
9. 不考虑低端机、本地化、色盲、字号缩放。
10. 没有失败条件的方案，通常是没想清楚。
