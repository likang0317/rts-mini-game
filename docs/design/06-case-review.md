# 06 现有 UI 稿复盘：一套优秀的概念稿，离“可交付的移动 UI”还差一次重做

> 这一章只做一件事：把 `docs/ui/UI-SPEC.md`、`docs/ui/ui-a.html` 和六张状态截图当成真实项目案例，逐条说清楚**好在哪、哪里不够顶尖、如果按这套方法会怎么改**。
>
> 先说结论：**它的视觉方向和文化表达是上乘的，信息架构有判断，状态覆盖也超出一般概念稿；但它本质上仍是一套 1920×1080 的桌面静态稿，触屏、适配、无障碍、性能这四门课基本没交卷。**

- [UI-SPEC.md](file:///D:/work/RTS小游戏/docs/ui/UI-SPEC.md)：设计基准、布局、行业对照、字体、图标、交互状态、验收。

- `docs/ui/shots/` 下的六张截图：空镜、选中、建造、祭祀、战斗、胜利。
- [DESIGN-v2.md](file:///D:/work/RTS小游戏/docs/DESIGN-v2.md) 中与 UI 相关的段落，用来核对“设计文档说的”和“UI 稿做的”是否一致。

## 1. 评分卡

分数不是给“好不好看”，是给“作为交付物还差多少”。

| 维度 | 分数 | 判断 |
| --- | --- | --- |
| 视觉方向与一致性 | 8.5 / 10 | 玄黑/土黄/玉青/朱砂的体系完整，克制、有辨识度 |
| 信息架构 | 7 / 10 | “德望不是资源”的判断很对；但部分必需信息缺失 |
| 桌面可用性 | 7.5 / 10 | 宏大屏成立，键鼠路径清楚 |
| 触屏可用性 | 2 / 10 | 无移动布局、无手势、无按压态、热键是无效信息 |
| 适配与无障碍 | 2.5 / 10 | 0 个 `@media`、0 个安全区、0 个减少动效、字号偏小 |
| 工程可落地性 | 5 / 10 | token 有意识，但大量硬编码；效果在手机上昂贵 |
| RTS 完整度 | 5.5 / 10 | 六状态不错，但缺警报、队列、空闲农人、设置/失败等 |
| **总评** | **5.5 / 10** | **优秀的概念稿，不是可交付的移动 UI** |

一句话：**这套稿子值得保留的是“审美判断”和“德望的叙事化”，需要重做的是“移动端的骨架”。**

## 2. 做得好的地方（这些不要丢）

### 2.1 视觉方向有“约束”，不是堆素材

它明确规定了：

- 圆角全部为 0，靠直角和切角建立“礼器/竹简”的气质。
- 纸纹、金线、暗角三种纹理，不超过三种。
- 玄黑 55% / 土黄 25% / 玉青 15% / 朱砂 5% 的用色比例。

为什么这是优点：**约束产生风格**。大多数独立游戏 UI 的问题是“每个界面都换一种质感”，这套稿子有统一的物质感。

### 2.2 把“德望”从资源里拿出来

这是全稿最重要的信息架构判断。德望不是第六种资源，而是：

- 有上限（100）、有阈值（60 可受禅）、有叙事（受禅/天命）。
- 用玉璧形态、刻度、印章，而不是资源格。
- 将满/圆满时才提高强度。

为什么这是优点：如果德望做成资源格，玩家会把它当“第 6 种矿”，整个“天命”叙事就降级成了数值。把它独立出来，是用 UI 表达玩法。
这一点应该在后续版本里保留，甚至强化（比如受禅前的全屏仪式、部族归附的德望门槛可视化）。

### 2.3 阅读顺序是“选 → 令 → 报”

底部控制台分成：

- 左：选中信息（谁）。
- 中：命令/建造（做什么）。
- 右：战报/编队（发生了什么）。

为什么这是优点：它对应了 RTS 的一次完整决策循环，而不是按“系统模块”拼面板。桌面键鼠下，这条路径是顺的。

### 2.4 状态覆盖超过一般概念稿

六个状态：空镜、选中、建造、祭祀、战斗、胜利。并且做了：

- 资源不足的禁用态，带“石木不足 10”的原因。
- 建造卡的造价、说明、禁用。
- 战斗中的伤害/德望飘字。
- 胜利结算的统计与“继续经营”。

为什么这是优点：很多概念稿只有一张“最漂亮的主界面”，这套稿子至少想到了“玩家会进入不同状态”。

### 2.5 token 与组件意识

CSS 变量、字号阶梯、间距、图标 24px 规则、B/C 两版复用约定，说明作者不是“画完就算”，而是想过交付。

### 2.6 图标是内联 SVG，不是 emoji

24×24 网格、1.5px 描边、统一光源，图标语言基本一致；没有用 emoji 糊弄。这在独立项目里已经是加分项。

### 2.7 胜利界面的“仪式感”

不是常见的“MVP/三星/再来一局”，而是“受禅、天命所归、继续经营”。这是把玩法、题材、UI 绑在一起的做法，值得保留。

## 3. 不够顶尖的地方

下面按严重程度排。每条都给**证据 → 为什么是问题 → 怎么改**。

### P0-1：移动端在数学上不成立

**证据**

- 设计基准是 1920×1080，最小 1440（[UI-SPEC.md L5](file:///D:/work/RTS小游戏/docs/ui/UI-SPEC.md#L5)）。
- 舞台按 1920 等比缩放（[UI-SPEC.md L24-L33](file:///D:/work/RTS小游戏/docs/ui/UI-SPEC.md#L24-L33)）。
- 命令按钮 96×96（[ui-a.html L209](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L209)、[L285](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L285)）。
- 正文/标签大量 9–10px（[ui-a.html L141](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L141)、[L193](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L193)、[L207](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L207)）。
- 全文件 **0 个 `@media`**（实测），没有任何断点。

**数学**

以 2400×1080 物理像素、DPR 3 的手机为例：

```
CSS 视口 = 800×360
1920 宽舞台缩放 = 800/1920 = 0.417
96px 按钮 → 40px（低于 44dp 下限）
10px 文字 → 4.2px
9px 文字  → 3.8px
```

即使按 `min(800/1920, 360/1080)` 算，缩放是 0.333，按钮只剩 32px、文字 3.3px。**这不是“小一点”，是不可读、不可点。**

**为什么是问题**

交付形态是 Android APK。移动端不是可选项，是主战场。当前稿在手机上无法完成“看清资源、点中命令、读出伤害”这三个基本任务。

**怎么改**

- 放弃“1920 画布等比缩”，改为 **dp 布局**：640×360dp 为最小横屏基准，800×360 为常见基准。
- HUD 用锚点/安全区重排，战场吃满剩余空间。
- 字号按 sp 设计：正文 ≥14sp，辅助 ≥12sp，最小 ≥11sp。
- 按钮 ≥56dp，间距 ≥8dp。
- 详见 [03-touch-and-adaptation.md](03-touch-and-adaptation.md)。

### P0-2：触屏交互基本缺失

**证据**

- 全文件 14 处 `:hover`，但没有 `:active`/按下态规范（实测 grep）。
- 命令按钮左上角写着 `Q/W/E/R/T` 热键（[ui-a.html L291](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L291)），手机上这些是无效信息。
- UI-SPEC 的交互状态只写了 hover 160–180ms、数值 200ms，没有按下、冷却、误触、长按、拖动、双指。
- 没有任何手势状态机。

**为什么是问题**

- 触屏没有 hover，所有“悬停才出现”的信息在手机上永远不出现。
- RTS 的命令按钮会被连续快速点击，缺少按下/冷却/防连点，玩家不知道有没有点上。
- 热键占用了按钮最宝贵的角标位置，却没告诉玩家“这个按钮现在能不能点”。

**怎么改**

- 每个按钮补：默认、按下、禁用、不可用原因、冷却、选中。
- 按下反馈 80–120ms，出现在手指上方，不被手指遮住。
- 热键只在检测到外接键盘时显示；触屏默认隐藏，把角标让给“缺多少/冷却”。
- 写一张手势状态表（点按/长按/拖动/捏合/边缘手势），定义阈值和冲突优先级。
- 详见 [03-touch-and-adaptation.md](03-touch-and-adaptation.md) 第 2 节。

### P0-3：没有安全区、没有无障碍、没有减少动效

**证据**

- `safe-area` 出现 0 次，`prefers-reduced-motion` 出现 0 次，`@media` 出现 0 次（实测）。
- 9px 字号在 1440 宽下只有 6.75px。
- 没有 UI 缩放、色盲模式、字号设置。

**为什么是问题**

- 刘海/挖孔/手势条会遮住 HUD；Android 的返回手势会和镜头拖动冲突。
- 9px 灰字 + 2.75:1 对比度，是在“看起来高级”和“读不清”之间选了后者。
- 色盲玩家无法区分敌我。

**怎么改**

- `viewport-fit=cover` + `env(safe-area-inset-*)`；HUD 内边距 `max(12dp, safe+8dp)`。
- 提供 80/100/120/130% UI 缩放；缩放后重排，不是简单放大。
- 敌我加形状通道；提供色盲模拟自检。
- 尊重 `prefers-reduced-motion`，战斗闪烁 ≤3Hz。

### P1-1：对比度不达标，而且不是个别现象

按 WCAG 相对亮度计算（背景取面板主色 `#26271D`）：

| 颜色 | 用途 | 对比度 | 判断 |
| --- | --- | --- | --- |
| `#6E6957` muted-500 | 大量 9–10px 说明 | **2.75:1** | 不合格（正文需 4.5:1） |
| `#8F8874` muted-400 | 标签/战报 | 4.27:1 | 边缘，小字不合格 |
| `#9E3B32` 朱砂-500 | 警示/不足 | **2.25:1** | 不合格 |
| `#D0695A` 朱砂-300 | 深底文字 | 4.21:1 | 仅大字可用 |
| `#7C9E8E` 玉青-500 | 友军/可用 | 5.13:1 | 合格 |

**证据**：`muted-500` 用于选中说明（[ui-a.html L207](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L207)）、战报时间（[L411](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L411)）、空态说明（[L309](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L309)）；`muted-400` 大量用于 9–10px 标签。

**为什么是问题**

暗色界面的“高级感”很容易靠压暗文字获得，但代价是信息不可读。RTS 玩家在战斗中不会凑近屏幕辨认。

**怎么改**

- 正文改用 `#CEC6AF`（8.86:1）或 `#ABA38D`（6.01:1）。
- 9–10px 说明提升到 12sp，并把 muted-500 提到 muted-400 以上。
- 朱砂文字改用 `#D0695A`，且只用于大字/图标；小字警示用琥珀 + 图标 + 文案。
- 用脚本对每个 token 跑对比度，写进验收。

### P1-2：小地图的比例和视野框是错的

**证据**

- UI-SPEC 说小地图约 320×120（[UI-SPEC.md L275-L277](file:///D:/work/RTS小游戏/docs/ui/UI-SPEC.md#L275-L277)），世界是 40×30（4:3）。
- 代码里 SVG `viewBox="0 0 240 168"`，却 `preserveAspectRatio="none"`（[ui-a.html L1641](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L1641)），会被容器拉伸成约 2.2:1（世界是 1.33:1）。
- UI-SPEC 说视野框是“斜切梯形”，但代码画的是轴对齐矩形（[ui-a.html L1660 附近](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L1660)）。

**为什么是问题**

- 比例不一致，点击小地图的坐标映射会错位；玩家点“河湾”，镜头跑到别处。
- 正交俯视相机的视野在平面地图上就是矩形；画成梯形会让玩家误以为镜头有透视/旋转，也会让“视野范围”失真。
- 文档和实现不一致，后续程序不知道以哪个为准。

**怎么改**

- 小地图宽高比 = 世界宽高比（40:30 = 4:3），或者在小地图内部做 letterbox，不要拉伸。
- 视野框用矩形；如果镜头有旋转，再考虑旋转矩形。
- 实现点击/拖动映射，并用单元测试验证四个角。
- 把 UI-SPEC 的描述改成和实现一致。

### P1-3：多选卡片的“12 个才折叠”阈值太晚

**证据**

- 选中面板宽 296px（[ui-a.html L245](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L245)）。
- UI-SPEC 说“超过 12 个折叠为图标 ×N”（[UI-SPEC.md L272-L273](file:///D:/work/RTS小游戏/docs/ui/UI-SPEC.md#L272-L273)）。
- 12 张卡 + 11 个 6px 间距 = 66px；剩余约 200–230px / 12 ≈ **16–19px/张**。

**为什么是问题**

16–19px 宽的卡片既放不下兵种图标，也点不中。RTS 多选 12 个单位很常见，这正是最需要看清的时候。

**怎么改**

- 阈值降到 6–8 个；超过后用“图标 + ×N”聚合，或改为横向滚动。
- 多选时优先显示“兵种构成 + 总血量”，而不是 12 张同样的卡。
- 选中面板在无选中时折叠，把空间还给命令/战报。

### P1-4：“底部低于 1/4 屏”这个说法不成立

**证据**：`height: 300px`（[ui-a.html L163](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L163)），1080 高 → **27.8%**，高于 1/4。UI-SPEC 却写“低于 1/4 屏”（[UI-SPEC.md L75](file:///D:/work/RTS小游戏/docs/ui/UI-SPEC.md#L75)）。

**为什么是问题**：这不是小数点问题，是设计目标没有用数值验收。27.8% 已经超过桌面 RTS 的常见上限，手机上更紧。

**怎么改**

- 把目标改成“≤22%（手机横屏）/ ≤25%（桌面）”，并按占屏面积而不是固定高度验收。
- 压缩控制台：无选中时折叠选中面板；战报默认只显示最近 1 条；编队可折叠。
- 用 640×360dp 重新算：底部操作区 ≤80dp。

### P1-5：行业对照表有事实错误，导致“为什么”站不住

**证据**：[UI-SPEC.md L40-L52](file:///D:/work/RTS小游戏/docs/ui/UI-SPEC.md#L40-L52) 的对照表写：

- 星际争霸 2：资源“顶部左”，命令卡“底部中央偏右”。
- 魔兽争霸 3：资源“顶部左”。
- 帝国时代 2：资源“顶部左”。

实际（按游戏界面）：

- **星际争霸 2**：资源在**右上**；命令卡在**右下 3×5**；小地图在左下；选中信息在中下。命令卡的 3×5 网格与 Grid 热键是公认设计，可查 [Liquipedia](https://liquipedia.net/starcraft2/Hotkeys_per_Race)。
- **魔兽争霸 3**：资源在**右上**；命令卡在右下；小地图在左下。
- **帝国时代 2**：资源在顶部通栏（从左上起排），这一条基本对。

**为什么是问题**

这套稿子的结论（资源靠边、命令卡靠拇指）不一定错，但它的论证建立在错误事实上。更麻烦的是：**SC2/WC3 把资源放右上，恰恰说明“资源可以放在远端只读区”**——这反而支持本稿把资源放底部/边缘的选择，但理由要重写。

**怎么改**

- 重画对照表，逐项核对真实界面；不确定的标注“待复核”。
- 结论改成：“资源是只读信息，可以放远端；命令是高频操作，必须靠近拇指/鼠标。SC2/WC3 用右上资源 + 右下命令卡，证明的是‘读写分离’，不是‘资源必须在左上’。”
- 这样论证反而更强。

### P1-6：颜色语义过载

**证据**

| 颜色 | 现有用途 | 问题 |
| --- | --- | --- |
| 朱砂 | 敌方、资源不足、危险、印章装饰 | 玩家分不清“红”是敌情还是缺钱 |
| 玉青 | 友军、玉资源、可建造、天气 | “青”既是我方又是资源还是可用 |
| 土黄 | 华夏主色、描边、德望、高亮 | 金色到处都是，高亮不突出 |

**为什么是问题**：颜色是稀缺资源。一个颜色承担三种含义，等于没有含义。战斗中玩家需要 0.2 秒判断“红色=敌人”，如果红色还表示“缺石”，判断会被打断。

**怎么改**

- 朱砂只保留“敌方/危险”；资源不足改琥珀 + 图标 + 文案。
- 玉青保留“友军/可操作”；玉资源用图标区分，不靠颜色。
- 土黄保留“结构/描边”；德望用玉璧形态区分，不靠颜色。
- 加形状/图案通道，色盲也能读。

### P1-7：扩展性没有兑现

**证据**

- 资源条固定 5 项 + 人口 86px；M3 要加“铜”，没有位置。
- UI-SPEC 说 B/C 两版“复用 token，一个变量都不要改”，但 `ui-a.html` 里有 **100 处** `rgba(200,162,74,...)` 硬编码、**468 个**十六进制色值（含内联 SVG，实测）。换阵营主题需要全局替换，不是改一个变量。
- 建造卡固定 178px 宽；英文/德文一长就溢出。
- 所有文案中文，没有本地化表。

**为什么是问题**

- 加一个资源就要重排，说明布局不是数据驱动的。
- “换肤不改组件”是设计系统的核心承诺；硬编码让这个承诺落空。
- 三阵营是 M3 的核心卖点，UI 必须先支持。

**怎么改**

- 资源条改成数据驱动：`resources: [{id, icon, value, max}]`，布局用 flex/grid，自动增减。
- 把所有 `rgba(200,162,74,...)` 收进 `--accent-*` 变量；SVG 图标用 `currentColor`。
- 建造卡用 `min-width`/`max-width` + 两行文本，不写死 178px。
- 文案全部走 `i18n` 表，做中/英/德三版长度测试。

### P1-8：缺少 RTS 的“必需态”

**证据**：六状态覆盖了空镜/选中/建造/祭祀/战斗/胜利，但没有：

- 受攻击警报（方向、声音、震动）。
- 人口卡满/将满提示。
- 空闲农人提示。
- 生产队列/取消。
- 建造时间、占地、前置条件。
- 暂停/设置/失败/重开。
- 教程/首次引导。
- 断线/加载/错误 toast。
- 单位死亡后选中面板的空态。
- 资源将满/已满。

**为什么是问题**

这些不是“锦上添花”，是 RTS 的基本操作回路。没有空闲农人提示，新手会漏经济；没有受攻击警报，玩家会莫名其妙输掉；没有队列，玩家不知道兵什么时候出来。

**怎么改**

- 先补“警报层”：受攻击、人口卡住、空闲农人、建造完成、德望将满。用统一的事件优先级和视觉强度。
- 补“生产队列”：图标 + 进度 + 取消。
- 补“建造卡信息”：造价、时间、占地、前置、不可用原因。
- 补“系统态”：暂停、设置、失败、加载、错误。
- 详见 [02-information-and-readability.md](02-information-and-readability.md) 第 2、4 节。

### P1-9：性能风险被低估

**证据**（实测）：

- 每个面板 `::after` 叠噪点 + `mix-blend-mode: overlay`（[ui-a.html L123](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L123)、[L238](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L238)、[L466](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L466)）。
- 全屏 grain：`feTurbulence` + `mix-blend-mode: overlay`（[L1133](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L1133)）。
- 全屏雾气层：`filter: blur(10px)` + 46 秒循环动画（[L100](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L100)）。
- `backdrop-filter: blur(10px)`（[L425](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L425)）和 `blur(5px)`（[L457](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L457)）。
- 大面积阴影、渐变、多层半透明。

**为什么是问题**

这些效果在桌面 Chrome 上很便宜，在 Android WebView + 中低端 GPU 上是 fill rate 杀手。尤其是全屏 blur + blend + 动态雾气叠加，可能直接把 60fps 打到 30fps。

**怎么改**

- 噪点、雾气、渐变、阴影**预烘焙**进九宫格贴图；运行时不再做 `blur`/`mix-blend-mode`/`feTurbulence`。
- 去掉全屏动态雾气；用静态暗角贴图。
- `backdrop-filter` 只在大块模态上保留，且提供低端机关闭。
- 用真机测：UI 帧耗时 ≤4ms，draw call ≤30。
- 详见 [05-engineering.md](05-engineering.md) 第 7 节。

### P1-10：字体与本地化没有落地

**证据**

- 字体栈是系统字体（[UI-SPEC.md L154 附近](file:///D:/work/RTS小游戏/docs/ui/UI-SPEC.md#L154)）；Android 通常没有 Source Han Serif/Songti/SimSun。
- 9px/10px 大量使用，且字距 0.14–0.24em（[ui-a.html L137-L152](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L137-L152)）。
- 所有文案中文；固定宽度容器多（96px 按钮、178px 卡、296px 选中面板、380/340px 侧栏）。

**为什么是问题**

- 设计稿里的宋体气质，在 Android 上会回退成另一种字；最坏情况是标题和正文都变成系统黑体。
- 小字号 + 大字距，中文可读性进一步下降。
- 英文/德文一长，固定宽度就溢出。

**怎么改**

- 嵌入一个中文标题字体子集（3500 字 + 标点，约 1–3MB），正文用系统黑体；或者接受标题也用黑体，用排版做古意。
- 小字去掉大字距；正文 ≥12sp。
- 容器用 min/max + 换行，不写死宽；做中/英/德三版长度测试。
- 数字用等宽，资源变化不抖动。

### P2-1：装饰在部分状态里压过了内容

**证据**：建造态（`a-03-build.png`）里，三张建造卡非常暗，卡内文字和造价对比度低；“大邑”禁用卡几乎融进背景。空镜态（`a-01-empty.png`）底部控制台 920×288 大部分是空的，但边框、角饰、分隔线仍然很重。

**为什么是问题**：装饰的任务是“建立物质感”，不是“抢注意力”。当卡片内容读不清、空态大面积留白时，装饰就显得吵。

**怎么改**

- 角饰只保留在模态/结算等“仪式性”界面；常驻 HUD 用更轻的分隔。
- 建造卡提高底/字对比度；禁用态用“降饱和 + 明确原因”，不是“整体压黑”。
- 空态减少边框层级，用一句“择地而居”+ 一个主操作，而不是两列热键。

### P2-2：文档与实现漂移

**证据**

- [DESIGN-v2.md](file:///D:/work/RTS小游戏/docs/DESIGN-v2.md) 的 UI 段落写“资源在顶部左、德望环形刻度”；UI-A 实际是“资源在底部左、德望横向条 + 玉璧”。
- UI-SPEC 说小地图是梯形视野框；代码是矩形。
- UI-SPEC 说底部低于 1/4；代码是 27.8%。

**为什么是问题**：程序、美术、策划各拿一份文档，最后没人知道哪个是准的。UI 返工大多不是“做错了”，是“做的是另一版”。

**怎么改**

- 指定 `UI-SPEC.md` 为唯一视觉契约；DESIGN-v2 只引用，不重复描述布局。
- 每次改动同时更新：spec、HTML、截图、状态矩阵。
- 加一条“文档与实现不一致”检查项到验收。

### P2-3：胜利/模态的固定尺寸

**证据**：胜利面板 980px 宽（[ui-a.html L459](file:///D:/work/RTS小游戏/docs/ui/ui-a.html#L459)）、`vic-inner` 固定布局；手机上必然溢出。

**怎么改**：模态用 `max-width: min(980px, 92vw)`，内部用流式布局；小屏改为全屏 sheet。

## 4. 如果按这套方法改：三步重做

### 第一步：换骨架（移动优先）

目标：640×360dp 能玩，800×360dp 舒适，4:3 平板不空。

```
┌──────────────────────────────────────────────────────┐
│ 谷 320  木 140  石 90  玉 45  人口 9/16   德望 62/100 │ 40dp，只读
│                                                      │
│                                                      │
│                      战 场                            │
│                                                      │
│                                                      │
│ ┌──────────┐                        ┌──────────────┐ │
│ │ 小地图    │                        │  3×2 命令盘  │ │
│ │ 120×90   │                        │  56dp        │ │
│ └──────────┘                        └──────────────┘ │
│  编队条（可折叠）        建造/祭祀 = 底部抽屉（二级）  │
└──────────────────────────────────────────────────────┘
```

- 资源/德望：顶部只读，图标 + 数字；名称长按查看。
- 左拇指：小地图 + 镜头 + 框选。
- 右拇指：3×2 命令盘；建造/祭祀从底部抽屉展开，不常驻。
- 选中信息：压缩成命令盘上方的一条（兵种构成 + 总血量），无选中时消失。
- 战报：默认折叠为最近 1 条，点开看历史。
- 警报：受攻击/人口卡住/空闲农人/建造完成，用屏幕边缘 + 声音 + 短震动。
- 所有 HUD 处理安全区；竖屏只做提示，不主推。

### 第二步：换视觉参数（保留气质，提升可读）

| 项目 | 现在 | 改后 |
| --- | --- | --- |
| 正文 | 9–10px，muted-500（2.75:1） | ≥12sp，`#ABA38D`（6.01:1）以上 |
| 数字 | 17px，等宽 | ≥18sp，等宽，资源变化不抖 |
| 朱砂文字 | `#9E3B32`（2.25:1） | `#D0695A`（4.21:1），仅大字/图标 |
| 按钮 | 96px（桌面） | 56–64dp，间距 ≥8dp |
| HUD 面积 | 27.8% | ≤22%（手机横屏） |
| 装饰 | 每个面板噪点 + 全屏 grain | 仅大面板静态纹理；全屏 grain 删除 |
| 模糊 | 全屏 drift blur + backdrop-filter | 预烘焙暗角/底图；低端机关闭 |
| 圆角 | 0 | 保留 0；这是风格，不用改 |
| 字体 | 系统宋体栈 | 标题嵌入选定子集；正文系统黑体 |

保留：玄黑/土黄/玉青/朱砂的色板、直角/切角、纸纹质感、玉璧德望、印章胜利。

### 第三步：补必需态与交付物

- 警报层：受攻击、人口卡住、空闲农人、建造完成、德望将满。
- 生产队列：图标 + 进度 + 取消。
- 建造卡：造价、时间、占地、前置、不可用原因。
- 危险操作：撤退/拆除二次确认或 1.5 秒撤销。
- 系统态：暂停、设置、失败、加载、断线、错误 toast。
- 本地化：中/英/德三版；容器弹性；无图片文字。
- 无障碍：UI 缩放、色盲模拟、减少动效。
- 性能：图集、九宫格、字体子集、DPR 上限、低端机降级。
- 验收：3 种分辨率、3 台真机、5 人任务测试、性能数据。

| 指标 | 现状 | 目标 |
| --- | --- | --- |
| 手机横屏可玩 | 不成立 | 640×360dp 可完成核心循环 |

| UI 帧耗时 | 未测 | ≤4ms（中端机） |

## 5. 复盘时常见的错误

1. **只看截图，不看交互。** 截图能看出风格，看不出按压态、误触、冷却、切后台回来后的状态。
2. **把风格当水平。** 视觉统一只是及格线；信息架构、触屏、性能才是分水岭。
3. **不做数学核算。** “手机上应该能看清”不是判断，`96 × 0.333 = 32px` 才是。
4. **只批评，不给改法。** 说“移动端不行”很容易，给出 dp 布局、按钮尺寸、验收指标才有用。
5. **把“移动端适配”理解成“等比缩小”。** 缩小会把字号和可点区域一起杀死。
6. **忽略文档漂移。** 设计文档、HTML、截图各说一套，最后没人知道以哪个为准。
7. **用“个人审美”替代用户测试。** 找 5 个没玩过的人做 5 分钟任务，比争论十次有用。

---

## 6. 如果只能改三件事

1. **把 1920 画布换成 dp 布局**：640×360dp 起，HUD 锚点 + 安全区，战场自适应。这一件不改，APK 上的 UI 就是不可用的。
2. **把 hover 换成触屏状态机**：按下/禁用/冷却/误触/撤销，按钮 ≥56dp，命令盘放右下拇指区。这一件决定“能不能打”。
3. **把文字从 9–10px 灰字提到 12sp、4.5:1 以上**：保留宋体标题，但正文必须能读。这一件决定“能不能看懂”。

这三件做完，再谈动效、换肤、无障碍，才有意义。

## 7. 事实核对表

| UI-SPEC 的说法 | 实际/核对结果 | 影响 |
| --- | --- | --- |
| SC2 资源在顶部左 | 实际在**右上**；命令卡右下 3×5；小地图左下 | 论证前提错误，但“读写分离”的结论仍可成立 |
| SC2 命令卡在底部中央偏右 | 实际在最右下 3×5 网格 | 位置描述不准 |
| WC3 资源在顶部左 | 实际在**右上** | 同上 |
| AoE2 资源在顶部通栏 | 基本正确（顶部通栏，左上起排） | — |
| 底部 300px 低于 1/4 屏 | 300/1080 = **27.8%** | 目标未用数值验收 |
| 小地图 320×120，4:3 地图 | 代码 `240×168` 且 `preserveAspectRatio="none"`，被拉成约 2.2:1 | 点击映射会错位 |
| 小地图用斜切梯形视野框 | 代码是轴对齐矩形；正交俯视应为矩形 | 文档与实现不一致，概念也不对 |
| 9px 仅用于眉标 | 实测大量 9–10px 用于标签/说明/战报 | 小字可读性风险 |
| B/C 复用 token，一个变量不用改 | 100 处硬编码金色、468 个 hex | 换肤需全局替换，不是参数化 |
| HUD 明度低于地图受光区 | 截图里金色边框/控制台仍然抢眼；建造卡过暗 | 主观看成立，但需以对比度数据验收 |

> 说明：SC2/WC3 的界面布局按游戏实际画面与 Liquipedia 的命令卡资料核对；“最佳布局”的判断属于个人经验，不是唯一答案。

## 8. 结论

这套稿子最值钱的不是“画得好”，而是三件事：

1. **它有明确的物质感**：玄黑、土黄、玉青、朱砂、直角、纸纹，放在一堆“赛博玻璃”手游 UI 里有辨识度。
2. **它把德望当叙事，而不是资源**：这是玩法与 UI 真正结合的地方。
3. **它想到了状态**：禁用、不足、战斗、胜利，不是只有一张主界面。

但它离“顶尖”还差一次**从桌面概念稿到移动产品**的转变：

- 不是把 1920 缩小，而是按 dp 重排。
- 不是把 hover 改成 touch，而是重写输入状态机。
- 不是把字调大，而是重新分配信息密度。
- 不是加更多装饰，而是删掉引擎跑不动的效果。

如果按上面的三步改，它会从“一张很帅的设定图”变成“一套能在手机上打完整一局的 UI”。这才是这套资料希望你达到的标准。
