# 02 信息、可读性与反馈：游戏 UI 的专业内核

> 这一章讲的是“玩家在压力下能不能看懂、能不能做对”。它不讨论风格，只讨论判断。风格可以换，判断错了，换什么风格都救不回来。

## 先建立三个读速

玩家看 UI 的时间不是均匀的，大致分三档：

| 读速 | 时间 | 看什么 | 设计责任 |
| --- | --- | --- | --- |
| 扫 | 0.2–0.5 秒 | 颜色、形状、位置、数字量级 | 必须“不读字也懂” |
| 读 | 1–2 秒 | 单位名、资源差多少、按钮能不能点 | 文字必须一次读懂 |
| 研究 | 10 秒以上 | 属性、说明、造价明细、战报 | 可以密，但要可检索 |

RTS 的绝大部分时间花在“扫”。所以游戏 UI 的第一原则不是“信息齐全”，而是**在正确的时刻，让正确的信息以正确的强度出现**。

为什么：RTS 玩家的注意力在主战场，HUD 是余光。要求玩家把视线移到角落、逐字阅读，等于在每个决策点收一次税。
常见错误：把所有系统都常驻，把所有说明都写成一句话，结果每个都很小、都很灰、都读不清。

## 1. 信息架构：先决定“什么不该显示”

### 1.1 用“频率 × 后果”分级

把每一条信息放进下面这个矩阵，而不是按“系统模块”排布：

| | 后果高（错了会输/会浪费） | 后果低 |
| --- | --- | --- |
| **频率高** | 常驻、最大、最靠视线中心：资源、人口、命令、选中状态 | 常驻但可压缩：战报、编队 |
| **频率低** | 情境出现、强提醒：受攻击、人口卡住、建造完成、德望将满 | 按需展开：属性、说明、图鉴 |

三条推论：

1. **高频高后果**的信息不能藏进二级菜单。资源、人口、当前可执行命令必须在主界面。
2. **低频高后果**的信息要用“事件”出现，而不是常驻。比如“受攻击”不应该是一行小字，而是一个带方向、带声音、带震动的警报。
3. **低频低后果**的信息应该被折叠。属性说明、建筑背景、图鉴，点开再看。

为什么：屏幕面积和注意力都是有限预算。常驻一条低频信息，就挤掉一条高频信息的位置。
常见错误：把“系统入口”当“信息”。设置、图鉴、排行榜不需要常驻在战斗 HUD 里。

### 1.2 三层信息结构

任何一屏 UI 都可以分成三层：

- **决策层**：现在要做什么。资源够不够、命令能不能点、目标在哪。
- **确认层**：做完之后发生了什么。建造进度、单位状态、伤害、资源变化。
- **叙事层**：我是谁、局势如何。势力名、天气、任务、德望。

三层的视觉强度必须递减。很多“看起来很满”的界面，问题不是元素多，而是**三层一样重**。

本项目的对应关系：

| 层 | 本项目内容 | 应该放哪 | 强度 |
| --- | --- | --- | --- |
| 决策 | 谷/木/石/玉、人口、命令卡、建造卡、小地图 | 拇指/鼠标可达区，屏幕边缘 | 最高 |
| 确认 | 选中信息、血条、飘字、进度、战报 | 选中附近 + 屏幕边缘 | 中 |
| 叙事 | 轩辕、任务、大雾、德望 | 顶部/独立面板 | 低到中 |

为什么：玩家的眼睛先找“能做什么”，再找“做了什么”，最后才看“我是谁”。
常见错误：把势力名做成 25px 宋体大字加发光，把资源数字做成 17px 灰字。视觉强度和决策重要性反了。

### 1.3 视线路径

RTS 的视线中心是**屏幕中部偏下的战场**，不是 HUD。由此得到两条布局原则：

1. 重要读数放在边缘，但不能要求玩家“移到角落再移回来”。资源、人口、小地图最好在同一侧，形成一次扫视的闭环。
2. 命令区放在拇指/鼠标自然停留位。桌面是屏幕中下偏右，手机是右下拇指弧。

为什么：这不是审美，是眼球和手指的物理路径。
常见错误：资源在左上、小地图在左下、命令在右下、选中信息在正下——玩家每做一次决策要跨四次屏。

### 1.4 层级手段的强弱排序

从强到弱：

```
位置 > 尺寸 > 明度对比 > 颜色 > 字重/字号 > 装饰（描边、发光、纹理）
```

为什么：位置决定“会不会被看到”，明度决定“能不能读清”，装饰只决定“好不好看”。很多设计一上来就用发光和描边堆层级，结果所有东西都在发光，等于没有层级。

常见错误：

- 用外发光区分选中态。战场上 20 个单位都发光时，谁也看不出谁被选中。
- 用颜色区分敌我，却不给形状差异。色盲玩家直接失去信息。
- 用 1px 描边区分可点击/不可点击。手机上根本看不见。

## 2. HUD 密度：不是越少越好，是“该在的都在，不该在的都不在”

### 2.1 给 HUD 定面积预算

一个可用的经验区间：

| 平台 | 常驻 HUD 占屏面积 | 底部操作区高度 |
| --- | --- | --- |
| 桌面 RTS | 18–28% | ≤ 25% |
| 手机横屏 RTS | 15–22% | ≤ 22%（含安全区） |
| 手机竖屏 | 25–35% | ≤ 30% |

本项目现有稿是 1920×1080、底部 300px，占比 **27.8%**，已经超过桌面区间上限；手机横屏更紧。详见第 06 章的核算。

为什么：RTS 的战场可见面积直接等于战术信息量。HUD 每多占 5%，就少看见一片兵。
常见错误：用“面板高度”而不是“占屏比”来定尺寸；换到 20:9 手机后，底部面板显得更矮，但实际可点区域更小。

### 2.2 常驻 / 情境 / 按需

把 HUD 元素分成三种存在方式：

- **常驻**：资源、人口、小地图、当前命令。始终可见。
- **情境**：选中信息、建造菜单、祭祀预览。有选中/有操作时才出现。
- **按需**：属性详情、图鉴、战报历史、设置。点开才出现。

本项目的现状与建议：

| 元素 | 现状 | 建议 |
| --- | --- | --- |
| 资源条 | 常驻，5 项 + 人口 | 保留常驻，但压缩标签，数字优先 |
| 德望 | 常驻独立面板 | 保留；将满/圆满时才提高强度 |
| 选中信息 | 常驻占 296px | 无选中时折叠，把空间还给命令/战报 |
| 战报 | 常驻 340px | 战斗中常驻；非战斗折叠为最近 1 条 |
| 编队 | 常驻 104px | 触屏上改为可展开的编组条 |
| 属性/说明 | 常驻小字 | 改为长按/点按查看 |

为什么：常驻元素越多，玩家越难在 0.3 秒内找到“现在该点哪”。
常见错误：无选中时仍然保留一整块“未选中部众”的空白面板，既占地方又没有信息。

### 2.3 渐进披露

复杂操作分两步，而不是一次全铺开：

```
第一步：选类别（营造 / 祭祀 / 训练）
第二步：选具体项（大邑 / 粟田 / 祭坛）
```

每一步只显示当前可做的 3–6 项，附带“为什么不能做”。

为什么：一次显示 15 个按钮，玩家要读 15 次；分两步，每步读 5 次，而且第二步可以只显示相关的。
常见错误：把所有建筑塞进一个 4×4 网格，用灰色表示不可建，却不写原因。玩家只看到“一大片灰”。

### 2.4 信息密度的三个反模式

1. **三重冗余**：图标 + 名称 + 数值 + 说明同时出现，但每一项都很小。保留两项，放大。
2. **同权并列**：谷/木/石/玉/人口/德望一样大。德望是叙事资源，应该升格或降格，不能并列。
3. **装饰占位**：角饰、花纹、分隔线占了 30% 的视觉面积，却不承载信息。

为什么：冗余不是错，错在“冗余但都看不清”。信息密度应该用“可读的信息量”衡量，不是“元素个数”。

## 3. 战场可读性：俯视角下如何一眼分清单位和状态

这是 RTS UI 最容易被平面设计师低估的部分。它不是 HUD，是**战场本身的信息设计**。

### 3.1 剪影优先

在 32×32 到 64×64 的尺寸下，玩家认单位靠轮廓，不靠细节：

- 农人：弯腰 + 背篓/铲，最矮。
- 近战：宽肩 + 横持戈/钺。
- 远程：侧身 + 弓弧/投矛线。
- 精英：高冠/大肩/披风，高 1/4。
- 祭司：直杖 + 玉琮轮廓。

为什么：战斗中单位只占几十像素，五官和纹样全部丢失，只有外轮廓还在。
常见错误：给每个单位画精细的衣服纹样，缩小后全变成噪点；四个兵种看起来一样。

### 3.2 敌我不能只靠颜色

最低要求是**双通道编码**：

| 通道 | 友军 | 敌军 | 中立 |
| --- | --- | --- | --- |
| 颜色 | 玉青 | 朱砂 | 灰白/土黄 |
| 形状 | 圆环/盾形底 | 三角/尖角底 | 菱形 |
| 血条 | 玉青 | 朱砂 | 不显示 |

为什么：红绿色盲约占男性 8%，只靠红/绿区分敌我，等于让这部分玩家失去核心信息。
常见错误：友军绿色、敌军红色，其他全一样；色盲模拟一开，两边完全分不清。

### 3.3 头顶信息的预算

每个单位头顶最多同时显示三样：

1. 血条（只在受伤/选中/鼠标悬停时出现）
2. 一个状态图标（增益/减益/动作）
3. 一个短标签（“耕作中 64%”“建造中”）

超过三样，战场就会变成“文字雨”。

为什么：50 个单位 × 3 条信息 = 150 个视觉元素，已经接近屏幕噪声阈值。
常见错误：所有单位常驻血条；每个单位都显示名字；伤害飘字不合并、不 pooling，叠成一团。

### 3.4 缩放级别与 LOD

RTS 至少有三种缩放：

- **远**：看阵型、看资源点、看敌方推进。单位只需色块 + 阵营色 + 轮廓。
- **中**：看兵种、看血量、看动作。显示剪影 + 血条。
- **近**：看细节、看建造、看祭祀。显示完整动画和标签。

为什么：同一套信息在所有缩放级别都显示，远看是噪点，近看又不够。
常见错误：镜头拉远后，名字和血条仍然一样大，遮住半个屏幕。

### 3.5 选中与指令反馈

- **选中环**：2px 高对比描边 + 底部短弧，不用大面积发光。
- **框选框**：半透明填充 + 1px 虚线，不能遮住单位。
- **移动目标**：地面落点标记 + 短暂路径线，0.4 秒内消失。
- **攻击目标**：目标脚下红环 + 一条细线，线不能比单位更亮。

为什么：反馈要“指向对象”，而不是“照亮屏幕”。
常见错误：选中特效比单位还大；攻击线用高饱和红色粗线，战斗中像激光秀。

### 3.6 战场与 HUD 的明度关系

HUD 的明度应该低于战场受光区，形成“画框中看画”的关系。但“低”不等于“糊”：

- HUD 面板底可以暗，但文字/数字必须保持 4.5:1 以上。
- 战场可以有雾气/暗角，但单位剪影必须和地形有明度差。
- 不要把“氛围滤镜”盖在单位上；滤镜应该只作用于地形层。

为什么：玩家需要先看清单位，再感受气氛。顺序反了，就是“好看但打不了”。
常见错误：全屏黄色雾化 + 低对比单位，截图很统一，实战找不到兵。

## 4. 状态反馈与动效节奏

### 4.1 反馈要回答四个问题

任何一次操作反馈，都应该让玩家在 0.5 秒内回答：

1. 发生了什么？（选中/移动/攻击/建造/资源变化）
2. 对我有利吗？（+3 德望 / −14 气血 / 资源不足）
3. 有多强？（数值、进度、范围）
4. 下一步是什么？（可继续/需等待/需换目标）

为什么：反馈不是“动一下”，是“传递决策所需的信息”。
常见错误：按钮按下去只变暗，玩家不知道是“按到了”还是“不能按”。

### 4.2 时间尺度

| 时长 | 用途 | 例子 |
| --- | --- | --- |
| 0–100ms | 即时确认 | 按钮按下、单位被选中 |
| 100–200ms | 状态切换 | hover→active、面板展开 |
| 200–400ms | 强调 | 资源 +20、建造完成、德望将满 |
| 400–1000ms | 叙事 | 祭祀完成、胜利结算 |
| >1s | 过场 | 只用于非交互时刻 |

为什么：低于 100ms 人眼几乎感知不到“过程”，只感知“结果”；高于 400ms 的反馈会打断操作节奏。
常见错误：所有动画都 300ms；战斗中每个数字都做 500ms 滚动，玩家读不完。

### 4.3 缓动

- 进入/强调：`ease-out`（快起慢停），让玩家看到“到达”。
- 离开/收起：`ease-in`（慢起快走），不拖泥带水。
- 呼吸/循环：`ease-in-out`，幅度 ≤ 20%。
- 不要默认 `bounce`。弹跳属于风格化，和“礼器式 HUD”的克制气质冲突。

为什么：缓动传达物理感。ease-out 像“落定”，bounce 像“玩具”。
常见错误：面板展开用弹簧，结果像手机 App，不像上古军帐。

### 4.4 数值变化

资源数字是最容易做坏的地方。三种做法：

| 做法 | 适用 | 代价 |
| --- | --- | --- |
| 直接替换 + 闪色 150ms | 高频、小额变化（+10 谷） | 最低，推荐默认 |
| 滚动数字 200–300ms | 中额、需要感知“涨了” | 需要等宽数字，否则抖动 |
| 飘字 +N / −N | 战斗、德望、祭祀 | 需要 pooling，避免叠加 |

规则：

- 数字容器必须 `tabular-nums`，否则 1 和 8 宽度不同，滚动时会抖。
- 同屏飘字不超过 8–12 个；超出合并为“+N”。
- 资源不足时，不要只变红；同时给出“缺多少”（“石木不足 10”）。

为什么：玩家对“数字在变”比对“数字是多少”更敏感；但变化太多会淹没真正的信息。
常见错误：每帧刷新数字并触发文本重建；飘字不回收，战斗后期卡顿。

### 4.5 危险与不可逆操作

- 高危操作（撤退、拆除、放弃祭祀）需要二次确认或 1.5 秒撤销窗口。
- 受攻击警报要带方向（屏幕边缘箭头）+ 声音 + 短震动。
- 资源将满/人口卡住要提前 5–10 秒提示，而不是满了才报错。

为什么：误触的代价远大于慢。手机上尤其如此。
常见错误：把“撤退”做成普通按钮，紧挨着“攻击”；一次误触毁掉整局。

### 4.6 动效预算

同一时刻，屏幕上最多 2–3 个“主动画”。其余反馈用颜色/数字/音效解决。

为什么：动画是注意力货币。每个都在动，等于没有重点。
常见错误：面板呼吸、徽记发光、数字滚动、按钮浮动、背景雾气同时播放；玩家不知道看哪。

## 5. 字体与数字排版

### 5.1 中文 UI 字体的现实

- **标题**可以用宋体/衬线，传达“礼器/古籍”的气质。
- **正文/标签**用黑体/无衬线，保证小字号可读。
- **数字**用等宽/表格数字（tabular），避免跳动。

本项目的字体栈是系统字体：

```
serif: "Source Han Serif SC", "Noto Serif SC", "Songti SC", "STSong", "SimSun", serif
sans:  "PingFang SC", "Microsoft YaHei", "Noto Sans SC", "Hiragino Sans GB", sans-serif
num:   "Bahnschrift", "DIN Alternate", "Segoe UI", sans-serif
```

问题：Android 上通常没有 Source Han Serif / Songti / SimSun，最后会回退到系统默认字体。设计稿里的宋体气质，在真机上会变成另一种字。

为什么：字体是 UI 气质的一半，也是跨端一致性最容易漏掉的一环。
常见错误：只在 Mac/Windows 浏览器里验收；从不看 Android 真机截图。

**建议**：至少嵌入一个中文标题字体的子集（常用 3500 字 + 标点），正文用系统黑体；或者接受“标题也用黑体”，用字距和排版做古意，而不是靠字体。

### 5.2 字号阶梯与最小字号

现有稿的阶梯是 9/10/11/12/13/15/17/22/25px（1920 基准）。在桌面上成立，但在手机上：

```
手机横屏 CSS 视口约 800×360
1920 → 800 的缩放 = 0.417
10px → 4.2px
9px  → 3.8px
```

这不是“小”，是不可读。**手机端的字号应该按 dp/sp 设计，而不是按 1920 画布等比缩。**

经验值：

- 手机正文：≥ 14sp（Android）/ 15pt（iOS）
- 辅助信息：≥ 12sp
- 最小可读：≥ 11sp，且只用于非关键信息
- 数字：比同层级文字大 1–2sp

为什么：字号不是视觉参数，是物理尺寸。人眼在 30cm 距离能分辨的最小汉字大约 8–9pt，低于这个值只能靠猜。
常见错误：用“设计稿缩小后还能看清”来验收；缩放比例一换就崩。

### 5.3 数字的排版

- 所有资源、伤害、时间、人口使用 `font-variant-numeric: tabular-nums`。
- 大数字用缩写：`1.2k`、`12.4万`，并在 tooltip 给全值。
- 数字和单位之间留 2–4px，单位字号小 2–3px。
- 资源不足时，数字变朱砂，但**同时**给出差额。

为什么：RTS 的数字是决策依据，不是装饰。对齐和可比较性比字体漂亮重要。
常见错误：用比例字体显示资源，数字变化时整行左右跳动；用“很多位数”炫耀精确，玩家读不出量级。

### 5.4 文本长度与换行

- 按钮文字最多两行；超过就缩短或改图标。
- 中文标题字距可以到 0.1–0.2em，正文不要超过 0.05em。
- 不要把关键信息放在会被截断的位置（按钮、固定宽卡片）。

为什么：中文方块字在宽字距下显气质，但正文宽字距会降低阅读速度。
常见错误：所有文字都加 0.2em 字距，读起来像标语；按钮固定宽 96px，英文一长就溢出。

## 6. 图标语言与一致性

### 6.1 统一的是“规则”，不是“风格”

一套图标要统一四件事：

1. **网格**：24×24 viewBox，安全区 20×20，视觉重心居中。
2. **笔画**：1.5px 描边，圆头；或纯面性，不要混。
3. **透视**：全部正视，或全部 45° 俯视，不要混。
4. **光源**：统一从上方来，高光在同一侧。

为什么：图标不是插画，是一套符号系统。规则不统一，玩家会觉得“拼凑”。
常见错误：线性图标和面性图标混用；有的圆角、有的直角；有的正视、有的等距。

### 6.2 24px 可辨

任何图标在 24px 下必须能说出是什么。检验方法：

- 缩到 24px，给 5 个人看 3 秒，能说出 4/5 即合格。
- 细节不超过 6 条线；不写文字；不用渐变。
- 需要“镂空”时用 `fill-rule:evenodd`，不要用透明度挖空。

为什么：HUD 图标通常在 20–32px；细节在缩小后全部丢失。
常见错误：在图标里画建筑纹理、画云纹、画篆字；24px 下变成一团。

### 6.3 隐喻的选择

本项目的图标有两类来源：

- **通用符号**：谷（穗）、木（树干）、石（石块）、玉（玉璧）、人口（人形）。这些不需要学习。
- **文化符号**：鼎、玉琮、华表、图腾柱。这些有气质，但需要教学。

规则：**核心资源用通用符号，文化符号用于装饰/高级内容。** 玩家不应该先学一遍上古器物才能采矿。

为什么：图标的第一职责是“可识别”，第二才是“有文化”。
常见错误：把“谷”画成甲骨文，把“木”画成图腾柱；好看，但玩家要猜。

### 6.4 状态图标

资源不足、锁定、可建造、推荐、冷却，最好用**同一套角标语言**：

- 左下：资源不足（缺多少）
- 右上：推荐/新
- 中央：锁定/不可用
- 底部：进度/冷却

为什么：位置固定，玩家可以“扫角标”而不是读每个按钮。
常见错误：每个按钮用不同的方式表示不可用（有的灰、有的斜纹、有的红字），玩家要逐个判断。

## 7. 暗色界面的颜色与对比度

### 7.1 暗色不是“黑底白字”

暗色 UI 的层次靠**明度台阶**，不是靠描边：

```
背景（最深） → 面板 → 抬高面 → 悬停面 → 文字
```

本项目的 `ink-950/900/850/800/700/600` 就是这个思路，方向是对的。

为什么：纯黑背景 + 纯白文字会产生强烈光晕和视觉疲劳；多级暗面能让层级自然。
常见错误：所有面板都用 `#000` + 10% 白描边；看起来像线框图，不像实体。

### 7.2 对比度要用数值验收

按 WCAG 相对亮度计算（背景取面板主色 `#26271D`）：

| 颜色 | 用途 | 对比度 | 判断 |
| --- | --- | --- | --- |
| `#E7E1CE` 玉白 | 主文字 | 11.55:1 | 优秀 |
| `#CEC6AF` 玉白暗 | 正文 | 8.86:1 | 优秀 |
| `#ABA38D` 灰玉 | 次级正文 | 6.01:1 | 合格 |
| `#8F8874` 灰 | 标签 | 4.27:1 | 接近下限，仅限大字号 |
| `#6E6957` 暗灰 | 三级说明 | **2.75:1** | **不合格** |
| `#9E3B32` 朱砂 | 警示文字/底 | **2.25:1** | **不合格** |
| `#D0695A` 朱砂浅 | 深底文字 | 4.21:1 | 边缘，仅限大字 |
| `#7C9E8E` 玉青 | 友军/可用 | 5.13:1 | 合格 |
| `#C8A24A` 土黄 | 描边/强调 | 6.27:1 | 合格 |

阈值：

- 正文（<18pt）：≥ 4.5:1
- 大字（≥18pt 或 14pt 粗体）：≥ 3:1
- 非文本 UI（边框、图标）：≥ 3:1

为什么：暗色界面最容易“看起来有质感，实际上读不清”。对比度是唯一能客观验收的指标。
常见错误：用 `#6E6957` 写 9–10px 说明文字；用 `#9E3B32` 做小号警示；觉得“暗一点更高级”。

### 7.3 饱和度与面积

- 大面积用低饱和（玄黑、墨、土黄暗）。
- 小面积用高饱和（朱砂、玉青亮）。
- 金色不要铺满；它是“描边/点缀”，不是“背景”。

为什么：高饱和大面积会让眼睛疲劳，也会让真正的高亮失效。
常见错误：整个 HUD 都是金色渐变；朱砂红到处都是，危险提示失去意义。

### 7.4 颜色语义要“专款专用”

本项目现在有多个颜色同时承担多种含义：

| 颜色 | 现有含义 | 风险 |
| --- | --- | --- |
| 朱砂 | 敌方、资源不足、危险、印章装饰 | 玩家无法判断“红”是敌情还是缺钱 |
| 玉青 | 友军、玉资源、可建造、天气 | “青”既是我方又是资源还是可用 |
| 土黄 | 华夏主色、描边、德望、高亮 | 金色到处都是，高亮不突出 |

建议：

- **朱砂只保留“敌方/危险”**；资源不足改用琥珀色 + 图标 + 文字。
- **玉青保留“友军/可操作”**；玉资源用图标区分，不靠颜色。
- **土黄保留“结构/描边”**；德望用独立的玉璧形态区分，不靠颜色。

为什么：颜色是稀缺资源。一个颜色承担三种含义，等于没有含义。
常见错误：用同一个红色表示敌人、缺资源、按钮错误、品牌印章。

## 8. 本章验收表

做完一版界面，用下面 12 条自检。每条都必须能给出证据（截图、数值、测试记录），不能凭感觉。

- [ ] 每个元素都能归入“决策/确认/叙事”三层之一，强度递减。
- [ ] 高频高后果信息在主界面，低频低后果信息被折叠。
- [ ] 0.5 秒内能说出：我有多少资源、能造什么、选了什么。
- [ ] HUD 占屏比在预算内（桌面 ≤28%，手机 ≤22%）。
- [ ] 敌我区分有颜色 + 形状双通道。
- [ ] 50 个单位同屏时，能分清兵种、敌我、血量状态。
- [ ] 每个按钮都有默认/按下/禁用/不可用原因，触屏没有 hover 依赖。
- [ ] 数值变化有反馈，但同屏主动画不超过 3 个。
- [ ] 正文对比度 ≥4.5:1，非文本 ≥3:1；最小字号在真机可读。
- [ ] 数字使用等宽，资源变化不抖动。
- [ ] 图标在 24px 下可辨，风格规则统一。
- [ ] 颜色语义唯一，朱砂/玉青/土黄不串用。

## 常见错误总表

1. 把“信息齐全”当目标，结果每个信息都很小。
2. 三层信息一样重，界面看起来“满”，但找不到重点。
3. 用发光/描边代替层级，所有东西都在发光。
4. 敌我只靠红绿，色盲玩家直接失去信息。
5. 所有单位常驻血条和名字，战场变成文字雨。
6. 用 9–10px 灰字写关键说明，对比度 2.75:1。
7. 朱砂同时表示敌人、缺资源、危险、装饰。
8. 数字用比例字体，变化时整行抖动。
9. 所有动画 300ms，战斗中反馈拖沓。
10. 只在桌面浏览器验收，不看 Android 真机。
