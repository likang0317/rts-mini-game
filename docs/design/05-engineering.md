# 05 从设计稿到引擎：UI 工程规范

> 这一章解决“设计稿为什么一进引擎就变味”。核心不是某个 API，而是**损耗模型**：哪些东西能 1:1，哪些必然失真，哪些在手机上根本不该做。

## 为什么设计稿会“进引擎就变味”

设计工具是一个“无限算力 + 无限图层”的环境：模糊、混合、阴影、矢量、字体，想加就加。
引擎是一个“每帧 16.6ms + 有限填充率 + 有限纹理内存”的环境。两者之间有一道必然的损耗：

| 设计稿效果 | Web/DOM | Phaser Canvas | Unity UGUI | Godot Control | 结论 |
| --- | --- | --- | --- | --- | --- |
| 纯色/渐变 | 原生 | 贴图/Shader | 贴图/Shader | 贴图/Shader | 可用，但渐变建议烘焙 |
| 圆角 | CSS 原生 | 九宫格/遮罩 | 九宫格/遮罩 | 九宫格/遮罩 | 用九宫格，不用运行时遮罩 |
| 投影 | CSS 可用但贵 | 贴图 | 贴图/Shader | 贴图 | 烘焙进九宫格 |
| 高斯模糊 | `backdrop-filter` 贵 | 几乎不可用 | 后处理/贵 | 后处理/贵 | 手机不做实时模糊 |
| 混合模式 | CSS 可用但贵 | 有限 | 有限/Shader | 有限/Shader | 不要全屏叠加 |
| 矢量图标 | SVG 原生 | 运行时栅格化/预渲染 | SVG 导入/栅格化 | SVG 固定尺寸栅格化 | 预栅格化或字体图标 |
| 文字排版 | 浏览器最强 | 手工排版 | 中等 | 中等 | DOM 做 HUD 的优势 |
| 复杂动效 | CSS/JS | Tween/序列帧 | Animator/序列帧 | Tween/AnimationPlayer | 状态用 tween，装饰用序列帧 |

**一句话：设计稿里每一个“效果”，在引擎里都要问三个问题：多少钱、什么分辨率、怎么随状态变。**

常见错误：在设计稿里堆满效果，交付时才发现“这个模糊引擎做不了”“这个混合模式手机一开就掉帧”，然后程序用一张静态图糊过去，状态全丢。

## 1. 切图与图集

### 1.1 切图规范

命名建议：

```
ui_panel_command_01@2x.png
ui_btn_primary_default@2x.png
ui_btn_primary_pressed@2x.png
icon_res_grain_24.svg
icon_cmd_attack_24.svg
```

规则：

- 同一组件用同一前缀，状态用后缀：`_default / _pressed / _disabled / _selected`。
- 倍率写在文件名或目录：`@1x / @2x / @3x`。
- 透明边裁掉，但保留 1–2px 安全边，避免采样时切到内容。
- 记录 pivot（锚点）和九宫格边界。
- 不要用中文文件名，避免打包/路径问题。

### 1.2 图集

为什么：手机 GPU 的 draw call 主要按“纹理/材质切换”分组。100 个图标 100 张纹理 = 100 次切换；打进 1 张图集 = 1 次。

建议：

- 单张图集 ≤2048×2048（低端机兼容性最好）；高端可用 4096。
- 图集之间留 2–4px padding，边缘 extrude 2px，避免采样串色。
- 同一图集放“同时出现”的元素（HUD 图标、命令图标），不要把战场大图和 UI 小图混在一起。
- 压缩：Android 优先 ETC2/ASTC；无透明用 ETC1；iOS 用 ASTC/PVRTC。Web 用 WebP/PNG。
- 图集数量控制：UI 1–2 张，战场 2–4 张，特效单独。

内存估算：

```
2048 × 2048 × 4 字节 = 16 MiB（RGBA8888）
加 mipmap ≈ 21.3 MiB
4096 × 4096 × 4 字节 = 64 MiB
ETC2/ASTC 4bpp ≈ 2 MiB（2048²）
```

为什么：纹理内存是手机最容易爆的资源，尤其是低端机。
常见错误：每张图单独加载；图集做到 4096 导致低端机加载失败；透明像素不裁，图集里一半是空气。

### 1.3 切图清单

每个界面交付时附一张表：

| 资源名 | 尺寸 | 倍率 | 九宫格边界 | 状态 | 用途 |
| --- | --- | --- | --- | --- | --- |
| `ui_panel_main` | 96×96 | 2x | 24/24/24/24 | default | 主面板底 |
| `ui_btn_cmd` | 128×128 | 2x | 24/24/24/24 | default/pressed/disabled | 命令按钮 |
| `icon_res_grain` | 24×24 | SVG | — | currentColor | 谷 |

没有这张表，程序只能猜；猜错一次，返工一天。

## 2. 九宫格：面板拉伸的唯一正确做法

### 2.1 原理

把一张图切成 9 块：四角不拉伸，四边单向拉伸，中间双向拉伸。

```
┌───┬─────────┬───┐
│ 角 │  上边   │ 角 │
├───┼─────────┼───┤
│ 左 │  中间   │ 右 │
├───┼─────────┼───┤
│ 角 │  下边   │ 角 │
└───┴─────────┴───┘
```

适用：面板底、按钮底、输入框、提示条、卡片。
不适用：有复杂纹理/图案必须整体缩放的背景、角色头像、插画。

### 2.2 各引擎的写法

- **Unity**：Sprite 的 Border（左/右/上/下，单位像素），Image Type = Sliced；注意 Pixels Per Unit 与 Canvas Scaler。
- **Godot**：`NinePatchRect`，设置 `patch_margin_left/right/top/bottom`。
- **Cocos Creator**：`Sprite` 的 `type = SLICED`，设置 `insetLeft/Right/Top/Bottom`。
- **Phaser**：`this.add.nineslice(x, y, key, frame, width, height, left, right, top, bottom)`。

### 2.3 边界怎么定

- 边界必须落在“可以拉伸”的区域：纯色、细渐变、重复纹理。
- 不能切到角饰、文字、图标、阴影的锐利边缘。
- 2x 图上的边界是物理像素，换到 3x 要按比例重设。
- 边界至少 8–16px（1x），否则拉伸时会出现明显接缝。

为什么：九宫格是“用一张小图适配任意尺寸”的唯一稳定方案；用整图缩放，角饰会变形。
常见错误：把角饰切进拉伸区，按钮一拉长角就糊；边界太小，出现 1px 缝；不同倍率用同一组边界值。

## 3. 矢量还是位图

### 3.1 判断表

| 内容 | 推荐 | 理由 |
| --- | --- | --- |
| 图标（单色/双色） | SVG / 字体图标 | 清晰、可换色、文件小 |
| 图标（多色、渐变、发光） | 位图 | SVG 复杂后运行时栅格化贵 |
| 面板/按钮底 | 位图九宫格 | 纹理/阴影/噪点难以矢量化 |
| 地形/建筑/单位 | 位图/精灵 | 需要纹理和动画 |
| 文字 | 字体 | 不要用图片文字 |
| 小地图 | 运行时绘制 | 数据驱动，不能预渲染 |

### 3.2 运行时矢量的代价

- Web DOM：SVG 是原生矢量，清晰、可换色，成本低。
- Canvas/WebGL：SVG 不能直接画，通常要预栅格化成纹理；运行时解析 SVG 会增加 CPU 和内存。
- Unity/Godot/Cocos：SVG 导入一般是“按某个尺寸栅格化”，不是无限清晰；复杂路径还会增加导入时间。

为什么：很多团队以为“矢量=清晰”，但在游戏引擎里，矢量常常只是“导入时生成的一张位图”。
常见错误：把复杂插画做成 SVG 塞进图集；在 Canvas 里每帧绘制 SVG 路径；不同 DPI 下用同一张栅格化结果。

### 3.3 本项目的选择

- 图标：SVG（DOM 路线）或 24/48/72px PNG（Canvas 路线）。
- 面板：2x/3x 九宫格 PNG/WebP。
- 战场单位：32×32 或 48×48 像素/手绘，按缩放级别准备 1–2 档。
- 文字：字体，不用图片。

## 4. UI 分辨率适配方案对比

| 方案 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 固定设计分辨率 + 等比缩放 | 1920×1080，`min(w/1920,h/1080)` | 实现最快，构图稳定 | 手机上字太小/黑边 | 桌面、演示 |
| 锚点重排 | HUD 锚四边，战场自适应 | 充分利用屏幕 | 每个组件要写锚点 | 手机 RTS |
| 分区适配 | 战场全屏，HUD 固定物理尺寸 | 操作手感稳定 | HUD 可能遮挡 | 手机 RTS |
| 逻辑 dp + DPR | 以 dp 布局，按 DPR 渲染 | 字清楚、尺寸稳定 | 要处理 DPR/性能 | 推荐底层 |

### 4.1 本项目的推荐组合

```
逻辑坐标：dp（640×360 为最小横屏基准）
渲染：canvas 尺寸 = css 尺寸 × min(DPR, 2)
布局：HUD 锚定四边 + 安全区；战场吃满剩余空间
超宽屏：额外宽度给战场；联机时限制镜头边界
```

为什么：RTS 的战场要尽量大，HUD 要保持“手指能点、眼睛能读”的物理尺寸。两者不能用同一个缩放系数。

### 4.2 常见错误

- 用 `vw/vh` 写按钮尺寸：手机上 100vw 是 800px，按钮会巨大或 tiny。
- 只做 16:9：20:9 上 HUD 贴边、战场比例怪。
- 不处理安全区：挖孔挡住资源数字。
- 不给低端机降级：DPR 3 渲染 2400×1080，帧率崩。

## 5. 字体

### 5.1 嵌入还是系统

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| 系统字体 | 零体积、加载快 | 跨端不一致、Android 缺宋体 | 正文/备用 |
| 嵌入完整字体 | 一致 | 中文 10–20MB，包体大 | 不推荐 |
| 嵌入子集 | 体积可控（1–3MB） | 缺字要回退 | 推荐 |
| SDF 字体 | 任意缩放清晰 | 生成复杂、小字发虚 | 大标题/3D 文字 |

### 5.2 子集化

- 统计游戏内所有文案，取常用 3500 字 + 标点 + 数字 + 拉丁字母。
- 用 `fontmin` / `glyphhanger` / `pyftsubset` 生成 woff2（Web）或 ttf（引擎）。
- 保留一份完整字体用于编辑器/设计，不打包。
- 动态文本（玩家名、聊天）要有回退字体，或限制字符集。

为什么：中文字体是包体杀手。一个完整思源宋体可能十几 MB，子集后 1–3MB。
常见错误：直接打包完整字体；只做中文子集，英文/数字缺字；忘了标点。

### 5.3 动态文本

- 数字用 `BitmapText`（Phaser）或等宽字体，避免每帧重排。
- 文本频繁变化时，缓存字符串，只有变化才 `setText`。
- 富文本（颜色/图标混排）尽量少用；必要时拆成多个文本对象。
- 自动换行按实际渲染宽度算，不按字符数估。

为什么：文本重建是 UI 性能的隐形杀手，尤其是每帧变化的资源数字。
常见错误：每帧 `setText`；用 `Label` 自动换行处理长文；在 Update 里改布局。

## 6. 动效实现方式对比

| 方式 | 表现力 | 成本 | 可控性 | 适用 |
| --- | --- | --- | --- | --- |
| 引擎 Tween/动画 | 中 | 低 | 高（参数化） | 80% UI 反馈 |
| CSS transition/animation | 中 | 低 | 高 | DOM HUD |
| 序列帧 | 高 | 高（图集/内存） | 低（不可参数化） | 特效、角色 |
| 骨骼（Spine/DragonBones） | 高 | 中 | 中 | 角色、复杂 UI 角色 |
| Rive/Lottie | 中高 | 中（多一个运行时） | 高（状态机） | 交互状态、装饰 |
| 视频 | 高 | 高 | 无 | 过场，不用于 UI |

推荐分工：

- 按钮/面板/进度：引擎 tween 或 CSS。
- 数值变化：tween + 位图数字。
- 德望徽记呼吸：CSS/tween，3.2s，幅度 ≤20%。
- 祭祀完成/胜利：序列帧或 Lottie。
- 多状态图标：Rive（如果状态确实多）。

为什么：UI 动效的本质是“状态过渡”，不是“播放动画”。参数化实现才能跟逻辑同步。
常见错误：用序列帧做按钮 hover；用 AE 导出 60 帧做循环；动画时长和逻辑冷却不一致。

## 7. UI 性能：手机上的真实代价

### 7.1 帧预算

```
60fps = 16.6ms/帧
UI 建议 ≤ 3–4ms（中端机）
```

UI 超预算的常见原因：draw call、overdraw、文本重建、布局重建、遮罩、全屏后处理。

### 7.2 Draw Call

- 每次切换纹理/材质/混合模式，可能打断合批。
- 字体是独立纹理：不同字体/字号可能各自成批。
- 遮罩（Mask/Stencil）会打断合批，嵌套遮罩更贵。
- 目标：UI draw call ≤30，总 draw call ≤100（中端机，经验值）。

优化：

- 图标进同一图集；同一界面的面板进同一图集。
- 避免同屏多种字体/字号；用图集字体或 BitmapFont。
- 减少遮罩；圆角用九宫格，不用 Mask。
- 把频繁变化的元素和静态元素分到不同 Canvas/层（Unity 尤其）。

### 7.3 Overdraw

半透明叠加是手机 GPU 的主要负担：

```
1080p ≈ 207 万像素
3 层全屏半透明 × 60fps ≈ 3.7 亿像素/秒
```

这还不算模糊、噪点、阴影的额外采样。中端 GPU 的填充率有限，叠 3–4 层就可能掉帧。

高风险效果：

- 全屏 `backdrop-filter: blur()`：要读回背景再模糊，Android WebView 上很贵。
- 全屏 `mix-blend-mode`：强制合成/读回。
- 大面积 `box-shadow` / `filter: drop-shadow`：每帧重新采样。
- 半透明面板叠半透明面板：overdraw 翻倍。
- 全屏噪点/雾气：如果每帧动画，成本更高。

建议：

- 模糊/噪点/渐变**预烘焙**进九宫格贴图。
- 面板底不透明度 ≥0.9，减少透叠。
- 阴影用贴图，不用实时模糊。
- 全屏效果只在一个层里做，不要每个面板各做一次。
- 低端机提供“简洁模式”：关雾气、关噪点、关动态阴影。

### 7.4 文本与布局重建

- 每帧 `setText` 会触发文本纹理重建；资源数字只在变化时更新。
- 不要每帧改 `RectTransform`/布局组；布局重建会连锁。
- 滚动列表用对象池 + 复用；不要一次创建 100 个条目。
- 动画只改 `transform`/`opacity`，不改宽高和布局。

### 7.5 本项目的 DOM/CSS 专项

UI-A 这类稿子里有几个高风险效果，搬到手机上要特别小心：

| 效果 | 位置 | 风险 | 替代 |
| --- | --- | --- | --- |
| `backdrop-filter: blur()` | 状态条、胜利遮罩 | Android WebView 读回/模糊，掉帧 | 预烘焙半透明底图 |
| `mix-blend-mode: overlay` | 每个面板的噪点 | 强制合成层，overdraw 高 | 噪点烘进贴图 |
| `feTurbulence` 噪点 | 全屏 grain、面板 | 大面积合成 | 静态噪点贴图 |
| 大面积 `box-shadow` | 面板/控制台 | 每帧采样 | 九宫格阴影贴图 |
| `filter: drop-shadow` | 徽记/选中环 | 每帧滤镜 | 预渲染光晕贴图 |
| 多层半透明 | 面板 + 控制台 + 遮罩 | overdraw | 提高不透明度/合并层 |

为什么：这些效果在桌面浏览器上很便宜，在 Android WebView + 中低端 GPU 上完全是另一回事。
常见错误：用桌面 Chrome 的 Performance 面板验收手机；只看截图不看帧率。

### 7.6 测量方法

- Web/Capacitor：Chrome DevTools → Performance（CPU/帧）、Rendering（FPS meter、Paint flashing、Layer borders）。
- Android：`adb shell dumpsys gfxinfo`、GPU Inspector、设备开发者选项的“GPU 渲染模式分析”。
- Unity：Profiler、Frame Debugger、Rendering Statistics。
- Godot：Debugger → Monitors（draw calls、video memory）。
- 统一记录：设备型号、分辨率、DPR、场景、帧率、UI 耗时、draw call、纹理内存。

## 8. 本项目的落地：Phaser + DOM 混合

### 8.1 三种方案

| 方案 | 做法 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| A. 全 DOM HUD | Phaser 只渲染战场，HUD 用 HTML/CSS | 复用 `ui-a.html`，排版/字体/矢量强 | DOM 合成/触摸穿透/性能 | **推荐** |
| B. 全 Canvas HUD | 全部用 Phaser 对象 | 一套渲染、可控 | 排版/字体/本地化麻烦 | 单位少、HUD 简单时 |
| C. 混合 | 战场内 UI 用 Phaser，屏幕 HUD 用 DOM | 各取所长 | 两套坐标/事件 | **本项目最佳** |

### 8.2 分工

```
Phaser Canvas：
  - 地形、单位、建筑
  - 选中环、框选框、血条、飘字、攻击线
  - 建造 ghost、范围圈

DOM Overlay：
  - 资源条、德望、命令盘、建造菜单、祭祀面板
  - 战报、编队、设置、结算浮层
  - tooltip、确认框、错误提示

Canvas（小地图）：
  - 数据驱动绘制，不用 DOM 图片
```

为什么：战场内 UI 需要跟世界坐标/缩放同步，放 Canvas 最顺；屏幕 HUD 需要排版和文字，放 DOM 最顺。
常见错误：把所有东西都塞进 Phaser（排版痛苦）；或把所有东西都塞进 DOM（战场 UI 跟不住镜头）。

### 8.3 关键实现

**（1）DOM 层不挡战场**

```css
#hud { position: fixed; inset: 0; pointer-events: none; }
#hud .interactive { pointer-events: auto; }
canvas { touch-action: none; }
```

**（2）安全区**

```css
:root {
  --safe-top: env(safe-area-inset-top, 0px);
  --safe-right: env(safe-area-inset-right, 0px);
  --safe-bottom: env(safe-area-inset-bottom, 0px);
  --safe-left: env(safe-area-inset-left, 0px);
}
```

**（3）Phaser 缩放**

```ts
const config: Phaser.Types.Core.GameConfig = {
  type: Phaser.AUTO,
  scale: {
    mode: Phaser.Scale.RESIZE,
    autoCenter: Phaser.Scale.CENTER_BOTH,
    width: window.innerWidth,
    height: window.innerHeight
  },
  // ...
};
```

`RESIZE` 让画布跟随视口；HUD 的 DOM 用 `ResizeObserver` 重算。不要用 `FIT` 把 1920×1080 整体缩小——那会把字号一起缩没。

**（4）九宫格面板**

```ts
const panel = this.add.nineslice(0, 0, 'ui', 'panel', 480, 280, 24, 24, 24, 24)
  .setOrigin(0, 0)
  .setScrollFactor(0);
```

**（5）数字**

```ts
this.add.bitmapText(x, y, 'num', '320', 18).setScrollFactor(0);
```

数字变化时只更新变化的文本对象，不要每帧重建。

**（6）触摸穿透**

- Canvas 上的点击：Phaser input。
- DOM 按钮：浏览器事件。
- 两者交界：给 DOM 容器 `pointer-events:none`，只给可交互子元素 `auto`；避免在按钮上同时触发 Phaser 的选择。

### 8.4 性能守则

1. HUD 面板底不透明度 ≥0.9；少叠层。
2. 不在手机上用 `backdrop-filter`；用预烘焙。
3. 噪点/雾气/阴影全部烘焙进贴图。
4. 动画只改 `transform`/`opacity`。
5. 图集 1–2 张；UI draw call ≤30。
6. 字体子集 + 数字用 BitmapText。
7. 低端机降 DPR、关装饰层。
8. 每加一个效果，记录帧耗时变化。

## 9. 交付流程与验收

### 9.1 流程

```
设计 token → 组件/状态矩阵 → 切图/图集 → 引擎实现 → 真机验收 → 性能回归
```

每一步的产物：

| 步骤 | 产物 | 验收 |
| --- | --- | --- |
| token | JSON/CSS/TS | 程序不手抄色值 |
| 组件 | 状态矩阵 | 每个状态可实现 |
| 切图 | 图集 + 清单 | 无缺图/无重复 |
| 实现 | 可运行界面 | 与设计稿偏差可接受 |
| 真机 | 截图/录屏 | 3 种分辨率、2 种设备 |
| 性能 | 数据表 | 帧率/耗时/draw call 达标 |

### 9.2 还原度验收

- 布局偏差 ≤2px（1x）；色差 ΔE ≤3。
- 字号/行高/字距与 token 一致；不允许“差不多”。
- 九宫格拉伸后角饰不变形。
- 所有状态可触发；禁用态有原因。
- 本地化后不溢出。

### 9.3 性能验收

| 指标 | 目标（中端机） |
| --- | --- |
| 帧率 | 稳定 60fps（战斗 50 单位） |
| UI 帧耗时 | ≤4ms |
| UI draw call | ≤30 |
| 总 draw call | ≤100 |
| 纹理内存 | ≤64MB（UI + 战场） |
| 冷启动到可操作 | ≤5s |

数字是经验目标，不是绝对标准；关键是**有基线、有回归**。

## 10. 常见错误总表

1. 设计稿用实时模糊/混合模式，手机上掉帧。
2. 每个图标一张纹理，draw call 爆炸。
3. 图集 4096，低端机加载失败。
4. 九宫格边界切到角饰，拉伸变形。
5. 运行时解析 SVG，CPU 飙升。
6. 打包完整中文字体，包体 +20MB。
7. 每帧 `setText`，文本纹理不断重建。
8. 用 `FIT` 缩放 1920 画布，手机上字变成 3px。
9. DOM HUD 全屏拦截触摸，战场点不到。
10. 不做真机性能测试，只在桌面 Chrome 看。
