前言：这本书怎么用

约 2 千字 · 阅读约 5 分钟

这本书是什么

这是一本关于把一个 Phaser 3 的 RTS 骨架，做成能装在安卓手机上的游戏的书。

它从仓库里真实存在的 280 行 MainScene.ts 出发，讲到固定时间步长、触屏交互、寻路、经济、战斗、性能、打包、签名和发布。每一章都回答三个问题：为什么这么做、这个仓库现在哪里不对、你动手时会踩什么坑。

它不是引擎 API 手册，也不是"游戏开发 30 天速成"。API 细节请查官方文档，这里讲判断和方法。

这本书不是什么

  • 不是"从零教你写代码"。默认你会 TypeScript、用过 Vite、知道什么是 npm script。
  • 不是"完整商业项目复盘"。这是一个单人、小规模、以验证玩法为目标的项目。
  • 不是"引擎广告"。开篇会把三十多种引擎摊开讲，但最后只给一个结论，不给你一堆并列选项。

读者

  • 熟悉 Vue / 前端工程，没做过游戏。
  • 想自己做一个 2D RTS，最终交付物是 Android APK。
  • 已经有这个仓库的 Phaser 骨架，或者愿意照着搭一个。
  • 每天能投入 3-4 小时，能接受"先出丑包，再谈体验"。

这一章会把三十多种工具摊开，逐个说清它解决什么问题、代价是什么、什么人该用。但它不是清单，是一次筛选：读完你应该能划掉其中的绝大多数，并且知道自己为什么划掉。

先给结论

如果你只想要答案，这里是：

继续用 Phaser 3.90 + Capacitor 出 APK。 什么时候换：真机上 100 单位同屏、图集化、DPR 压到 2 之后持续低于 30fps，或者你的设计目标明确要求 200+ 单位同屏。换的时候换 Godot 4，不是 Unity，也不是 Cocos。

这个结论在第 00 章会展开成闸门和数字。本章负责让你相信它不是随口说的——把替代品都看一遍，才知道为什么不动。

怎么读这一章

每个引擎给七件事：定位、长处、短板、能不能出 APK、授权与成本、中文资料、什么时候选它。最后一条是判断，不是描述。

关于数字，统一约定：

  • 有来源的：标出查证日期和大致出处（纯文本，书里不放外链）。
  • 经验值：来自实践的量级，不是厂商承诺，你可以推翻。
  • 推测：我没验证过的判断。

包体、帧率这类数字，出厂即过时。看量级，不要记数字。

一、主流 3D / 综合引擎

这五个是"什么都能做"的一类。它们的共同点是：编辑器重、功能全、学习曲线陡，但一旦上手，从 2D 小游戏到 3D 大作都能覆盖。

Unity

  • 定位：通用商业引擎，2D/3D/XR/移动端全吃。独立游戏和中型商业项目的事实标准之一。
  • 长处：工具链最完整——编辑器、动画、粒子、UI、地形、Asset Store、Profiler、云构建都有。C# 生态成熟，第三方插件几乎覆盖所有需求。招人和找教程都最容易。
  • 短板：重。空白项目就带一堆用不到的模块；编辑器启动、进入 Play 模式、IL2CPP 构建都要等；版本升级容易踩 API 变更。2D RTS 用不到它 80% 的能力，你付的是"可能性"的钱。
  • 能出 APK 吗：能，官方 Android Build Support 模块，输出 APK 或 AAB。需要 Android SDK/NDK/JDK，环境配置本身是一道门槛。
  • 授权与成本：个人版免费，有营收/融资上限（Unity 6 时代个人版门槛为年收入 20 万美元量级，具体条款会变，以官网为准）。超过要买 Pro 订阅。2024 年闹过的 Runtime Fee 已取消，但授权条款是这家公司历史上变动最频繁的部分，长期项目要留意。
  • 中文资料：中文教程、视频、书籍最多，遇到问题几乎一定能搜到中文答案。社区体量最大。
  • 什么时候选它：你要做 3D、要上 Steam 或主机、要接商业 SDK（广告、支付、分析）、需要雇人接手，或者你已经有 C# 基础。做一个 2D RTS 上安卓，这些条件一条都不满足。

Unreal Engine

  • 定位：3D 高保真画面的行业标准。3A、影视虚拟制片、写实向手游。
  • 长处：渲染能力天花板，Nanite/Lumen 这类技术把"画面"这件事的门槛拉到了别人够不着的位置。蓝图可视化编程让策划也能改逻辑。商城资源质量高。
  • 短板：对 2D 极不友好——2D 要靠 Paper2D 或第三方方案，绕。C++ 编译慢，蓝图一多性能下降，移动端包体和内存压力大（经验值：空移动项目就是百 MB 量级）。学习成本是本章所有引擎里最高的。
  • 能出 APK 吗：能。要装 Android Studio、指定 NDK、配 JDK，打包链路比 Unity 更重。中小项目打包一次几分钟到十几分钟很常见。
  • 授权与成本：免费使用，产品总收入超过 100 万美元后按 5% 分成（条款会变，以官网为准）。听起来友好，但它的隐性成本是人力——UE 项目通常需要专门的 TA/渲染向人手。
  • 中文资料：不少，但偏 3D、偏美术、偏大厂管线。2D 小游戏方向的资料几乎没有。
  • 什么时候选它：画面本身就是卖点，团队里有 3D 美术，预算和时间都够。你做 2D RTS，选它等于用航天飞机送快递。

Godot 4

  • 定位：MIT 协议的开源通用引擎，2D 和 3D 都是一等公民。这几年独立开发者的首选替代品。
  • 长处：轻。编辑器几十 MB，启动快，导出的 2D 项目包体小。2D 渲染是真 2D（不是 3D 平面），像素对齐、Y 排序、Tilemap 都顺手。内置 AStarGrid2D 网格寻路、Navigation2D、Control 节点 UI、动画状态机。GDScript 语法接近 Python，写起来快；也支持 C#。
  • 短板：3D 仍在追赶（4.x 大幅改善，但和 UE 不在一个段位）。生态比 Unity 小，商业插件少。GDScript 是动态类型，大项目重构时不如 TypeScript 有安全感（可以用 C#，但 C# 的移动端导出链路比 GDScript 麻烦）。版本间有过破坏性变更，4.0 到 4.x 升级需要改代码。
  • 能出 APK 吗：能，而且是本章最省事的一档：装 export template，一键导出。调试空包 20MB 量级，release 更小，社区有 15MB 以下的成品案例（经验值范围，随版本和资源变化）。
  • 授权与成本：MIT，完全免费，无分成、无营收门槛、可商用、可改源码。这是它最硬的优势。
  • 中文资料：官方文档有完整中文翻译，质量高。中文社区比 Unity 小，但活跃，B 站教程够入门。
  • 什么时候选它：如果这个项目从零开始，我会直接让你用它。 现在不选，只因为你已经有一份能跑的 Phaser 骨架和一套设计资产，换引擎要两周起步，而换引擎不会自动解决"手机上怎么操作"这个真问题。

CryEngine

  • 定位：曾经的画面标杆（《孤岛危机》），现在是一个维护中的引擎，主要用户是 Crytek 自己和少数授权方。
  • 长处：渲染和植被/地形系统仍然强，沙盒编辑器（Sandbox）有历史积淀。
  • 短板：文档、教程、社区都在萎缩；工具链老旧，C++ 代码库庞大且风格偏旧；遇到问题基本只能自己读源码。招聘市场上会 CryEngine 的人极少。
  • 能出 APK 吗：技术上支持移动端，但公开的 Android 打包资料非常少，链路不顺。
  • 授权与成本：源码在 GitHub 上，但商业授权条款需要联系 Crytek，不像 Unity/Unreal 那样公开透明。商业使用前必须自己逐条读许可，不要信任何二手总结。
  • 中文资料：几乎没有。零散的中文文章多是十年前的。
  • 什么时候选它：几乎不存在"应该选它"的场景。除非你接手了一个 CryEngine 项目，或者你在做 Crytek 相关的外包。对你来说这是负资产，连了解都不必。

O3DE（原 Lumberyard）

  • 定位：亚马逊把 Lumberyard 捐给 Linux 基金会后形成的开源引擎，Apache 2.0。
  • 长处：开源、无授权费、组件化架构（Gem 系统）设计得比很多老引擎干净，自带一些云服务集成思路。
  • 短板：成熟度不够。 编辑器重、构建复杂（C++ 为主，编译一次很久）、文档和教程覆盖不全，社区规模小。它的定位更偏"给团队二次开发"，不是"给个人做游戏"。
  • 能出 APK 吗：有 Android 平台支持，但工具链和文档的完善度远不如 Unity/Godot，踩坑成本高。
  • 授权与成本：Apache 2.0，免费。但"免费"省下的钱会被学习成本吃掉。
  • 中文资料：极少。
  • 什么时候选它：你的公司需要一个可深度定制的开源 3D 引擎，且有 C++ 团队。个人开发者不要碰。

这一类的判断

  • 做 3D、要生态、要招人 → Unity。
  • 做 3D 且画面是卖点、有美术团队 → Unreal。
  • 做 2D、要轻、要免费、一个人干 → Godot 4。
  • CryEngine、O3DE → 不在选项里。它们不是"差一点的选择"，是"另一个世界的问题"。

二、2D 专门引擎

这一类只做 2D。它们用"放弃 3D"换来了更短的启动时间、更简单的概念模型、更小的包体。对 2D 项目，这通常是划算的。

GameMaker

  • 定位：最老牌的 2D 商业引擎之一，GML 语言，Room/Object/Sprite 三件套的心智模型极简。大量独立 2D 名作出自它。
  • 长处：2D 工作流顺到极致——画精灵、拖进房间、写几行事件代码就能跑。内置序列帧、碰撞、粒子、瓦片地图。GML 上手一两天够用。导出 Android 是一键。
  • 短板：语言生态封闭（GML 只在这个引擎里有用，学到的东西带不走）。3D 基本没有。复杂系统的代码组织能力弱于通用语言——上千行逻辑后，重构和测试会难受（GML 有单元测试方案，但不是主流用法）。订阅制，长期成本要算。
  • 能出 APK 吗：能，官方移动端导出。
  • 授权与成本：有免费版（限制导出平台和功能），专业版一次性买断，移动端导出需要对应授权档位。具体价格和档位近年调整过，以官网为准。
  • 中文资料：中等。入门教程有，深水区资料少，遇到怪问题多半要英文搜索。
  • 什么时候选它：你做的是小而完整的 2D 游戏——平台跳跃、弹幕、塔防、轻量 Roguelike——且你不想被工程化绑架。RTS 不在它的舒适区：框选、编队、寻路、多单位调度，这些在 GameMaker 里都要自己搭，而它的语言对"搭系统"并不友好。

Godot 2D

严格说它不是独立产品，是 Godot 4 的 2D 管线。单独列出来，是因为很多人搜"Godot 2D 引擎"时以为它是另一个东西。

  • 定位：Godot 4 内的真 2D 渲染路径，Node2D、TileMapLayer、CanvasItem、Area2D 构成整套 2D 世界。
  • 长处：像素对齐、Y 排序、2D 光照/遮挡、Tilemap 自动图块、AStarGrid2D 网格寻路。启动快，包体小，导出 Android 顺。做 2D RTS，这是本章综合分最高的一个。
  • 短板：和 Godot 4 共享短板——生态比 Unity 小，GDScript 动态类型，中文深度资料有限。2D 物理（Godot Physics 2D）在大量单位密集碰撞时不如自己写空间划分来得快。
  • 能出 APK 吗：能，和 Godot 4 同一条链路。
  • 授权与成本：MIT，免费。
  • 中文资料：官方文档中文完整。
  • 什么时候选它：你的下一个 2D 项目，或者本项目触发了换引擎闸门时。 这是唯一一个我会主动推荐给"个人做 2D RTS"的引擎。

Defold

  • 定位：King 开源、现由 Defold 基金会维护的 2D 引擎，Lua 脚本，主打"小包体 + 全平台"。
  • 长处：包体极小（空项目几 MB 量级），启动快，内存占用低，对低端安卓友好。编辑器轻，消息传递式架构清晰。HTML5 和原生导出都支持。
  • 短板：生态小，插件和教程都不多。Lua 生态不如 JS/TS 丰富。编辑器功能相对朴素，复杂 UI 要自己搭。中文资料很少。
  • 能出 APK 吗：能，官方支持。
  • 授权与成本：免费，开源（类 Apache 风格，具体条款以仓库为准），无分成。
  • 中文资料：少。基本靠英文文档。
  • 什么时候选它：极低端设备、极小包体是硬指标，或者你做的是轻量 2D 休闲游戏。RTS 的多单位调度在 Defold 里能写，但没有现成红利。

Construct 3

  • 定位：浏览器里的可视化 2D 游戏工具，事件表（Event Sheet）驱动，几乎不写代码。
  • 长处：上手最快的一档——不写代码也能做出完整 2D 游戏。自带大量行为（Platform、Bullet、Pathfinding、Tilemap），做平台跳跃和俯视角射击极快。编辑器在浏览器里，跨设备。
  • 短板：事件表在系统复杂度上升后会失控。 RTS 的单位管理、状态机、寻路调度不适合用事件表拼。订阅制，断订就不能编辑。导出原生包依赖 Cordova 封装，调试链路比原生引擎绕。
  • 能出 APK 吗：能，官方 Android 导出（基于 Cordova）。
  • 授权与成本：订阅制，按年/按月，个人版价格不高但长期是持续支出。
  • 中文资料：中等偏少，社区以英文为主。
  • 什么时候选它：非程序员想做完整 2D 小游戏，或者做原型验证玩法。你是前端工程师，写代码比拖事件表快，它对你的价值有限。

GDevelop

  • 定位：开源、免费的可视化 2D 引擎，思路接近 Construct，但开源、可扩展。
  • 长处：免费，无订阅门槛；事件系统比 Construct 更开放；支持自定义扩展（JS）；一键导出 Web/Android/Windows；社区活跃，模板多。
  • 短板：和 Construct 一样，复杂系统会被可视化逻辑拖累。原生导出底层也是 Cordova，性能和调试不如原生引擎。3D 很弱。
  • 能出 APK 吗：能，官方 Android 导出。
  • 授权与成本：开源免费，商业使用无分成。
  • 中文资料：少。
  • 什么时候选它：预算为零、不写代码、做小体量 2D。不适用于 RTS。

Solar2D

  • 定位：Corona SDK 的开源延续，Lua，2D 移动游戏老牌方案。
  • 长处：Lua 轻快，2D 渲染和物理（Box2D）成熟，热重载体验好，社区虽小但肯回答问题。包体小。
  • 短板：项目活跃度不如从前，生态萎缩；编辑器能力弱（很多人用 VS Code + 命令行）；中文资料稀少。
  • 能出 APK 吗：能，Android 是其主打平台之一。
  • 授权与成本：免费开源。
  • 中文资料：很少。
  • 什么时候选它：你熟悉 Lua、做轻量 2D 手游、不想要重编辑器。不是 RTS 的优选。

Stencyl

  • 定位：可视化 2D 游戏制作工具，积木式逻辑（类似 Scratch），面向教育和轻量独立开发。
  • 长处：零代码门槛，内置平台跳跃模板，导出多平台，适合教学和非程序员。
  • 短板：更新节奏慢，生态小，复杂逻辑表达困难，性能上限低。付费档位才能导出移动端。
  • 能出 APK 吗：能（付费档）。
  • 授权与成本：免费版可试用，发布/移动端需付费。
  • 中文资料：很少。
  • 什么时候选它：教学、原型、非程序员的小游戏。做 RTS 不合适。

RPG Maker

  • 定位：日式 RPG 专用工具，不是通用引擎。地图、事件、数据库、战斗系统都是为 JRPG 预设好的。
  • 长处：做 JRPG 极快——对话框、队伍、道具、技能、敌人配置全是现成的，插件生态（尤其 MV/MZ 的 JS 插件）庞大。
  • 短板：它的预设就是它的边界。 你想要的实时多单位 RTS，和它的回合制/事件驱动模型是两种东西，改造成本高于从零写。
  • 能出 APK 吗：官方主线面向 Windows；移动端要靠社区方案或导出 Web 后封装，链路不顺。
  • 授权与成本：商业软件，按版本买断；用它的素材有额外限制（不同版本条款不同）。
  • 中文资料：多，但集中在"做 RPG"。
  • 什么时候选它：你要做的是 JRPG。其它类型都不要考虑。

AppGameKit

  • 定位：TheGameCreators 出品的 2D/轻 3D 引擎，AGK BASIC 脚本，也有 C++ 层。
  • 长处：语法简单，跨平台导出（Android/iOS/Windows/Mac/Linux），一次性买断，老牌稳定。
  • 短板：社区小，英文资料为主，编辑器与调试体验偏旧，现代工具链（热重载、包管理）缺失。
  • 能出 APK 吗：能。
  • 授权与成本：一次性买断，无分成。
  • 中文资料：几乎没有。
  • 什么时候选它：你在维护老项目，或偏爱 BASIC 式简单语法。新项目没有理由选它。

这一类的判断

  • 小体量 2D、要快、不想工程化 → GameMaker（付费）或 GDevelop（免费）。
  • 认真做 2D、要长期维护、要免费 → Godot 4 的 2D 管线。
  • 极低端设备、包体是硬指标 → Defold。
  • 不写代码、做原型 → Construct 3。
  • RPG Maker / Stencyl / AppGameKit / Solar2D → 除非你的需求正好落在它们的预设里，否则跳过。

对 RTS 来说，这一整类里只有 Godot 2D 是真正的候选。

三、代码型 / 框架型

这一类不是"编辑器里拖出来的游戏"，是"用代码写出来的游戏"。你已经在用其中之一（Phaser）。它们的共同点：没有场景编辑器（或很弱）、没有现成玩法、自由度高、上限取决于你。

Phaser

  • 定位：Web 2D 游戏框架，JS/TS，基于 Canvas/WebGL，场景 + 游戏对象 + 输入 + 物理 + 音频一整套。
  • 长处：API 直白，文档和示例极多，社区大。TypeScript 支持好。同一套代码跑浏览器，套 Capacitor 就出 APK。本项目正在用它，MainScene.ts 280 行就能跑起选择、移动、缩放。
  • 短板：它的"引擎"只到框架层——没有编辑器、没有内置寻路、没有 RTS 手势、UI 要自己搭。性能受 WebView 限制，填充率和绘制调用是天花板（第 12 章）。包体虽然小（本项目 dist JS 约 1.5MB），但 WebView 壳带来额外开销。
  • 能出 APK 吗：能，通过 Capacitor/Cordova 封装，这是本书主线（第 13 章）。
  • 授权与成本：MIT，免费。锁 3.90 稳定版；Phaser 4 已在 RC 阶段，但本书不建议现在升。
  • 中文资料：中等。入门教程有，深水区靠英文文档和源码。
  • 什么时候选它：你已经有 Web 技术栈、要快速验证玩法、能接受 WebView 的性能上限。 这就是本项目的处境。

PixiJS

  • 定位：Web 2D 渲染器，不是游戏引擎。它只负责"把精灵高效画到屏幕上"。
  • 长处：渲染性能是 Web 2D 里最好的一档，批处理强，API 干净，生态插件多（滤镜、粒子、骨骼）。体积小。
  • 短板：没有游戏循环之外的任何东西——没有场景管理、没有物理、没有输入系统、没有音频。你要自己搭一套框架，等于先写半个引擎。
  • 能出 APK 吗：能，Capacitor 封装。
  • 授权与成本：MIT，免费。
  • 中文资料：少。
  • 什么时候选它：你已经有一套自己的架构，只需要一个高性能渲染层；或者你在做数据可视化/交互展示而非游戏。RTS 从零起步不要选它，你会把时间花在造轮子上。

Three.js

  • 定位：Web 3D 渲染库，事实标准。不是引擎。
  • 长处：3D 场景、材质、光照、后处理、加载器齐全，示例极多，社区巨大。
  • 短板：同样只有渲染。物理、碰撞、动画状态机、音频、资源管理都要自己接（通常配 Rapier/Cannon、Howl 等）。移动端 WebGL 性能有限，包体比 2D 方案大。
  • 能出 APK 吗：能，Capacitor 封装，但 3D 在 WebView 里的性能要实测。
  • 授权与成本：MIT，免费。
  • 中文资料：多。
  • 什么时候选它：做 3D 展示、3D 小游戏、或需要和现有 Web 页面融合的 3D 内容。2D RTS 不需要它。

Babylon.js

  • 定位：完整的 Web 3D 引擎（比 Three.js 更"引擎"），微软系，Apache 2.0。
  • 长处：内置物理、粒子、材质、GUI、动画、导航等模块，编辑器（Babylon.js Editor）和 Playground 在线调试好用，文档质量高。
  • 短板：体积比 Three.js 大，移动端性能仍受 WebGL 限制；中文资料比 Three.js 少。
  • 能出 APK 吗：能，WebView 封装。
  • 授权与成本：Apache 2.0，免费。
  • 中文资料：中等偏少。
  • 什么时候选它：你要在 Web 上做 3D 且希望"少拼装、多内置"。和 2D RTS 无关。

PlayCanvas

  • 定位：浏览器里的 3D 引擎 + 在线编辑器，主打 Web 3D 和轻量游戏。
  • 长处：编辑器在云端，协作方便；引擎开源（MIT），运行时轻；WebGL 优化做得早。
  • 短板：生态比 Three/Babylon 小；在线编辑器意味着依赖网络和平台；原生打包要靠封装。
  • 能出 APK 吗：能，WebView 封装。
  • 授权与成本：引擎开源免费，编辑器有免费额度与付费档。
  • 中文资料：少。
  • 什么时候选它：Web 3D 产品、需要团队在线协作编辑场景。不是本项目的选项。

Bevy

  • 定位：Rust 写的 ECS 游戏引擎，数据驱动、并行、现代。
  • 长处：性能好，架构干净（System/Component/Query），Rust 的类型系统让大项目重构有保障，编译产物是原生二进制，没有 WebView 开销。
  • 短板：API 变动频繁，版本之间经常要改代码；生态还在长，编辑器几乎没有，UI 方案不成熟；Rust 学习曲线陡；Android 打包链路（cargo + NDK）对新手不友好。
  • 能出 APK 吗：能，官方有移动端支持，但要自己配 NDK 和构建脚本。
  • 授权与成本：MIT/Apache 双协议，免费。
  • 中文资料：少，且容易过时（版本变得快）。
  • 什么时候选它：你会 Rust、追求原生性能、能接受频繁破坏性变更、项目周期不长。对一个前端背景、要先验证玩法的人，这是给自己加难度。

LÖVE

  • 定位：Lua 的 2D 框架，极简，love.draw / love.update 两个回调就能开始。
  • 长处：极轻、极简、上手快，Lua 写起来舒服，社区有大量小游戏范例。包体小。
  • 短板：只有基础——图形、音频、输入、文件。没有 UI、没有寻路、没有场景管理、没有物理（要配 Box2D 库）。生态小。
  • 能出 APK 吗：能，通过 love-android 社区方案，链路比 Capacitor 生疏。
  • 授权与成本：zlib，免费。
  • 中文资料：少。
  • 什么时候选它：做小而美的 2D 游戏、你享受"从零搭"。RTS 的工程量会让"极简"变成"什么都得自己写"。

MonoGame

  • 定位：XNA 的开源继承者，C#，2D/3D 底层框架。
  • 长处：C# 生态，性能接近原生（不走 WebView），控制力强，跨平台（Windows/Linux/macOS/Android/iOS/Switch/Xbox）。很多商业 2D 游戏用它。
  • 短板：底层——没有编辑器、没有 UI 系统、没有场景管理，内容管线（Content Pipeline）配置麻烦。Android 打包要装 .NET Android 工作负载，环境成本不低。
  • 能出 APK 吗：能，通过 .NET for Android。
  • 授权与成本：MS-PL，免费。
  • 中文资料：少。
  • 什么时候选它：你会 C#、想要原生性能、愿意自己搭框架。和 Bevy 类似，是把"验证玩法"推迟成"搭引擎"。

libGDX

  • 定位：Java/Kotlin 的跨平台游戏框架，Android 是它的主场。
  • 长处：原生 Android 性能，一套代码跑桌面/Android/iOS/Web；生态成熟（Box2D、Scene2D UI、Ashley ECS）；Java 工具链稳定，调试方便；包体可控。
  • 短板：Java 样板代码多；UI（Scene2D）风格老旧；没有编辑器；Kotlin 生态比 Java 好但仍需自己搭架构。
  • 能出 APK 吗：能，而且是它的强项——Android 就是第一目标平台。
  • 授权与成本：Apache 2.0，免费。
  • 中文资料：中等，Android 游戏方向有积累，但近年新资料少。
  • 什么时候选它：你会 Java/Kotlin、目标就是 Android、要原生性能、能接受自己搭框架。这是"不走 WebView"路线里最务实的一个。

Raylib

  • 定位：C 写的极简游戏编程库，绑定几十种语言（含 TS/JS 的 raylib 绑定，但主流是 C/C++）。
  • 长处：API 极简、编译快、依赖少，学习游戏编程本身的好工具。自带基础 2D/3D、音频、输入。
  • 短板：只有库，没有引擎；UI、寻路、场景管理全靠自己；C 语言的内存管理对小项目也是负担；Android 打包要自己配 NDK。
  • 能出 APK 吗：能，官方有 Android 构建脚本，但要手动配置。
  • 授权与成本：zlib，免费。
  • 中文资料：少。
  • 什么时候选它：学图形编程、做小工具、做原型。不是 RTS 的工程选择。

这一类的判断

  • 前端背景、要快、能接受 WebView → Phaser（你在这里）。
  • 只要渲染层、自带架构 → PixiJS。
  • 3D Web → Three.js（轻）或 Babylon.js（全）。
  • 会 C#/Rust/Java、要原生性能、愿意搭框架 → MonoGame / Bevy / libGDX。
  • 学原理、做小东西 → LÖVE / Raylib。

关键判断：框架型的自由是用"什么都得自己写"换来的。 对一个人做 RTS，这个交换只在"你已经有一套成熟架构"时才划算。你现在没有。

四、国产引擎与小游戏

这一类的共同背景是：国内市场、小游戏平台、中文文档。它们在"国内发行"这件事上有真实优势，但这个优势只在你真的要走那条路时才兑现。

Cocos Creator

  • 定位：国内最主流的商业 2D/3D 引擎，TypeScript，编辑器驱动，原生 + 小游戏双线。
  • 长处：中文文档和社区最好；编辑器里搭 UI 效率高；原生打包（C++ 底层）成熟；一键发微信/抖音小游戏；国内 SDK 接入资料多。
  • 短板：编辑器驱动——场景、节点树、预制体、动画都在编辑器里，代码是挂在节点上的脚本。你现在"代码生成一切"的思路要整个换掉。版本升级（2.x → 3.x）有过较大破坏性变更。RTS 需要的网格寻路没有内置，要自己写。包体不小（hello world 三 ABI 30MB、单 ABI 8MB，官方论坛实测）。
  • 能出 APK 吗：能，原生构建输出 APK/AAB。
  • 授权与成本：引擎免费，无分成（以官网条款为准）。
  • 中文资料：最好的一档。
  • 什么时候选它：你要上国内小游戏平台，或者团队里有策划/美术需要编辑器协作，或者你要接国内渠道 SDK。做纯安卓 APK 的 2D RTS，它的优势用不上，编辑器模型反而是负担。

LayaAir

  • 定位：国产 2D/3D 引擎，TypeScript，主打 H5 与小游戏，性能口碑不错。
  • 长处：H5/小游戏方向优化好，包体控制不错，API 偏底层、可控；中文文档完整；有 LayaNative 做原生封装。
  • 短板：社区规模比 Cocos 小；工具链和编辑器体验不如 Cocos；原生 Android 方案（LayaNative）的普及度和资料都少。
  • 能出 APK 吗：能，通过 LayaNative 封装。
  • 授权与成本：免费（以官网为准）。
  • 中文资料：中文为主，量中等。
  • 什么时候选它：做 H5/小游戏、在意包体和首屏。不是原生 APK 项目的首选。

Egret

  • 定位：早期国产 H5 游戏引擎，TypeScript，曾经的白鹭引擎。
  • 长处：H5 时代积累了大量教程和案例；API 对 Flash 开发者友好；工具链（Egret Wing）曾很完整。
  • 短板：维护活跃度明显下降，新项目生态萎缩，社区热度不如 Cocos/Laya。原生方案（Egret Native）资料少。
  • 能出 APK 吗：有原生方案，但链路和资料都偏旧。
  • 授权与成本：开源免费。
  • 中文资料：有历史存量，但新内容少。
  • 什么时候选它：维护老项目。新项目不要选。

微信小游戏方案

这不是一个引擎，是一个平台。你需要先选引擎，再走它的"小游戏适配"。

  • 平台特点：不用装 APK，点开即玩，靠微信分发；包体有严格限制（主包 + 分包，首包通常要求很小，具体上限以微信官方文档为准）；能力受限于小游戏 runtime（没有完整 DOM、音频/文件 API 是定制的）。
  • 常见路线：
    • Cocos Creator → 官方一键发布，最顺。
    • LayaAir / Egret → 官方适配，历史项目多。
    • Unity → 通过官方的 Unity WebGL 小游戏适配方案转换，包体和性能要仔细压。
    • Phaser / 其它 Web 框架 → 通过社区适配层（canvas/WebGL 兼容层）跑，能跑但坑多，官方支持弱。
  • 长处：获客成本低，传播快，不用处理安装包签名和渠道。
  • 短板：它不是 APK。 性能上限比原生低，包体限制严，平台规则会变，变现和审核受平台约束。对 RTS 这种要长时间操作、单位多的类型，小游戏的操作空间和性能都不宽裕。
  • 什么时候选它：你的目标是"让人点开就玩、快速传播"，而不是"装一个安卓应用"。这和本书的目标（APK）是两条路，不要混着做。

这一类的判断

  • 要国内小游戏发行 → Cocos Creator（首选）或 LayaAir。
  • 要纯安卓 APK → 这一类的优势不存在，不要因为"中文文档好"就选它。中文文档好省的是查资料的时间，编辑器模型改的是你的工作方式，后者贵得多。
  • Egret → 只用于维护老项目。

五、游戏 UI 中间件

这三个不是引擎，是"把 UI 从引擎里拿出来单独做"的方案。列出来是因为你在搜引擎时会撞见它们，容易误以为"做游戏 UI 必须用这个"。

NoesisGUI

  • 定位：把 WPF/XAML 那套 UI 技术搬进游戏引擎（Unity、Unreal、C++ 原生都有集成）。
  • 解决什么问题：游戏引擎自带的 UI 系统通常很弱——没有数据绑定、没有样式、没有 MVVM、复杂列表和动画写起来痛苦。NoesisGUI 让你用 XAML 声明式地写 UI，逻辑和表现分离，美术和前端可以并行。
  • 短板：商业授权收费；学习 XAML；对小项目是过度设计。
  • 为什么你基本用不到：你的 HUD 是几个按钮、一条血条、一个资源数字。用 Phaser 的 Text/Rectangle 或 DOM 覆盖层就够了。引入中间件等于为了三个按钮装一套框架。

Coherent GT

  • 定位：用 HTML/CSS/JS 写游戏内 UI 的商业中间件，AAA 项目常用（尤其欧美大厂）。
  • 解决什么问题：让 Web 前端技能直接做游戏 UI，且渲染质量、动画能力、开发效率都高于引擎自带 UI；支持复杂布局、动效、数据绑定。
  • 短板：商业授权，价格对个人不友好；集成成本高；需要专门的前端/UI 工程角色。
  • 为什么你基本用不到：你本来就在 Web 技术栈里。Phaser 之上直接叠一层 DOM/HTML 就是"穷人版 Coherent GT"，而且零成本。你不需要买它，你已经在用它解决的问题。

Scaleform

  • 定位：基于 Flash（SWF）的游戏 UI 中间件，Autodesk 出品，曾经是 AAA UI 的标准方案。
  • 解决什么问题：Flash 时代，用 Flash 做 UI 再嵌进游戏，美术和交互都能复用 Web 工作流。
  • 短板：Flash 已经死了，Scaleform 也早已停止维护和销售。 新项目不可能选它。
  • 为什么你基本用不到：技术底座已死。看到"Scaleform"字样，基本可以判断那篇资料是十年前的。

这一类的判断

游戏 UI 中间件解决的是"大团队、复杂 UI、美术与程序分工"的问题。一个人做小项目，引擎自带 UI + 一点 HTML 就够了。 你唯一需要记住的是：UI 的复杂度应该跟项目规模匹配，不要提前引入中间件。

针对"独立开发者做 2D RTS 上安卓"

推荐结论

Phaser 3.90 + Capacitor，继续。

理由不是"Phaser 最好"，是对你当前处境，它的风险最低：

  1. 你已经有能跑的骨架（280 行 MainScene.ts），复用率 100%。
  2. 你要验证的核心风险是"手机上能不能玩 RTS"，这和引擎无关——换任何引擎都要重做触屏交互（第 04 章）。
  3. 出包链路已经打通（第 13 章），一两天能看到手机上的单位。
  4. 包体 6-9MB 量级，对独立游戏是优势。

代价也写清楚：WebView 的填充率上限、没有内置寻路、没有 RTS 手势库、UI 要自己搭。这些在第 03、04、06、12 章都有对应的做法。

为什么不是那些看起来更"专业"的选择

  • Unreal：它的专业性是给 3D 大作的。2D RTS 用它，等于用渲染管线换掉了你的开发时间。
  • Unity：工具链最全，但你用不到；C# + 编辑器 + IL2CPP 构建，三重成本。
  • Cocos：中文文档最好，但"都会 TypeScript"不等于迁移便宜，编辑器模型会改掉你的工作方式。
  • Bevy / MonoGame / libGDX：原生性能是真的，但"没有编辑器、没有 UI、没有寻路"也是真的。你现在缺的不是性能，是玩法验证。

继续用仓库现有的 Phaser 3.90 + TypeScript + Vite，用 Capacitor 打成 Android APK。

这不是"各有利弊"

为什么不是 Godot（现在）

Godot 4 是这四条里最适合"个人做 2D"的：轻、快、2D 原生、内置网格寻路、导出 APK 只要装 export template。如果这个项目从零开始，我会直接让你用 Godot。

不选它的理由只有一个，但很硬：你现在有一份能跑的骨架、一套设计文档、一套 UI 高保真稿，换 Godot 意味着这些代码映射全部作废，UI 还要在 Control 节点里重搭一遍。 而你要验证的"手机操作链"换引擎并不会自动解决。

投入产出比：两周起步，换来的是你目前还用不到的性能余量。

为什么不是 Unity

Unity 做 2D RTS 完全没问题，工具链最全。但它对你是三重负担：C#、编辑器工作流、构建时间（IL2CPP 一次 5-15 分钟，经验值）。

你现在要的是"手机上装个包，验证 10 分钟一局好不好玩"。用 Unity 是拿卡车送外卖。等你确定要做 3D 表现、上 Steam、或者需要成熟的商业插件生态，再考虑它。

为什么不是 Cocos

Cocos Creator 用 TypeScript，中文文档最厚，原生打包成熟，看起来技能迁移最顺。两个坑：

  • 它是编辑器驱动的。 场景、节点树、预制体、动画都在编辑器里搭，代码只是挂在上面的脚本。你现在"代码生成一切"的思路要整个换掉。
  • 它的强项是国内小游戏发行，不是 RTS。你不上架、不做小游戏，这部分优势用不上。

顺带一个反直觉的点："都会 TypeScript"不等于迁移成本低。 编程模型（节点树 vs 场景类、生命周期、资源加载）完全不同，语言相同只省了语法学习。

选 Phaser 的真实代价

不是"WebView 慢"这种空话，是四件一定会遇到的事。

1. 填充率（fill rate）先崩，不是逻辑先崩

手机 DPR 普遍 2.75-3。1920×1080 的 Canvas 按 DPR 3 渲染，等于 5760×3240 的像素量，中端机 GPU 直接跪。第一优先级永远是把 DPR 压到 2 甚至 1.5（第 13 章给代码）。

2. 绘制调用与纹理切换

Phaser 对同纹理的 Sprite 会自动批处理。你现在用 this.add.rectangle（MainScene.ts:100-102），它们共享 Phaser 内置白纹理，能批处理，这点比 Graphics 好——drawMap() 里的 Graphics（MainScene.ts:68）是独立绘制，但它只画一次，静态开销可以接受。

真正的问题是以后换成每单位一张图：纹理一换，批次就断。所有单位最终必须进同一张图集（第 12 章）。

3. 后台节流

Android WebView 切到后台后 requestAnimationFrame 会停。你的采集、建造、祭祀读条如果按真实时间算，切出去 5 分钟回来会全部错乱。对策：用逻辑帧计数（第 02 章），并在 visibilitychange 时暂停仿真，不要补帧。

4. 音频延迟

移动端 WebView 要求首次用户交互后才能播音频，部分机型有 100-300ms 延迟（经验值）。RTS 的点击音、攻击音延迟明显会显得"发虚"。对策：第一屏放「点击开始」，同时解锁 AudioContext。

一条纪律：把"能换引擎"当保险

src/game/ 里不许出现任何 Phaser 的运行时引用（类型可以用 import type）。

做到这条，将来迁 Godot 时，仿真核心可以按 1:1 重写成 GDScript，只重写渲染和输入。这条纪律在第 03 章展开，在这里它是你选 Phaser 的风险对冲。

如果触发了，迁 Godot 4：它的 AStarGrid2D、Control UI、原生 2D 渲染正好对上你的需求；社区规模不如 Unity，但对单人 2D 项目够用。Unity 只有在你要做 3D 或重度商业化时才值得。

02 游戏循环与固定时间步长

约 2 千字 · 阅读约 6 分钟

本章用"按下右键"这类桌面操作举例，只是为了说明时钟问题；触屏上的等价操作见第 04 章。

先看你现在怎么写的

src/scenes/MainScene.ts:246-264：

TypeScript
private updateUnits(delta: number): void {
  const step = (UNIT_SPEED * delta) / 1000;
  ...
  unit.body.x += Math.cos(angle) * step;
  unit.body.y += Math.sin(angle) * step;
}

delta 是 Phaser 从 requestAnimationFrame 拿到的两帧间隔，单位毫秒。这段代码的意思是"每秒走 140 像素，这一帧占多少秒就走多少"，看起来完全正确，教科书也这么写。

问题在于它把一个连续量直接塞进了离散仿真。

为什么这在 RTS 里是致命的

先说后果，再说原理。

后果一：同一份操作，两台机器跑出两个世界

你按下右键的那一帧，单位目标点一致；但接下来 3 秒里，你的机器跑了 180 帧，朋友的机器掉帧跑了 155 帧。每一帧都"按实际时间补足位移"，理论上总位移一样 —— 但浮点加法不满足结合律：(a+b)+c ≠ a+(b+c) 在最后几位上是真会不一样的。于是 3 秒后两个单位的位置差了 0.0001 像素。这本来无所谓。

但一旦你开始做"两个单位贴到 22 像素内就互相阻挡""距离 48 内触发攻击"这种判定，0.0001 的差异就会在某个临界帧变成"我这打过、你那没打"，然后两边世界彻底分叉。

RTS 的联机几乎都是 lockstep（帧同步）：双方不传单位位置，只传你的操作指令，各自跑同样的仿真。这个模型的前提是给定相同输入，必须得到逐位相同的结果。delta * speed 从根上破坏这个前提。

后果二：掉帧时穿模

一帧卡 200ms，step 变成 28 像素。如果单位直径 26 像素、判定半径 22，这一帧直接从敌人身上跳过去了 —— 移动不发生碰撞反应，攻击判定被跳过。帧率越低，穿透越严重。

后果三：你没法做回放和自动化测试

想做"记录一局操作、重放验证 bug"，或者"用脚本模拟 10 分钟经济运营看曲线"，都需要确定性。带 delta 的仿真只能重放"操作"，不能重放"结果"。

正确做法：固定步长累加器

核心就三行：逻辑永远按固定的 1/60 秒推进，跟渲染帧率脱钩。

TypeScript
const SIM_DT = 1 / 60;          // 逻辑步长，秒
const MAX_STEPS_PER_FRAME = 5;  // 防止死亡螺旋
let accumulator = 0;

update(_time: number, delta: number): void {
  // 1. 把真实时间换算成"还剩多少逻辑时间要跑"，并夹住上限
  accumulator += Math.min(delta, 250) / 1000;

  // 2. 跑够整数个逻辑步
  let steps = 0;
  while (accumulator >= SIM_DT && steps < MAX_STEPS_PER_FRAME) {
    this.sim.step(SIM_DT);
    accumulator -= SIM_DT;
    steps++;
  }

  // 3. 剩下的零头留给下一帧，别丢
  if (steps === MAX_STEPS_PER_FRAME) accumulator = 0;

  // 4. 渲染层按仿真状态摆放，可以做插值
  this.render(accumulator / SIM_DT);
}

几个细节，都是踩过的坑：

  • 必须夹 delta（这里 250ms）。用户切走标签页再切回来，delta 可能是 30000ms。不夹的话你会一帧跑 1800 个逻辑步，浏览器直接假死。
  • 必须限步数（MAX_STEPS_PER_FRAME）。这是防"死亡螺旋"：仿真一帧要 30ms，而一帧只有 16.7ms，越跑越落后，最后彻底卡住。
  • 零头不能丢，否则当 60Hz 显示器和 60Hz 逻辑不对齐时，你会持续吞掉零点几毫秒，表现为"走位比预期慢 3%"。
  • 渲染插值可以最后做。先做"逻辑 60Hz、渲染每帧读最新状态"，画面会有最多 1 帧的抖动，肉眼几乎看不出来。等动作多了再插值。

改到你的代码上，UNIT_SPEED 仍然是 140，但每步位移恒等于 140 / 60 ≈ 2.333px，与帧率无关。

确定性：不止是"固定步长"

固定步长解决"帧数不一致"，但还不够。下面是 RTS 里真正会让你半夜起来查 bug 的几件事。

1. 三角函数和开方

Math.sin / Math.cos / Math.atan2 / Math.sqrt 在不同 JS 引擎（V8 / JSC / SpiderMonkey）和不同 CPU 上，最后一位可能不同。IEEE 754 只保证 + - * / 精确。

MainScene.ts:256-257 现在每帧算一次 atan2 再算 cos/sin，这既慢又不确定。

实用解法（按成本从低到高）：

  • 能不用就不用。移动改成"目标点方向增量 = (dx, dy) 归一化"，用 dx / len、dy / len，只剩一次 sqrt；再狠一点用 1/len 的牛顿迭代近似，各平台一致。
  • 查表。预生成 4096 项 sin 表，用整数索引取，跨平台完全一致。
  • 定点数。位置用"千分之一像素"的整数存，全部整数运算。彻底确定，但写起来累，只在真要做联机时上。

先做前两条，够用很久。

2. 随机数

现在代码里没有随机数。请保持这个习惯，或者一开始就用可播种的 PRNG：

TypeScript
// mulberry32：32 位状态，跨平台逐位一致
function mulberry32(seed: number) {
  return function () {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

绝对不要用 Math.random() 做任何影响玩法的事（暴击、AI 决策、单位初始微偏移）。Date.now() 同理。渲染层（粒子、飘字）用 Math.random() 没关系，因为它不改状态。

3. 遍历顺序

MainScene.ts:207-209 用 this.units.forEach 做框选，MainScene.ts:232 用 Array.from(this.selected) 下令。数组顺序是稳定的，Set 在 V8 里也是插入序，所以现在没问题。

但一旦你把单位存进哈希表、按对象引用排序、或者用 Map 遍历后重建数组，顺序就可能变。规则：仿真里所有"遍历所有实体"的地方，都按稳定的整数 id 升序。别依赖容器实现细节。

4. 累加顺序

for (const u of units) { 加血; 减血; } 这种在一个循环里既读又写的写法，结果依赖顺序。先结算伤害、再统一扣血（两段式），顺序的影响就小得多。第 08 章会展开。

落到这个仓库：建议的重构形状

目标是让 MainScene 变成"输入采集 + 渲染"，仿真搬进纯逻辑层（第 03 章详述）：

Text
src/
├── game/
│   ├── sim/
│   │   ├── GameState.ts     # 纯数据：units/资源/帧号
│   │   ├── step.ts          # step(state, commands, fixedDt) 纯函数
│   │   └── rng.ts           # 可播种 PRNG
│   └── ...
└── scenes/MainScene.ts      # 只负责：收集输入 → 调用 step → 把状态摆到 GameObject 上

step 里 不许出现 Phaser、Date、Math.random、window。能做到这一条，后面所有测试和回放都是免费的。

自检清单

改完之后，用这三条验证：

  1. 在 DevTools 里把 CPU 降速 6 倍（Performance 面板 → CPU throttling），单位走同样距离的时间应该基本不变（差在启动/停止的那一帧）。

03 场景、实体与逻辑分层

约 1 千字 · 阅读约 5 分钟

Phaser 的心智模型，一句话版本

Game 持有若干 Scene；Scene 有一个显示列表（display list），你 this.add.xxx(...) 加进去的东西都在这条列表上，每帧由渲染器按 depth 画一遍；Scene.update() 每帧被调用一次。

就这些。Phaser 没有"实体"概念，没有内置 ECS，也不规定你怎么组织数据。你现在组织数据的方式，会成为后面所有 bug 的来源。

现在这 280 行里混了五件事

打开 src/scenes/MainScene.ts，同一个类里同时住着：

  1. 仿真状态：units、selected、每个单位的 target（L21-22、L12-17）
  2. 仿真规则：怎么算移动（L246-264）、怎么判定框选命中（L189-213）、怎么分配目标点（L230-244）
  3. 渲染：body / ring / hpBar 三个 Rectangle（L97-104）
  4. 输入：指针事件、键盘（L106-149）
  5. UI：一段文本（L151-163）

这五件事的变更频率完全不同：UI 天天改，规则一周改一次，状态结构一个月改一次。混在一起的结果是，你想调一个 HUD 位置，得先读懂寻路代码。

一个单位的"本体"和"外观"是两回事

看 MainScene.ts:12-17：

TypeScript
// src/scenes/WorldScene.ts
type UnitView = {
  body: Phaser.GameObjects.Rectangle;
  ring: Phaser.GameObjects.Rectangle;
  hpBar: Phaser.GameObjects.Rectangle;
  lastHp: number;
};

private views = new Map<number, UnitView>();

private syncViews(s: GameState): void {
  // 1. 新增
  for (const u of s.units) {
    if (!this.views.has(u.id)) this.views.set(u.id, this.createView(u));
  }
  // 2. 删除（反向遍历，边删边遍历会漏）
  for (const id of [...this.views.keys()]) {
    if (!s.units.some(u => u.id === id)) {
      this.destroyView(this.views.get(id)!);
      this.views.delete(id);
    }
  }
  // 3. 摆位
  for (const u of s.units) {
    const v = this.views.get(u.id)!;
    v.body.setPosition(u.x, u.y);
    v.ring.setPosition(u.x, u.y).setVisible(this.selected.has(u.id));
    v.hpBar.setPosition(u.x, u.y - 21);
    if (u.hp !== v.lastHp) {          // 只在变化时重建血条宽度
      v.hpBar.width = 30 * (u.hp / u.maxHp);
      v.lastHp = u.hp;
    }
  }
}

这一段就是"逻辑/渲染分离"的全部：逻辑只产出状态，渲染只读状态。没有回调、没有事件、没有观察者模式。RTS 的单位数上千时，这种"每帧全量比对"反而最稳最快——因为它没有隐藏的失效路径。

Phaser 的 Container 能把多个 GameObject 组成一个整体移动。听起来很适合"单位 = 本体 + 血条 + 选中圈"。

不建议。原因：

  • 每个 Container 都是一次额外的矩阵变换，几百个单位时开销明显。
  • Container 内的坐标是相对坐标，做世界空间判定时要来回换算，容易错。
  • 销毁 Container 时要手动清子对象，容易泄漏。

RTS 的标准做法是不用容器，按 id 手动摆位（上面 syncViews 那样），血条和选中圈的偏移写死在渲染层。简单、快、好调试。

数据驱动：数值不要写在场景里

现在 UNIT_SPEED = 140、TILE_SIZE = 48、HOME_TILE = {8,21} 全是文件顶部的常量（MainScene.ts:3-10）。这一步先这样没问题。

但从"加第二种单位"开始，就必须把它们挪进数据表：

TypeScript
// src/game/data/units.ts
export const UNIT_DEFS = {
  peasant:  { name: '农人', hp: 40,  speed: 110, cost: { gu: 50 },  buildTime: 12 },
  warrior:  { name: '族兵', hp: 90,  speed: 130, cost: { gu: 60 },  buildTime: 18 },
  archer:   { name: '弓手', hp: 55,  speed: 120, cost: { gu: 70, jade: 10 }, buildTime: 20 },
} as const;

注意 DESIGN-v2.md:3.3 只给了造价，没有给血量、攻击、攻速、建造时间。这些数你现在必须自己定，第 10 章会给一套推法。

好处不只是"好改"：平衡表集中在两个文件里，你可以写脚本读出来做模拟（第 15 章），也可以将来换成 JSON 让策划改。

自检清单

  • src/game/ 下 grep -r "phaser" 应该无结果（类型导入除外）。
  • 注释掉整段 syncViews，游戏逻辑照常跑（画面不动）。
  • 把 Rectangle 换成 Sprite 时，只改渲染层文件。
  • 主场景文件行数不再随功能增长而线性膨胀（目标是每个系统 100-200 行）。

一句话总结

状态是数据，画是投影。 你现在写的 Unit 让两者纠缠，越早拆开越省事。

13 先出包：用 Capacitor 把网页变成 APK

大部分人会想"先把游戏做完，最后再打包"。这是反的。

WebView 里跑 Canvas 的注意点

1. 先量清楚你在渲染多少像素

手机 DPR 普遍 2.75-3。不要假设 Phaser 会自动帮你压 DPR，先打一行日志：

TypeScript
const c = game.canvas;
console.log(c.width, c.height, c.clientWidth, c.clientHeight, devicePixelRatio);
  • 如果 c.width === c.clientWidth，你按 CSS 像素渲染，性能最好、画面略软。
  • 如果 c.width === c.clientWidth * 3，你在按 DPR 3 渲染，清晰但填充率是 9 倍。

目标：把渲染像素控制在 CSS 尺寸的 2 倍以内。 具体做法取决于你测出来的结果：

  • 如果已经是 1 倍，不要为了"锐利"去提到 3 倍，中端机会直接掉帧。
  • 如果是 3 倍，把 Phaser 的内部尺寸或 canvas 后备缓冲压到 2 倍，或者改用固定内部分辨率（见下）。

一个稳妥的做法是固定内部渲染尺寸 + 等比缩放，不跟随设备 DPR：

TypeScript
new Phaser.Game({
  type: Phaser.AUTO,
  scale: {
    mode: Phaser.Scale.FIT,
    width: 1280,
    height: 720,
    autoCenter: Phaser.Scale.CENTER_BOTH,
  },
  // ...
});

代价是 20:9 的手机上会有黑边（或你改用 ENVELOP 裁切）。先按现在的 RESIZE 跑，量完再决定要不要换。

2. Phaser.Scale.RESIZE 要自己处理 resize

你 src/main.ts:8-11 用的是 RESIZE + CENTER_BOTH。它在横竖屏切换、刘海屏适配时靠得住，但你要自己重排相机与 HUD：

TypeScript
this.scale.on('resize', (gameSize: Phaser.Structs.Size) => {
  this.cameras.main.setSize(gameSize.width, gameSize.height);
  this.layoutHud(gameSize.width, gameSize.height);
});

3. 纹理与内存

APK 里的资源从 assets/public 加载，走 https://localhost，不是 file://，所以 fetch、纹理加载都正常。

但不要在运行时生成大尺寸 Canvas 纹理（比如用 Graphics 生成 1024×1024 的地图底图）。低端机很容易 OOM，而且这种纹理不会自动释放。

4. 音频必须"用户先点一下"

WebView 沿用浏览器的自动播放策略。做法：启动画面放一个「点击开始」，在里面初始化 AudioContext 并 resume()。

TypeScript
const ctx = new AudioContext();
await ctx.resume();   // 必须在点击事件里调用

04 触屏 RTS 的交互重设计（最重要的一章）

约 3 千字 · 阅读约 10 分钟 · 9 项清单

为什么这章必须先写

MainScene.ts:106-149 里那套输入模型是桌面思维：右键下令、拖拽框选、滚轮缩放、Shift 加选、H 回基地。这五件事在手机上一件都不成立：

  • 没有右键
  • 没有悬停（手指按下才算事件，抬起就结束）
  • 拖拽被"平移镜头"占用
  • 没有滚轮
  • 没有键盘（除非做软键盘，那更糟）

如果你先按桌面做完，装到手机上会发现操作链根本走不通，而交互是长在逻辑里的——改它等于重写。所以这一章放在经济、战斗之前。

手机 RTS 的四条硬约束

先记住这四条，后面所有方案都是它们的推论。

  1. 手指是 9-11mm 的肉垫，不是 1px 的箭头。 可点击目标最小 44-48 CSS px，推荐 56 px 以上。你现在 MainScene.ts:197 的点选半径是 22px，在手机上等于"永远选不中"。
  2. 拇指只覆盖屏幕下三分之一。 高频操作必须放在底部 35-40% 区域，顶部只放"看"的信息。
  3. 一次触摸只能做一件事。 鼠标可以"移动的同时按键"，手指不行。所以每个操作都要串行化、要有明确的状态机。
  4. 误触的代价远大于慢。 桌面点错一下重来；手机上误触移动会让整队兵跑进敌人家里。所有"不可逆"的操作都要二次确认或可撤销。

手势方案对照表

先给结论，再解释：

拖拽框选空白处长按 250ms 后拖动保留框选语义与平移抢同一个手势，要有明显进入反馈
右键下令点选后再点地面（tap-tap）单手、无遮挡容易误触移动，需要"点击空白=取消选中"来兜底
悬停看信息点选即看 / 长按查看简单看不到就点，节奏变慢

我建议的这套（可直接照做）

相机

  • 单指在空白处拖动 = 平移。判定阈值 8-10 px：位移小于阈值算"点击"，大于才算"拖动"。
  • 双指捏合 = 缩放，缩放中心取两指中点，范围限死（比如 0.8-1.6），不要让它缩到看不见单位。
  • 不要做屏幕边缘推屏。桌面 RTS 的边缘滚动在手机上极易误触，而且手指本来就挡着边缘。
  • 不要做惯性滑动。RTS 需要精确对位，惯性会让"我明明停在这里"变成"又滑过去半个屏幕"。

Phaser 里必须显式开启多点触控，默认只处理单指：

TypeScript
// main.ts 的 GameConfig
input: { activePointers: 3 }   // 鼠标 + 双指

// 或者场景内
this.input.addPointer(2);

同时把浏览器的默认手势全关掉，否则 Android WebView 会把双指捏合当成页面缩放：

HTML
<!-- index.html -->
<meta name="viewport" content="width=device-width,initial-scale=1,maximum-scale=1,user-scalable=no,viewport-fit=cover">
CSS
html, body, canvas {
  touch-action: none;        /* 关键：交给游戏处理所有手势 */
  overscroll-behavior: none;
  user-select: none;
  -webkit-tap-highlight-color: transparent;
}

选择：三套方案怎么选

方案 A：长按进入框选（推荐）

  • 空白处按住 250ms → 屏幕出现"框选模式"提示（边框变色 + 轻微震动 navigator.vibrate(10)）
  • 继续拖动 → 拉出选框；抬起 → 选中框内单位
  • 空白处快速拖动 → 平移镜头

优点：保留了"一把框住一队兵"的爽感，这是 RTS 的核心操作。缺点：需要一个清晰的模式反馈，否则玩家分不清自己在平移还是在框选。

实现要点：用 pointer.getDuration() 判断按住时长，用 pointer.distance 判断位移。进入框选模式后，把相机平移锁死，避免两个动作同时发生。

方案 B：点选 + 范围选择

  • 点中一个单位 → 自动选中它周围同类的 5 个单位
  • 想精确多选，用底部编组槽

优点：零学习成本，绝对不会误操作。缺点：失去了精确控制，打不了微操。对"轻量 RTS"可以接受，对正经 RTS 不够。

方案 C：双指轻点 = 全选屏幕内单位

  • 补一个"一键选全屏部队"的兜底

优点：极端简单。缺点：只能当辅助，不能当主操作。

我的建议：A 为主（长按框选），C 作为补充，再加 HUD 上两个按钮「全选部队」「全选农人」。 三个入口覆盖 90% 场景，手指不用做精细动作。

下令：tap-tap 的坑和补法

选中单位后，点地面 = 移动。这看起来最自然，但有两个问题：

坑 1：误触。 玩家想点空地取消选中，结果部队跑过去了。

补法：点击空白地面 = 取消选中，不移动；要移动必须点在"有意义的区域"（地图内任意位置都算有意义……所以这条行不通）。

更实用的补法是双保险：

  • 选中后，画面底部出现一个明显的"移动"激活态（选中的单位脚下有目标标记）
  • 点地面下令后，目标点显示一个 0.5 秒的落点标记，期间点"取消"按钮可撤销

坑 2：抬手才生效还是按下就生效？

必须在 pointerup 时生效，不能在 pointerdown。手指按下时玩家还在调整，抬起的瞬间才是"确认"。Phaser 里就是 this.input.on('pointerup', ...)，你现在 MainScene.ts:137-143 用的就是 up，这点是对的，保留。

指令盘：什么时候值得做

长按单位 300ms 弹出环形菜单（移动/攻击/采集/驻守/取消）——RTS 手游常用。

建议 v0.1 不做。 理由：环形菜单在 5 英寸屏上按钮会挤到 40px 以下，误触率高于收益；而且你的玩法里单位类型少，用底部命令卡（一章 5 个按钮）已经够。

什么时候做：当单位指令超过 6 种，或者需要"对着某个目标下特定指令"（比如右键敌人=攻击、右键资源=采集）时。环形菜单真正的价值是把"目标 + 动词"合并成一次操作，而不是省按钮。

编队：用按钮，不用键盘

底部放 3-5 个编组槽（每个 56×56）：

  • 点击 = 选中该编组
  • 长按 = 把当前选中写入该编组
  • 双击 = 镜头飞到编组位置

实现上就是 groups: number[][]（每组存单位 id），不复杂，但对手机玩家的体验提升极大——它替代了 Ctrl+1 到 Ctrl+5。

现在有什么

MainScene.ts 里和"下达指令"有关的只有三处：

能跑，但只覆盖了"移动"一种指令，而且没有队列、没有编队、没有目标类型判断。这一章讲怎么把它扩成一套完整的指令系统——注意，输入方式要先按第 04 章改成触屏，再回来加指令。

RTS 的指令模型：三层

不要一上来写"右键 = 移动"。RTS 的指令应该拆成三层：

Text
玩家意图（点了一个敌人）
  → 指令类型（攻击）
    → 参数（目标实体 id）
      → 执行器（走到攻击距离内，按间隔攻击）

对应到类型：

TypeScript
// src/game/sim/orders.ts
export type Order =
  | { kind: 'move'; x: number; y: number }
  | { kind: 'attackMove'; x: number; y: number }
  | { kind: 'attack'; targetId: number }
  | { kind: 'gather'; nodeId: number }
  | { kind: 'build'; buildingId: number; x: number; y: number }
  | { kind: 'stop' };

export interface OrderQueue {
  current: Order | null;
  pending: Order[];      // 最多 4-5 条，多了玩家也记不住
}

为什么不用一个 target: Vector2 打天下：因为攻击要追一个会动的实体，采集要循环往返，建造要等资源到位。这些都不是"一个坐标"能表达的。现在的 Unit.target（MainScene.ts:16）在只有移动时够用，加第二种指令就会开始塞 if。

没有右键，怎么表达"对目标下令"

桌面的右键是"动词 + 目标"一次完成。手机上的替代方案是上下文指令：玩家只点目标，系统根据目标类型决定动词。

点到的对象默认指令备注
敌方单位攻击不需要先按"攻击"按钮
资源点采集农人才有效，兵点了变成移动
己方建筑选中建筑 / 打开面板不是移动
中立部落交涉（或攻击，需长按）默认不打，避免误掉德望（DESIGN-v2.md:5.3）
空地移动唯一需要"确认感"的指令

这套映射的好处是手指只需要点一次。坏处是歧义：敌军站在资源点旁边，你点下去到底打还是采？

处理办法：先做命中测试，按优先级取目标——单位 > 资源点 > 建筑 > 地面。然后再看目标与当前选中单位的关系（敌方/己方/中立）。命中测试的半径要比视觉大一圈（第 04 章说的 44-48px）。

目标点分配：别让 12 个单位叠在一个像素上

commandMove() 现在的做法是方阵：

TypeScript
const columns = Math.ceil(Math.sqrt(targets.length));
const offsetX = ((index % columns) - (columns - 1) / 2) * 34;
const offsetY = (Math.floor(index / columns) - (rows - 1) / 2) * 34;

三个问题：

  1. 不检查落点是否可走。偏移后可能落在建筑里、水里、地图外。现在只做了 Clamp（L240-241），挡不住建筑占位。
  2. 不按距离分配。Array.from(this.selected) 的顺序决定谁去哪个格子。结果是最远的单位可能分到最近的格子，队伍先交叉再散开。
  3. 没有队形概念。方阵适合"站住"，不适合"穿过窄口"。

实用改法（按成本从低到高）：

方案 1：贪心就近分配（够用）

  1. 生成 N 个目标槽位（方阵或圆形）。
  2. 对每个单位，找最近的空槽位，占用。
  3. 槽位不可走就向外扩散一圈重找。
TypeScript
function assignSlots(units: UnitState[], slots: Vec2[], walkable: (x: number, y: number) => boolean): Map<number, Vec2> {
  const free = slots.filter(s => walkable(s.x, s.y));
  const result = new Map<number, Vec2>();
  for (const u of units) {
    let best = -1;
    let bestD = Infinity;
    for (let i = 0; i < free.length; i++) {
      const d = (free[i].x - u.x) ** 2 + (free[i].y - u.y) ** 2;
      if (d < bestD) { bestD = d; best = i; }
    }
    if (best >= 0) {
      result.set(u.id, free[best]);
      free.splice(best, 1);
    }
  }
  return result;
}

这是 O(N²)，N < 50 时完全没问题。不要上匈牙利算法，收益不值那个复杂度。

方案 2：按编队形状分配

  • 方形队形：适合站桩防守。
  • 楔形/横排：适合正面推进，近战在前、远程在后。
  • 纵队：适合穿窄口。

形状由"当前选中单位的兵种构成"决定，不是由玩家选。手机上不要再加一个"选队形"的按钮。

方案 3：流场（第 06 章）

当目标点相同、单位数超过 30 时，逐单位 A* 会让所有人挤同一条路。这时用流场：对目标点做一次反向 BFS，得到每个格子的"下一步方向"，所有单位共享。代价是只适合"同一目的地"的群体移动。

指令队列：手机上的取舍

桌面用 Shift 排队列。手机没有 Shift，两种做法：

  1. 队列开关：命令卡上有一个「队列」按钮，打开后连续点的指令会追加而不是替换。适合少量操作。
  2. 默认替换，长按追加：点地面 = 立刻移动；长按地面 300ms = 追加到队尾。这个更符合触屏直觉，但需要明确反馈（队尾出现编号小旗）。

建议 v0.1 只做"替换"，队列等到有采集回环和建造之后再上。理由：队列的 bug（永远不清空、执行到一半卡住）很难查，而前期玩家一次只会下一两个指令。

队列实现的三个坑：

  • 执行完要清空。current 完成时必须从 pending 取下一条，不能只把 current 置空。
  • 新指令要能打断。玩家点"停止"或点新目标时，队列要整体清掉，不能"排队等死"。
  • 目标实体可能已死。attack 指令的 targetId 找不到时，要降级为 move 到目标最后位置，而不是原地发呆。

编队：按钮替代 Ctrl+数字

底部 3-5 个槽位，每个 56×56（第 04 章的手指点按下限）：

  • 点击 = 选中该编组。
  • 长按 300ms = 把当前选中写入该编组。
  • 双击 = 镜头飞到编组中心。

数据结构就是 groups: number[][]，存单位 id，不存对象引用。单位死亡时不用急着清理，选中时过滤掉不存在的 id 即可——每帧清理反而容易漏。

  • 框选只判断中心点（L208），大单位边缘在框内但中心在框外就选不中。

  • 命中测试按"单位 → 建筑 → 地面"分层，每层内部再按距离。

  • 点选半径用世界坐标 24-28px（对应屏幕上 48-56px），并且随相机缩放反向补偿：放大时半径缩小，缩小时半径放大，保证屏幕上的手感一致。

现在的地图只是一张画

drawMap()（MainScene.ts:67-86）画了底色、一条浅水带、网格线。没有任何数据结构。所有"地图"信息都在渲染调用里，这意味着：

  • 你无法回答"这个格子能不能走"。
  • 你无法放资源点，因为资源点需要坐标、储量、类型。
  • 你无法做范围查询，比如"以这个单位为中心 4 格内有哪些敌人"。

坐标约定：先定死，再写代码

现在代码里有两套约定，而且不一致：

  • 单位：createUnit() 用 tileX * TILE_SIZE + TILE_SIZE / 2（L98-99）——格中心。
  • 基地：createBase() 用 tileX * TILE_SIZE（L89-90）——格左上角。

结果就是：基地和单位差半个格子。看起来只是"基地偏了一点"，但到了建造放置、占位判定、寻路时，这半个格子会变成"明明点在空地上却提示被占用"。

统一约定（建议）：

  • 世界坐标原点在左上角，单位用浮点像素。
  • 格子 (tx, ty) 的左上角是 (tx * 48, ty * 48)，中心是 +24。
  • 所有实体逻辑位置一律存中心。渲染时如果某个图形以左上角为锚点，自己减半，不要在逻辑层补偿。

地形数据

TypeScript
// src/game/map/terrain.ts
export enum Tile {
  Grass = 0,
  ShallowWater = 1,   // 苗蛮不减速，其他 -30%（DESIGN-v2.md:5.4）
  Blocked = 2,        // 建筑、山体
}

export class Terrain {
  readonly cols = 40;
  readonly rows = 30;
  readonly tiles = new Uint8Array(this.cols * this.rows);

  idx(x: number, y: number) { return y * this.cols + x; }

  at(x: number, y: number): Tile {
    if (x < 0 || y < 0 || x >= this.cols || y >= this.rows) return Tile.Blocked;
    return this.tiles[this.idx(x, y)];
  }

  walkable(x: number, y: number) {
    const t = this.at(x, y);
    return t !== Tile.Blocked;
  }

  /** 世界坐标 → 格坐标 */
  toTile(wx: number, wy: number) {
    return { tx: Math.floor(wx / 48), ty: Math.floor(wy / 48) };
  }
}

占位：建筑和单位是两种碰撞

不要用一套碰撞搞定所有东西。

建筑：硬占位

建筑覆盖的格子直接标 Blocked。这样 A* 天然绕开，不需要额外碰撞检测。

问题在于建筑尺寸不一定是整数格。现在基地是 2.5 格（120px），放下去必然压住半格。两个选择：

  1. 把建筑尺寸改成整数格（推荐）。基地 3×3，祭坛 2×2，民居 1×1。
  2. 保留非整数尺寸，但占位按 Math.ceil 向上取整，代价是视觉上建筑边缘会"多吃"一格。

建议选 1。 网格游戏里，所有占地都应该是整数格，否则放置预览、寻路、范围查询三处都要处理小数。

单位：软避让，不是硬碰撞

单位之间不要做"撞上就停"的硬碰撞。RTS 的单位需要能互相穿过一点、再被推开，否则一队兵会在门口卡死。

// 每帧一次，O(n²)；n < 200 时可以接受
for (let i = 0; i < units.length; i++) {
  for (let j = i + 1; j < units.length; j++) {
    const dx = units[j].x - units[i].x;
    const dy = units[j].y - units[i].y;
    const d2 = dx * dx + dy * dy;
    const min = 20;                    // 两个单位的最小间距（像素）
    if (d2 > 0 && d2 < min * min) {
      const d = Math.sqrt(d2);
      const push = (min - d) * 0.5;
      const nx = dx / d, ny = dy / d;
      units[i].x -= nx * push;
      units[i].y -= ny * push;
      units[j].x += nx * push;
      units[j].y += ny * push;
    }
  }
}

200 单位 = 19,900 次距离比较/帧，JS 里大约 0.2-0.5ms（经验值），可以接受。超过 300 再上空间分区。

空间查询：先别急着上四叉树

RTS 最常见的查询是：

  • 框选：矩形内有哪些单位。
  • 攻击范围：以某点为中心，半径 R 内有哪些敌人。
  • 采集：最近的同类型资源点。

1200 格、100 单位以内，暴力遍历完全够。 100 个单位做一次范围查询 = 100 次距离比较，一帧做 50 次也就 5000 次，微不足道。

什么时候需要空间分区：

  • 单位 > 300，且每帧有大量范围查询（比如每个单位都在索敌）。
  • 这时用均匀网格（uniform grid），格子大小取 3-4 个 tile，把单位 id 挂到格子里。查询时只遍历覆盖的格子。

不要上四叉树。均匀网格在 RTS 这种分布相对均匀、单位会移动的场景里更快也更好写。

TypeScript
// 均匀网格的骨架
class SpatialGrid {
  private cells = new Map<number, number[]>();  // cellKey -> unitId[]
  constructor(private cellSize: number, private cols: number) {}

  key(x: number, y: number) {
    const cx = Math.floor(x / this.cellSize);
    const cy = Math.floor(y / this.cellSize);
    return cy * this.cols + cx;
  }

  insert(id: number, x: number, y: number) {
    const k = this.key(x, y);
    let list = this.cells.get(k);
    if (!list) this.cells.set(k, (list = []));
    list.push(id);
  }

  clear() { this.cells.clear(); }   // 每帧重建，比增量维护简单且不易错
}

每帧重建（清空 → 全部插入）比"移动时从旧格子删、往新格子加"简单得多，而且不容易泄漏。1000 个单位重建一次也就 1000 次插入。

为什么现在还没问题

updateUnits()（MainScene.ts:246-264）是直线移动：算角度，cos/sin 走一步。地图是 40×30 的空网格（MainScene.ts:3-7），没有任何阻挡，所以怎么走都对。

一旦有了建筑和资源点，直线移动就会出现三种情况：

  1. 撞墙后原地抖动（目标在墙后，永远走不到）。
  2. 从两个建筑之间"擦"过去，视觉上穿模。
  3. 一队兵全部沿同一条直线走，末端堆成一坨。

寻路不是"让单位聪明"，是"让单位不违反地图规则"。

把地图离散成格子，每格两种状态：可走 / 不可走。

A* 的要点

A* 不复杂，容易写错的是四件事。

1. 启发函数要与移动方式匹配

八方向移动用 octile 距离：

TypeScript
function heuristic(x: number, y: number, gx: number, gy: number): number {
  const dx = Math.abs(x - gx);
  const dy = Math.abs(y - gy);
  return 10 * (dx + dy) + (14 - 20) * Math.min(dx, dy);
  // 直走代价 10，斜走代价 14（≈10√2）
}

四方向用曼哈顿距离。用欧氏距离配四方向、或用曼哈顿配八方向，都会让寻路变慢或走歪。

2. 禁止斜穿墙角

八方向最容易出的 bug：两个对角方向都是墙，但斜着穿过去了，视觉上从墙缝里钻出来。

// 从 (x,y) 走向 (nx,ny)，如果是斜向，要求两个相邻正交格都可走

3. 用开放列表的正确结构

小地图（1200 格）用"每次线性扫最小 f"也能跑，但单位一多就慢。写一个二叉堆，20 行：

TypeScript
class MinHeap<T> {
  private a: T[] = [];
  constructor(private less: (x: T, y: T) => boolean) {}
  push(v: T) { this.a.push(v); this.up(this.a.length - 1); }
  pop(): T | undefined {
    const top = this.a[0];
    const last = this.a.pop();
    if (this.a.length && last) { this.a[0] = last; this.down(0); }
    return top;
  }
  get size() { return this.a.length; }
  private up(i: number) {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (!this.less(this.a[i], this.a[p])) break;
      [this.a[i], this.a[p]] = [this.a[p], this.a[i]];
      i = p;
    }
  }
  private down(i: number) {
    for (;;) {
      const l = i * 2 + 1, r = l + 1;
      let m = i;
      if (l < this.a.length && this.less(this.a[l], this.a[m])) m = l;
      if (r < this.a.length && this.less(this.a[r], this.a[m])) m = r;
      if (m === i) break;
      [this.a[i], this.a[m]] = [this.a[m], this.a[i]];
      i = m;
    }
  }
}

4. 路径要平滑

A* 出来的是"格子中心点的折线"，单位走起来会一顿一顿。用视线拉直（string pulling）：从当前点出发，尽量连到最远的、中间无阻挡的点。

TypeScript
function smooth(path: Vec2[], walkableLine: (a: Vec2, b: Vec2) => boolean): Vec2[] {
  const out: Vec2[] = [];
  let i = 0;
  while (i < path.length - 1) {
    let j = path.length - 1;
    while (j > i + 1 && !walkableLine(path[i], path[j])) j--;
    out.push(path[j]);
    i = j;
  }
  return out;
}

walkableLine 用 Bresenham 逐格采样即可。

为什么多单位会堵成一团

这是 RTS 寻路真正的难点，不是 A* 本身。

假设 20 个单位从基地出发，目标同一片区域。每个单位独立跑 A*，得到的路径几乎一样（网格只有那么几条通路）。于是：

  1. 入口只有一个格子，20 个单位同时挤进去，互相推挤。
  2. 没有动态代价，先到的单位不会"让路"，后到的继续往同一个格子走。
  3. 没有局部避让，单位之间可以重叠，视觉上像一坨。

三种解法，按成本排：

解法 1：槽位 + 分离力（先做这个）

  • 目标点用第 05 章的槽位分配，不要所有单位同一个点。
  • 每帧给单位加一个"互相推开"的力：
TypeScript
// 只对距离 < 半径和的单位对生效
const push = (minDist - dist) * 0.5;
u.x -= nx * push;
u.y -= ny * push;

分离力要小，否则队伍会像爆炸一样散开。经验值：每帧最多推 0.5-1px。

解法 2：流场（30 个单位以上）

对同一个目标点，做一次反向 BFS（从目标扩散），得到每格的"下一步方向"。所有单位共享这张表，不再各自跑 A*。

  • 优点：一次计算，N 个单位共享；不会出现"20 条不同路径"。
  • 缺点：只适合同一目的地；目标变了要重算；窄口仍然会堵（物理上就那么大）。

解法 3：预约表 / 时间窗（不建议现在做）

给每个格子记录"谁在什么时候占用"，单位排队通过。这是正经 RTS 的做法，但实现复杂、容易死锁，单人项目不值得。

建议路线：v0.1 用槽位 + 分离力；单位超过 30 再用流场。 DESIGN-v2.md:9.5 也写了"M2 若单位 >30 再上网格 A*"，方向一致，但顺序要反过来——先有槽位和分离，再谈 A*，否则 A* 只会让所有人更快地挤到一起。

性能：A* 不是免费的

40×30 = 1200 格。一次最坏情况的 A* 大约扩展几百到一千个节点，在 JS 里 0.1-0.5ms（经验值，取决于实现和浏览器）。听起来很少，但：

  • 20 个单位同一帧寻路 = 2-10ms，直接吃掉 60fps 预算的一半。
  • 100 个单位 = 10-50ms，一帧卡死。

所以必须分帧：

配套两条：

  • 路径缓存：Map<"sx,sy,gx,gy", Vec2[]>，同起点终点直接复用。缓存要在地图变化（建筑建成/拆除）时清空。
  • 失败降级：找不到路时不要每帧重试，标记 pathFailedAt = tick，隔 30 帧再试一次。

什么时候不该用 A*

  • 单位在地图外/目标不可走：直接拒绝，不要跑 A*。
  • 直线可达：先用 Bresenham 检查视线，能直走就不寻路。这一步能省掉 80% 的计算（经验值）。
  • 同一帧大量单位收到同一目标：先合并请求，用流场或槽位，不要逐个跑。

和渲染无关

寻路结果只应该是"一串世界坐标"，放在 src/game。不要在 A* 里 this.add.circle 画路径，那是调试代码，用 if (DEBUG_PATH) 包起来，发布前删掉。

自检

一句话总结

A* 解决"怎么绕过墙"，槽位和分离力解决"怎么不挤在一起"。 后者才是玩家感知到的"寻路好不好"。

采集回环：一个状态机

农人的行为不是"每秒加资源"，是一个循环：

Text
空闲 → 走向资源点 → 采集（耗时） → 走回交付点 → 卸货 → 走回资源点 → ...

用状态机写，不要用一堆 if：

TypeScript
// src/game/sim/gather.ts
export type GatherPhase = 'toNode' | 'harvesting' | 'toDropoff' | 'depositing';

export interface GatherOrder {
  kind: 'gather';
  nodeId: number;
  phase: GatherPhase;
  /** 当前这一趟已经采到的量 */
  carrying: number;
  /** 采集开始/结束的帧号 */
  phaseEndTick: number;
}

每个阶段只做一件事：

TypeScript
function updateGather(u: UnitState, g: GatherOrder, state: GameState): void {
  const node = state.nodesById.get(g.nodeId);
  if (!node || node.amount <= 0) {
    // 资源点枯竭：找最近的同类资源点，找不到就回空闲
    const next = findNearestNode(state, node?.kind ?? 'wood', u.x, u.y);
    if (next) g.nodeId = next.id;
    else { u.order = null; return; }
  }

  switch (g.phase) {
    case 'toNode':
      if (moveTo(u, node.x, node.y, 40, state)) {   // 40px 内算到达
        g.phase = 'harvesting';
        g.phaseEndTick = state.tick + HARVEST_TICKS;
      }
      break;

    case 'harvesting':
      if (state.tick >= g.phaseEndTick) {
        g.carrying = Math.min(node.amount, CARRY_AMOUNT[node.kind]);
        node.amount -= g.carrying;
        g.phase = 'toDropoff';
      }
      break;

    case 'toDropoff':
      if (moveTo(u, state.dropoff.x, state.dropoff.y, 48, state)) {
        g.phase = 'depositing';
        g.phaseEndTick = state.tick + 6;            // 0.1 秒卸货
      }
      break;

    case 'depositing':
      if (state.tick >= g.phaseEndTick) {
        state.resources[node.kind] += g.carrying;
        g.carrying = 0;
        g.phase = 'toNode';
      }
      break;
  }
}

几个必须处理的边界：

  • 资源点被采空：换最近同类；没有就空闲。
  • 交付点被拆：换最近的大邑/伐木场；没有就空闲（并且 HUD 提示）。
  • 玩家中途下令：直接打断 GatherOrder，清空 carrying（或者让农人先把这趟送回去，二选一，但要在 UI 上说清楚）。
  • 多人采同一个点：资源点储量扣减要在"采集完成"那一刻做，不是开始采的时候做，否则会出现负数。

  2. 显示"预计 +10 木 / 8 秒"的速率提示。

如果两个农人分工（一个木一个石），材料齐大约 100 秒；再算上在资源点之间走动、建造时间（文档没给），第一个祭坛大约在 2-3 分钟。这个节奏是合理的。

但注意：这意味着开局两分钟里，玩家几乎没有决策，就是看着两个农人搬东西。手机上这种"干等"体验很差。两个解法：

  • 开局多给一个农人（3 个），或
  • 降低祭坛的石头需求（80 石是最重的一项，80 / 0.8 = 100 秒，占了三分之二的时间）。

我倾向第二个：石从 80 降到 50，祭坛时间缩短到约 70 秒。这是建议，不是文档结论。

德望：算完之后发现不够

这一节是本章最重要的部分。DESIGN-v2.md:5.3 说：

  • 德望来源：祭祀 +2、击败 +3（单次战斗上限 +9）、归附 +8、公共工程 +5。
  • 归附阈值 50，禅让阈值 100，开局 20。
  • 祭祀消耗：祈谷 20 玉、祈风 30 玉、祈雨 30 玉、告成 50 玉 + 100 谷（+10 德望）。

从 20 到 100，需要 +80 德望。

路线一：全靠祈谷（+2 / 20 玉）

  • 40 次祭祀 × 20 玉 = 800 玉。
  • 一座玉山总储量正好 800（DESIGN-v2.md:3.4）。
  • 还没算祭坛本身的 30 玉、祈风祈雨、精英单位的玉。
  • 结论：单座玉山不可能只靠祈谷走到禅让。

路线二：靠告成（+10 / 50 玉）

  • 8 次 × 50 玉 = 400 玉，玉够了。
  • 但告成冷却 120 秒，8 次 = 960 秒 = 16 分钟。
  • 再加 800 谷，以及前面采集、建造的时间。
  • 结论：理论可行，但最短 16 分钟，和 M2 验收的"10-15 分钟分出胜负"冲突。

路线三：混合

  • 归附 3 个部落：+24。
  • 击败敌方部队：每次 +3，上限 +9/场，可重复。
  • 加上 20 开局，靠战斗和归附补到 50，再用告成冲 100。
  • 这条最接近设计意图，但德望的主要来源变成了战斗，和"不打也能赢"的卖点有张力。

我的判断：德望的数值需要改，至少改一处：

  • 把禅让阈值从 100 降到 80（减少 20 点，约省 2 次告成 = 4 分钟），或
  • 把告成冷却从 120 秒降到 60 秒（16 分钟减半），或
  • 增加第二座玉山/提高玉的采集效率。

不改的话，"政治胜利"在单局时长内基本不可达——玩家会算出来"打架更快"，然后所有人都去打架，德望系统就白设计了。

攻击间隔用帧数，不用秒。 用秒就要每帧做浮点减法，累积误差会让两台设备的攻击节奏漂移，而且和固定步长（第 02 章）冲突。

伤害公式：两种，选一种

方案 A：减法护甲

TypeScript
damage = Math.max(1, attacker.damage - defender.armor);
  • 优点：玩家一眼能算清"我 14 攻，他 3 甲，一下打 11"。
  • 缺点：高攻低甲时会溢出，低攻高甲时收益断崖。数值范围要控制好。

方案 B：百分比减伤

TypeScript
damage = attacker.damage * (100 / (100 + defender.armor));
  • 优点：数值平滑，不会出现"1 点伤害"的尴尬。
  • 缺点：玩家算不清，需要 UI 显示"减伤 23%"。

建议用 A（减法），并且设最低 1 点。 你的单位种类少（农人/族兵/弓手/精英），减法足够表达克制关系，而且符合"符号化、可读"的美术方向（DESIGN-v2.md:7.1）。

攻击循环：用 tick 判定，不要用计时器

TypeScript
function updateCombat(u: UnitState, state: GameState): void {
  const target = u.targetId != null ? state.unitsById.get(u.targetId) : null;

  // 1. 目标没了 / 死了 / 跑太远 → 放弃
  if (!target || target.hp <= 0 || dist(u, target) > u.stats.acquireRange * 1.5) {
    u.targetId = null;
  }

  // 2. 索敌（不要每帧都做，见下）
  if (u.targetId == null && state.tick % 15 === 0) {
    u.targetId = findTarget(u, state);
  }

  if (u.targetId == null) return;

  // 3. 射程内且冷却好了 → 攻击
  if (dist(u, target) <= u.stats.range && state.tick >= u.nextAttackTick) {
    state.damageEvents.push({ from: u.id, to: target.id, amount: calcDamage(u, target) });
    u.nextAttackTick = state.tick + u.stats.attackInterval;
  }
}

注意几个细节：

  • nextAttackTick 用帧号，不是 cooldown -= dt。后者在掉帧时会漂移。
  • 索敌不是每帧做。每 15 帧（0.25 秒）一次，100 个单位也就每帧 6-7 次查询。
  • 脱战半径是 acquireRange × 1.5，不是无限追。没有这个，单位会追着敌人跑遍全图。

目标选择：优先级 + 黏性

简单版优先级：

  1. 正在攻击我的敌人（自卫优先）。
  2. 最近的敌人。
  3. 血量最低的敌人（集火）。

但不要每帧重新选。 每帧重选会导致"目标抖动"：两个敌人距离差不多，单位在两者之间来回转头，一下都打不出去。

两个机制解决：

  • 黏性：一旦选定，至少保持 1 秒（60 帧），除非目标死亡或超出脱战半径。
  • 迟滞：新目标的距离要比当前目标近 20% 才换。
TypeScript
function shouldSwitch(u: UnitState, current: UnitState, candidate: UnitState): boolean {
  if (current.hp <= 0) return true;
  if (dist(u, candidate) < dist(u, current) * 0.8) return true;
  if (candidate.id === u.lastAttackerId) return true;   // 被打优先还手
  return false;
}

两段式结算：不要边打边扣血

最典型的 bug：单位 A 打死 B，B 在同一帧也打出了伤害，因为 B 的更新在 A 之后、hp 还没扣到 0。

正确顺序：

TypeScript
function resolveCombat(state: GameState): void {
  // 阶段 1：所有单位决定"这帧打不打、打谁"，只写 damageEvents
  for (const u of state.units) updateCombat(u, state);

  // 阶段 2：统一结算伤害（先算总伤害，避免过杀）
  const incoming = new Map<number, number>();
  for (const e of state.damageEvents) {
    incoming.set(e.to, (incoming.get(e.to) ?? 0) + e.amount);
  }
  for (const [id, dmg] of incoming) {
    const t = state.unitsById.get(id);
    if (t) t.hp -= dmg;
  }

  // 阶段 3：清理死亡
  state.units = state.units.filter(u => u.hp > 0);
  state.damageEvents.length = 0;
}

三个阶段分开，顺序就不会影响结果。这也是第 02 章说的"累加顺序"的具体应用。

过杀（overkill）：远程齐射的通病

5 个弓手同时打一个 40 血的农人，每人 11 点，总伤害 55。前 4 个就够打死，第 5 个的伤害浪费了——更糟的是，如果目标已经死了，第 5 个还会"鞭尸"或者卡住。

三种处理：

  1. 算总伤害前先看血量：incoming 累计到目标当前 hp 就停止分配（简单，但会让部分单位"白打"）。
  2. 目标预约：每个目标记录"已被预约的伤害"，新单位索敌时跳过预约已满的目标。复杂，但效果好。
  3. 不处理。前期单位少，过杀不明显。等有 10 个以上远程单位再说。

建议 v0.1 用 3，v0.2 用 1。 不要一上来做预约表。

追击与攻击移动

两种指令要分开：

  • 攻击（点敌人）：走到射程内，停下打，目标死了就停。
  • 攻击移动（点地面）：往目标点走，途中遇到敌人就停下打，打完继续走。

手机上"攻击移动"需要一个独立按钮，因为 tap-tap 的默认语义是移动。放在命令卡第二排，图标用"剑 + 箭头"。

不要做"自动攻击移动"：玩家点地面就自动打沿途敌人，会导致"我只想撤退，结果部队停下来打架"。

战斗可读性（第 11 章展开）

战斗系统做完后，玩家要能一眼看出：

  • 谁在打谁（攻击目标有细线或朝向）。
  • 谁快死了（血条变红 + 闪烁）。
  • 谁在挨打（受击闪白，持续 100ms）。
  • 伤害数字（可选，单位多了会刷屏，建议只显示暴击/大伤害）。

这些都不是"特效"，是信息。没有它们，玩家会觉得"打起来了但看不懂"。

10 数值与平衡：从产出率推造价

平衡不是"调数字"

平衡是让每一段时间的投入产出大致相等。你不需要让所有单位一样强，你需要让玩家在"造农人还是造兵""采玉还是采木"之间真的需要想一下。

这一章给一套能落地的推法。所有具体数字都是经验值，方法比数字重要。

第一步：定"每秒产出"

平衡的基准不是造价表，是一个农人每秒能产出多少资源。

第二步：从"回本时间"推造价

一个农人 50 谷，每秒产 0.8 谷，回本时间 = 50 / 0.8 = 62.5 秒。

这个数字意味着什么：造农人后 1 分钟开始纯赚。RTS 里这个值通常在 60-90 秒（经验值）：

  • 低于 45 秒：农人太便宜，玩家会无脑爆农，前期没有决策。
  • 高于 120 秒：农人回本太慢，玩家宁愿直接造兵，经济系统失去意义。

如果你想让回本时间变成 75 秒，造价应该是 75 × 0.8 = 60 谷。这是一个可调的旋钮，不是拍脑袋。

同样的方法推到兵：

  • 族兵 60 谷，一个农人要 75 秒才能产出这 60 谷。
  • 也就是说，每造一个兵，你就少了一个农人 75 秒的产出。
  • 如果一局 10 分钟，2 个农人全力产谷 = 960 谷，够造 16 个族兵（不算其他开销）。这就是"兵力上限"的直觉来源。

第三步：训练时间与人口上限

训练时间决定"兵什么时候能出来"，人口上限决定"最多能有多少"。

DESIGN-v2.md:3.3 给了人口上限 12（基础）+ 4/民居（上限 24），但没给训练时间。

用"训练消耗速率"反推：

Text
训练一个单位消耗资源的速率 = 单位造价 / 训练时间

如果大邑 12 秒造一个农人（50 谷），消耗速率是 50 / 12 = 4.17 谷/秒。

而一个农人产 0.8 谷/秒。所以：

要维持大邑不停造农人，需要 4.17 / 0.8 ≈ 5.2 个农人在种田。

这是一个非常有用的结论：它告诉你"几个农人算够"。5 个农人 + 1 个造兵的建筑，就是经济饱和点；再多农人，谷会溢出，应该转去采木石玉。

同理，如果族兵 60 谷 / 18 秒，消耗速率 3.33 谷/秒，也需要约 4.2 个农人养着。

11 可读性：让玩家看懂战场

约 2 千字 · 阅读约 7 分钟 · 8 项清单

RTS 真正的难点不是"做出来"，是"看得懂"

即时战略的信息量是所有类型里最大的：

  • 你有多少资源、多少人口、多少兵。
  • 每个兵在哪、在打谁、还剩多少血。
  • 敌人在哪、在干什么、有没有来偷家。
  • 你现在选中的是谁、能下什么指令。

玩家每秒钟只能处理少量信息。 你的工作不是把所有信息都画出来，是决定"什么时候给他看什么"。

信息分三层

层级内容显示时机
常驻四资源 + 德望、人口、小地图、选中数量永远
选中时单位头像/名称、血条、可用指令、编组有选中
按需详细数值、建筑进度、祭祀剩余时间点开面板

现在的 HUD 是一段文本（createHud()，MainScene.ts:151-163），四行字把所有信息塞在一起。单位少的时候能看，单位一多就是灾难。

先做分层，再做美化。 把"常驻"和"选中时"分开，哪怕两边都还是纯文本。

血条：不要一直显示

现在每个单位头顶有一个 30×4 的血条（createUnit() L102），永远显示。

3 个单位时没问题，100 个单位时：

  • 100 条血条 = 视觉噪音，玩家反而看不清战场。
  • 每条血条都是一个 GameObject，渲染开销不大，但屏幕会花。

规则：

  • 满血 + 未选中 → 不显示。
  • 受伤 → 显示，颜色随血量变（绿 → 黄 → 红）。
  • 选中 → 显示，不管满不满。
  • 死亡 → 血条立刻消失（syncViews 的删除分支，第 03 章）。

血条宽度不要按像素写死 30，按单位尺寸比例算。手机上看，4px 高的血条在 DPR 2 下等于 8 物理像素，够用；再细就看不清。

选中反馈：圈 + 地面标记

选中圈现在的做法是 36×36 的描边矩形（createUnit() L100），能用，但有两个问题：

  • 单位重叠时，圈也重叠，分不清选中了谁。
  • 圈的颜色（0x7ef2c8）和单位颜色（0x4dabf7）对比度不够。

改进：

  • 圈用椭圆（俯视角看地面），比矩形更像"站在地上"。
  • 选中的单位脚下加一个半透明圆底，多个单位重叠时也能看出范围。
  • 敌方/己方用不同的圈形（己方实线、敌方虚线/双线），不要只靠颜色——色盲玩家分不清。

指令反馈：让玩家知道"命令收到了"

RTS 里最让人焦虑的是"我点了，但它没动"。

三类反馈，按优先级：

  1. 落点标记：点地面移动后，目标点出现一个 0.4 秒的收缩圆圈。这是最低成本的"收到了"。
  2. 路径预览：只对 1-2 个单位显示 0.3 秒的细线，队伍多了不显示（会糊成一片）。
  3. 失败提示：目标不可达时，单位头顶冒一个"×"或短促的红色闪烁，同时 HUD 出一行"无法到达"。

不要做：屏幕震动、全屏闪光、长音效。RTS 一局几百次指令，任何强反馈都会变成骚扰。

镜头：手机上不要抄桌面

桌面 RTS 的镜头习惯在手机上几乎全废：

滚轮缩放双指捏合标准手势
空格回基地双击基地按钮 / 小地图点基地没有键盘
惯性滑动不要做RTS 需要对位，惯性会让"停在这里"变成"滑过去"
小地图点击跳转保留手指点小地图比拖地图快

默认缩放：现在 cam.zoom 初始是 1（MainScene.ts 没设，Phaser 默认 1），开局只能看到 16×7 格（第 07 章算过）。建议初始 0.7，让视野到 23×10 格。

  • 布局是"左右两侧信息栏 + 中间战场"，手机横屏只有 360 高，两侧栏会把战场压成一条缝。

  • 阵营色 + 形状双重编码。只靠红/蓝区分，色盲玩家（约 8% 男性）会分不清。
  • 地形底色要压暗。现在的地图底色 0x27362b 偏暗，单位 0x4dabf7 亮蓝，对比够；但以后加资源点、建筑，要保证"单位永远比地形亮"。
  • 血条颜色：绿 0x5fdc7a 现在这个值偏亮，在亮地形上会糊。建议加 1px 深色描边。

现在 HUD 是 14px（MainScene.ts:155），在 DPR 2 的手机上物理像素是 28，能看。但：

  • 全屏游戏时，玩家离屏幕更远，14px 偏小。
  • 建议正文 16px，标题 20px，关键数字（资源）24px。
  • 不要用细体（100-300 字重），手机上会发虚。

一个残忍但有效的测试

  1. 能一眼看出哪边在赢吗？
  2. 能看出你的兵在哪吗？
  3. 能看出哪个单位快死了吗？
  4. 能看出你现在选中了什么吗？

如果四个问题有一个答不上来，说明信息层级不够，而不是"美术不好"。

12 性能预算：手机上先崩的是什么

约 2 千字 · 阅读约 7 分钟 · 7 项清单

先建立预算意识

60fps 意味着每帧 16.7ms。这 16.7ms 要分给：

项目预算（经验值）说明
逻辑仿真4ms移动、采集、战斗、寻路
渲染提交8msPhaser 更新显示列表 + WebGL 绘制
输入与 UI1ms触摸事件、HUD 更新
余量3.7ms系统抖动、GC、浏览器开销

任何一项超了，帧率就掉。 你要做的不是"优化代码"，是知道"现在超的是哪一项"。

手机 WebView 里，最先崩的五件事

按发生概率排序，不是按理论重要性。

1. 填充率（fill rate）

屏幕像素 × 每帧重绘次数。手机 DPR 高，800×360 的 CSS 视口，物理像素可能是 2400×1080。如果 Phaser 的 canvas 后备缓冲也按这个尺寸渲染，就是 259 万像素/帧，中端机 GPU 直接跪。

先量清楚你实际在渲染多少像素：

TypeScript
const c = game.canvas;
console.log(c.width, c.height, c.clientWidth, c.clientHeight, devicePixelRatio);
  • c.width === c.clientWidth：你在按 CSS 像素渲染，清晰度一般，但性能最好。
  • c.width === c.clientWidth * 3：你在按 DPR 3 渲染，画面锐利，但填充率是 9 倍。

这是第一个要调的旋钮，也是收益最大的。 经验值：DPR 从 3 降到 2，帧率提升 30-50%；降到 1.5，翻倍。

2. 绘制调用与纹理切换

Phaser 会把同纹理的 Sprite 合批。你现在用 this.add.rectangle（MainScene.ts:100-102），它们共享内置白纹理，能合批——这点比想象中好。

真正会断批的是"每单位一张不同图"。一旦你用 5 张单位图、3 张建筑图、2 张特效图，绘制调用会从 1 次变成 10 次以上。手机上每次 draw call 都有固定开销。

做法：一张图集（atlas）塞下所有单位/建筑/图标，控制在 2048×2048 以内。 一张 2048×2048 的 RGBA 纹理占 16MB 显存，低端机两三张就到顶。

drawMap() 里的 Graphics（L68）是独立绘制，但它只画一次，静态对象不参与每帧重建，可以接受。不要每帧 graphics.clear() 再重画地图，那会变成每帧重新三角化。

3. 每帧分配对象（GC）

下面这些写法在桌面没事，在手机上会周期性卡顿：

TypeScript
// 每帧 new 一个 Vector2
const v = new Phaser.Math.Vector2(x, y);

// 每帧创建数组
const targets = Array.from(this.selected);

// 每帧创建闭包
units.forEach(u => this.doSomething(u));

JS 引擎的 GC 在移动端更保守，堆一涨就会触发停顿。规则：更新循环里不 new 对象、不建数组、不建闭包。 用复用的临时变量和 for 循环。

你现在的 updateUnits()（L246-264）没有分配对象，这点是对的。commandMove() 里的 Array.from 是玩家点击时才调用，频率低，可以保留。

4. 文本重渲染

Phaser.GameObjects.Text 每次 setText() 都会把文字重新画到一张 canvas 纹理上，再上传 GPU。这是最贵的 UI 操作之一。

现在 refreshHud()（L165-172）只在选择变化时调用，没问题。但如果你做了"资源每秒刷新"，而且每秒 setText 4 次，就会开始掉帧。

做法：

  • 数字变化时才 setText，不要每帧设。
  • 资源数字用位图字体（BitmapText），比 Text 快一个量级。
  • 不要把整段 HUD 拼成一个长字符串每帧更新。

5. 寻路尖峰

第 06 章算过：一次 A* 0.1-0.5ms，20 个单位同帧寻路就是 2-10ms。这不会让"平均帧率"下降，但会让你看到明显的卡顿尖峰。

必须分帧：每逻辑帧最多算 2 条路径，其余排队。玩家感知不到 0.5 秒的延迟，但能感知到 50ms 的卡顿。

对象池：不要频繁创建销毁

子弹、飘字、选中标记、死亡特效，这些东西如果"用一次建一个、用完销毁"，会产生两个问题：

  • 创建/销毁本身有成本（尤其是 GameObject，要注册到显示列表、分配纹理帧）。
  • GC 压力。

对象池就是"提前建 50 个，隐藏起来，用的时候取一个、用完还回去"：

TypeScript
class Pool<T> {
  private free: T[] = [];
  constructor(private create: () => T, private reset: (o: T) => void, size: number) {
    for (let i = 0; i < size; i++) this.free.push(create());
  }
  get(): T { return this.free.pop() ?? this.create(); }
  put(o: T) { this.reset(o); this.free.push(o); }
}

什么时候需要：每秒创建 > 10 个的对象。什么时候不需要：单位（数量稳定，创建频率低）。不要为了"架构好看"给所有东西上池子。

空间分区：单位多了才需要

第 07 章说过：100 单位以内，暴力遍历范围查询完全够。超过 300，且每帧都在索敌，才需要均匀网格。

不要提前上四叉树。 四叉树的插入/删除成本在"单位一直在动"的场景里反而更高。

降级阶梯

不要等玩家骂"卡"才降级。做一个自动检测：连续 3 秒低于目标帧率，就降一档。

档位措施触发条件画质代价
0全开：DPR 2、粒子、阴影、60fps默认——
1DPR 1.5，关粒子连续 3s < 50fps轻微模糊
2DPR 1.5，30fps，关阴影连续 3s < 40fps明显但可玩
3DPR 1，30fps，单位上限 80连续 3s < 28fps明显降级
TypeScript
// 检测
if (game.loop.actualFps < target * 0.8) lowFpsFrames++;
else lowFpsFrames = 0;

if (lowFpsFrames > 180) {   // 3 秒
  applyQuality(nextQualityDown());
  lowFpsFrames = 0;
}

低端机的判定不要靠机型白名单，靠实测帧率。机型太多，维护不过来。

发热与耗电

这一条对"长时间对局"很关键，但最容易被忽略。

  • 60fps 持续渲染 + 高 DPR，手机 10 分钟内就会温热，20 分钟后可能触发降频（SoC 自我保护），帧率反而更差。
  • WebView 的耗电通常比原生高（经验值，具体差异取决于场景），因为多了一层合成。
  • 对策：给一个"省电模式"，锁 30fps + DPR 1.5。 对 RTS 来说 30fps 完全可玩，因为单位移动不是高速动作。

测耗电：

Shell
adb shell dumpsys batterystats --reset
# 玩 10 分钟
adb shell dumpsys batterystats | findstr "com.your.package"

怎么测，不要靠感觉

  1. 帧率叠加层：在场景里加一个 Text，每 30 帧更新 game.loop.actualFps，放在角落。发布前关掉。
  2. Chrome Remote DevTools：chrome://inspect → Performance → 录 10 秒 → 看火焰图。你能看到是 update 慢、render 慢，还是 GC 慢。
  3. 长任务：Performance 面板里找 > 16ms 的任务。一次 A* 尖峰、一次 setText、一次大量创建对象，都会在这里露出来。
  4. 真机，不要模拟器。模拟器的 GPU 是桌面显卡，帧率没有参考价值。

一个现实的性能目标

基于你的玩法（正交 2D、方块/矢量图形、无 3D、无大量粒子），我给一组推测值：

机型档位目标单位数目标帧率前提
旗舰（2024+）20060DPR 2、图集、对象池、流场

自检

一句话总结

先测，再猜，最后才优化。 手机上 90% 的"卡"来自填充率和 GC，不是来自你的算法。

14 签名、发布与分发

约 2 千字 · 阅读约 6 分钟 · 17 项清单

这一章解决什么

你已经有一个能装的 debug 包。现在要把它变成"能给朋友装、能覆盖升级、签名不会丢"的 release 包。

四件事：签名、版本号、图标/包名、分发方式。

包名：定了就不能改

appId（com.likang.rtsmini）是应用的身份。Android 用它区分"这是同一个应用"还是"另一个应用"。

  • 改了包名 → 手机上会装出两个图标，旧数据不共享。
  • 上架后更不能改。
  • 命名用反向域名：com.你的域名.项目名。没有域名就用 com.你的名字.项目名，但要注意可能和别人撞。

在第一次发给别人之前，把包名想清楚。 之后不要动。

版本号：两个字段，各管一件事

Gradle
// android/app/build.gradle
android {
    defaultConfig {
        applicationId "com.likang.rtsmini"
        minSdkVersion 24
        targetSdkVersion 36
        versionCode 1          // 整数，只能递增，Android 用它判断"哪个更新"
        versionName "0.1.0"    // 给人看的
    }
}

规则：

  • versionCode 每次发版 +1，不能回退。回退会导致新包装不上旧包。
  • versionName 用语义化版本：0.1.0 → 0.1.1（修 bug）→ 0.2.0（加功能）→ 1.0.0（正式）。
  • 一个可维护的换算：versionCode = major * 10000 + minor * 100 + patch。0.2.3 → 203。

每次发版前检查 versionCode。 忘了加，手机会提示"应用未安装"或"版本降级"。

  • 每个版本一个 tag，历史可查。
  • 缺点：国内下载可能慢。

把 APK 放在 GitHub Pages（你已经有 docs/ui/index.html 的经验），做一个简单下载页 + 更新日志。适合"给一小群人玩"。

不要做的：把 APK 提交进 git 仓库。二进制文件会让仓库迅速膨胀，而且每次更新都留一份历史。

更新策略

手动更新（推荐首版）

  1. 改 versionCode +1，versionName 递增。
  2. 打 release 包。
  3. 发给玩家，覆盖安装。
  4. 数据（localStorage）会保留，因为包名和签名没变。

热更新（不建议）

Capacitor 支持 server.url 指向远程，或用第三方 live update 插件替换 Web 资源。听起来很爽，但：

  • 远程挂了，游戏直接打不开。
  • 你等于在运行时执行任意 JS，安全风险自己承担。
  • 调试链路变复杂（"我改了怎么没生效"）。

首版不要做。 重新打包 30 秒的事，不值得引入一个运行时依赖。

package.json 里只有 dev、build、preview，没有测试框架，没有测试文件。build 只做 tsc --noEmit（类型检查）+ vite build，它能抓语法和类型错误，抓不到"农人采完木头卡在原地"。

RTS 的 bug 有两个特点：复现难、连锁反应多。改一个移动速度，可能让采集回环慢 20%，进而让祭坛晚 1 分钟，进而让整局节奏崩掉。靠手玩很难发现。

第一层：纯逻辑单测

前提是第 03 章的分层做了：src/game 不依赖 Phaser、不依赖 window。做到了，就能在 Node 里跑。

装 vitest：

Shell
npm i -D vitest

  "dev": "vite",
  "build": "tsc --noEmit && vite build",
  "test": "vitest run",

该测什么

不要追求覆盖率，测这五类：

  1. A*：直线可达、绕墙、不可达、斜角禁止穿墙。
  2. 伤害公式：减法护甲、最低 1 点。
  3. 目标点分配：12 个单位分 12 个槽位，不重复、不落在阻挡格。
  4. 采集回环：一个完整周期后资源增加准确值。
  5. 状态哈希：同样输入跑两遍，哈希一致（下面详述）。

例：

TypeScript
// src/game/sim/__tests__/gather.test.ts
import { describe, it, expect } from 'vitest';
import { createGame } from '../createGame';
import { step } from '../step';

describe('采集回环', () => {
  it('农人采一趟木，资源准确 +10', () => {
    const state = createGame({ seed: 1 });
    // 把农人放到林地旁边，省掉走路时间
    state.units[0].x = 400; state.units[0].y = 400;

    state.units[0].order = { kind: 'gather', nodeId: 1 };

第二层：可重放对局

这是 RTS 最有价值的测试手段，也是第 02 章确定性的回报。

记录什么

TypeScript
interface Replay {
  version: number;        // 数值表版本，改过就不兼容
  seed: number;           // PRNG 种子
  commands: Array<{
    tick: number;
    player: 0 | 1;
    type: 'move' | 'attack' | 'gather' | 'build' | 'train';
    payload: unknown;
  }>;
  /** 每 60 帧一个状态哈希，用来定位分叉 */
  checkpoints: Array<{ tick: number; hash: number }>;
}

只记录指令，不记录结果。 位置、血量、资源都是由指令 + 种子推出来的。这是 lockstep 的基础，也是"回放文件只有几 KB"的原因。

状态哈希

TypeScript
function hashState(s: GameState): number {
  let h = 0x811c9dc5;                       // FNV-1a
  const mix = (n: number) => {
    h ^= n & 0xff; h = Math.imul(h, 0x01000193);
    h ^= (n >>> 8) & 0xff; h = Math.imul(h, 0x01000193);
    h ^= (n >>> 16) & 0xff; h = Math.imul(h, 0x01000193);
    h ^= (n >>> 24) & 0xff; h = Math.imul(h, 0x01000193);
  };

  mix(s.tick);
  mix(s.units.length);
  for (const u of s.units) {                // 必须按 id 升序
    mix(u.id);
    mix(Math.round(u.x * 1000));            // 量化到千分之一像素
    mix(Math.round(u.y * 1000));
    mix(u.hp);
  }
  mix(s.resources.grain);
  mix(s.resources.wood);
  mix(s.resources.stone);
  mix(s.resources.jade);
  mix(s.legitimacy);
  return h >>> 0;
}

三个细节：

  • 按 id 升序，不能依赖数组当前顺序。
  • 量化浮点。Math.round(x * 1000) 把 0.0001 的差异过滤掉，否则你会被正常的浮点抖动淹没。
  • 包含所有影响玩法的状态：资源、德望、人口、冷却、目标 id。漏一个，哈希就测不出那部分的 bug。

怎么用

TypeScript
// 录制时
replay.checkpoints.push({ tick: state.tick, hash: hashState(state) });

// 重放时
for (let i = 0; i < replay.checkpoints.length; i++) {
  const expected = replay.checkpoints[i];
  while (state.tick < expected.tick) step(state, 1 / 60);
  if (hashState(state) !== expected.hash) {
    throw new Error(`分叉于 tick ${expected.tick}`);
  }
}

分叉帧就是 bug 的位置。 比"我玩的时候感觉不对"精确一百倍。

什么时候会分叉

  • 用了 Math.random() 或 Date.now()。
  • 用了 Math.sin/cos/atan2（跨引擎最后一位可能不同）。
  • 遍历顺序依赖 Map/对象键顺序。
  • 浮点累加顺序变了（比如把两段循环合并）。
  • 渲染层偷偷改了逻辑状态（比如 body.x 就是逻辑坐标，第 03 章那条）。

第三层：真机清单

纯逻辑测不到触摸、渲染、性能、安全区。每次发版前，在真机上过一遍：

最小可玩循环：怎么定义

不要用"感觉差不多了"判断。用一条可观测的链路：

选中农人 → 采集一种资源 → 造一个建筑 → 造一个兵 → 打掉一个敌方单位 → 出现胜利/失败提示。

这条链路能在 10 分钟内走完，且不需要重启，就算"能玩了"。

五个验收标准：

  1. 闭环：上面六个动作全部可完成，没有死路。
  2. 时长：一局 8-12 分钟（DESIGN-v2.md:10.2 的 M2 验收是 10-15 分钟，首版可以短一点）。
  3. 反馈：每个动作 0.1-0.4 秒内有可见反馈（第 11 章）。
  4. 稳定：连续三局不崩、不卡死。
  5. 可解释：你能说清"我为什么输/赢"，而不是"不知道怎么就结束了"。

性能回归测试

不需要自动化工具，做一个手动基线：

  1. 固定场景：100 个单位，全部移动，10 秒。
  2. 记录：game.loop.actualFps 的平均值。
  3. 每次改动后重跑，掉超过 15% 就查。

把这个数字写在 docs/guide 或 commit message 里，形成历史。没有基线，"变卡了"只是感觉。

如果仓库在 GitHub，加一个最简 workflow：

如果决定换引擎

按第 00 章的闸门，只有满足条件才换。换的时候：

  1. 冻结玩法：不改规则，只做移植。
  2. 带走数据表：src/game/data/*.ts 导出成 JSON，Godot 直接读。
  3. 带走逻辑：src/game/sim/* 按 1:1 重写成 GDScript（状态机、A*、伤害公式都是语言无关的）。
  4. 重写表现：Godot 的 Node2D + Control，不要试图复刻 Phaser 的 Scene 结构。
  5. 先跑通一条链路：选中 → 移动 → 采集，再谈战斗。

不要"边移植边加功能"。 那是两个项目叠在一起，一定烂尾。
