怎么用这本书

这不是一本软件说明书。它想解决的是：面对同一个界面，为什么老练的设计师会选 A 而不是 B，以及这个选择在什么条件下会失效。

全书有一条主线：界面是玩家做决策的场所，不是信息的陈列柜。所有章节都在回答三个问题——玩家此刻要做什么决定、这个决定需要哪些信息、这些信息用什么代价送到他眼前。工具、动效、切图、引擎，都是为这条主线服务的。

三条阅读路径

你现在的状态读什么读完能得到

有一个周末01–04、06、09、12能独立重做一版可上手机的 HUD，知道每一步的交付物
准备长期投入全书 + 第 14 章练习能建立设计系统、定验收标准、在引擎里控制 UI 成本

四种标记

正文里会出现四种固定块，含义如下：

  • 为什么这样做：解释取舍的因果，而不是规范条文。如果因果不成立，规范就该改。
  • 常见错误：真实项目里反复出现的坏做法，通常不是审美问题，而是流程问题。
  • 实测：来自本仓库 docs/ui/ 的可复现数据。数字可以被你重新测量。
  • 个人经验：没有权威来源、只来自实践判断的部分，会明确标出来。你可以不同意。

三个约定

  1. 尺寸用 dp，不用 px。设计稿上的 1920×1080 是像素，手机上的 640×360 是 dp。两者混用是本书要反复纠正的第一个错误。
  2. 所有“应该”都尽量给出可观测的判断标准。“更清晰”不是标准，“缩到 50% 仍能在 0.5 秒内认出三个资源数值”才是。
  3. 不追求一次做对。UI 是迭代出来的，本书给的是每一轮的检查项，不是终稿。
为什么这样做

游戏 UI 的失败往往不在“画得不好看”，而在“决策链断了”：玩家不知道现在能做什么、刚发生了什么、下一步该点哪里。把评价标准从“美观”换成“决策是否顺畅”，学习路径才会收敛。

常见错误

把这本书当灵感图册，跳过前八章直接看工具和第 12 章。工具决定的是效率上限，判断决定的是方向；方向错了，工具越熟练，返工越快。

01

游戏 UI 与平面设计的七处分歧

很多游戏 UI 看起来“像网页”或“像海报”，不是因为美术差，而是因为把另一套媒介的评价标准搬了过来。先把分歧说清楚，后面的规范才有依据。

1.1 用户不是读者，是操作者

读者可以停下来回看，玩家不能。RTS 里一秒钟可能同时发生交火、采集、建造、人口卡满四件事，玩家的视线在战场与 HUD 之间来回跳。平面设计追求“读进去”，游戏 UI 追求“扫一眼就能做下一个动作”。这决定了两件事：文字必须短，结构必须稳。

一个可操作的检验：把界面截图给没玩过的人看 3 秒，然后遮住，问他“你现在能做什么”。答不出来，说明可操作性没有外显。

1.2 三个读速：0.2 秒、2 秒、10 秒

界面上的信息不是同一等级，它们对应三种读速：

读速玩家在找什么典型元素设计手段
0.2–0.5s“我现在有多少、安不安全”资源、人口、德望、警报、选中单位固定位置、形状稳定、数字等宽、颜色只做辅助
1–2s“我该下什么命令”命令按钮、建造项、目标信息分组、图标语义、可用/不可用对比、冷却可见
10s+“这局该怎么打”科技树、说明、战报、图鉴可展开、可搜索、允许长文本

常见错误是把 10 秒信息塞进 0.2 秒区域。比如在资源栏旁边放一行小字解释“德望影响受禅”，玩家既读不完，又挤掉了数值本身。

1.3 静态图只是状态之一

平面设计的交付物是一张成品；游戏 UI 的交付物是一个状态集合。同一个按钮至少有默认、按下、禁用、资源不足、冷却中、选中六种状态，这还没算长按、拖拽、多选。只画一张“正常态”的高保真稿，等于只交付了六分之一。

更麻烦的是组合态：一个按钮可以同时“选中 + 冷却 + 资源不足”。如果没有定义状态维度，而是每个组合画一张图，维护成本会指数上升。第 4 章会给状态机的做法。

1.4 UI 是负空间，不是画面主角

在网页里，内容区越大越好；在 RTS 里，战场才是内容，HUD 是必须付的税。手机屏幕只有 640×360dp 左右的可视面积，底部一条 100dp 的指令区就吃掉了 28% 的高度。玩家真正用来观察战场的面积，是被 UI 挤剩下的部分。

所以评价 HUD 的第一指标不是“信息全不全”，而是“在信息够用的前提下，占了多少战场”。桌面端常驻 HUD 建议不超过 28%，手机不超过 22%，这是经验值，不是定律；但超过之后，战场可读性会明显下降。

1.5 输入方式决定界面形态

键鼠有 hover、右键、快捷键、精确指向；触屏只有一根手指、一块被手指遮住的区域，以及有限的手势。把桌面 RTS 的 24×24 小按钮直接搬到手机上，不是“缩小”，是“失效”：视觉上还在，物理上点不中。

这带来一个连锁反应：触屏 UI 必须减少同屏可点元素、增大命中区、把低频功能收进二级。信息架构不改，只改尺寸，最后一定是“按钮太大放不下”。

1.6 失败的代价不对称

网页上误点一个链接，退回来就行；RTS 里误点“解散部队”或“献祭祭司”，可能直接输掉一局。因此游戏 UI 对危险操作的容错要求远高于一般软件：二次确认、长按、滑动解锁、可撤销，至少要有一样。反过来，高频操作要尽可能零阻力，不能每次造农人都弹确认框。

判断依据是“频率 × 后果”：高频低后果要快，低频高后果要慢。第 2 章会把这张矩阵展开。

1.7 交付物是运行时系统

设计稿通过评审，只完成了 30%。剩下的 70% 在引擎里：九宫格拉伸会不会变形、字体子集有没有缺字、半透明遮罩在低端机上掉不掉帧、安全区有没有避开挖孔。一个不会看引擎实现的设计稿，不能算完成。

同一件事，两套评价标准
维度平面 / 网页设计游戏 UI

为什么这样做

这七处分歧最终都指向同一个结论：游戏 UI 的设计对象不是“画面”，而是“玩家在时间压力下的注意力分配”。谁在什么时候需要看到什么、以多快速度看到、看到后能做什么，这三件事决定了布局、颜色、尺寸和动效。先有这三问，再谈风格。

常见错误

把“高级感”理解成低对比、大留白、细字重。这套语言在杂志和品牌站成立，在战场背景上会直接失效：低对比文字被地形吃掉，大留白让 HUD 吃掉战场，细字重在 5 英寸屏上糊成一片。另一个高频错误是先做视觉、后补交互，导致所有状态都靠“再加一个弹窗”解决。

02

信息架构：先决定什么不该显示

RTS 是最容易信息过载的类型：经济、军事、侦察、科技四条线并行，每条都在产生数字。好的 HUD 不是把所有数字摆出来，而是让玩家在正确的时刻只看到该看的那几个。

2.1 先列决策，再列信息

不要从“资源栏要显示谷、木、石、玉”开始，而要从“玩家每分钟要做哪些决定”开始。以本作为例，列出高频决策：

决策需要的信息频率后果归属
要不要再造一个农人谷余量、人口、农人数、田数高中常驻资源栏 + 人口
现在能不能升铜铜前置、资源缺口、德望中高建造菜单内联缺口
部队要不要撤敌我数量、兵种、地形、血量高高战场 + 选中面板
祭坛要不要开祭司数、德望增速、敌方压力低高情境面板 + 警报
下一个伐木场放哪树林分布、现有伐木场、路径中中建造预览 + 小地图

这张表会直接告诉你：哪些信息必须常驻，哪些可以情境出现，哪些根本不用显示。它也是后面所有布局争论的裁决依据——如果两个人对某个数字放哪里意见不同，回到“它服务哪个决策、频率多高”。

2.2 频率 × 后果矩阵

矩阵的用法不是分类，而是决定打断成本。右上角的信息不打断玩家，只占一个稳定位置；左下角的信息必须打断，因为错过一次可能输掉整局。真正危险的是把左下角做成“安静的小图标”：基地正在被拆，玩家却在专心种田。

2.3 三层信息

界面上的每个元素都可以归入三层之一：

  1. 决策层：现在能做什么、还差什么。资源、冷却、人口、可用命令。
  2. 确认层：我刚做了什么、系统收到了吗。选中高亮、命令确认、生产队列、飘字。
  3. 叙事层：世界在发生什么。德望变化、祭坛光效、胜利仪式、敌方动向。

三层不能互相挤占。常见的坏例子是用叙事层的方式做决策层：把“资源不足”做成一段缓慢淡入的书法提示，玩家已经点了三次按钮，提示还没出来。反过来，用决策层的方式做叙事层，会让整个世界像仪表盘，赢了一局只有一行“胜利”。

2.4 画一张界面地图

在画任何视觉稿之前，先画界面地图：把游戏循环里的状态列出来，标出每个状态需要哪些输入、产生哪些输出、能跳到哪些状态。RTS 的典型状态是：探索、建造、交战、防守、升级、暂停、结算。

地图会暴露两类问题：一是同一信息在多个状态重复出现，可以合并；二是某个状态没有出口，比如“建造中”没有取消入口，“单位被卡住”没有提示。这些问题在视觉稿阶段几乎发现不了，因为视觉稿只画了正常流程。

2.5 渐进披露：先给三个，再给全部

建造菜单是最典型的例子。本作有住房、农田、伐木场、采石场、祭坛、图腾、射庐等建筑，如果一次全铺开，玩家在战斗中根本找不到“造个射庐”。渐进披露的做法是：

  • 第一层只给当前最可能的 3–4 个，按局势动态排序；
  • 第二层按经济 / 军事 / 信仰分组，组内再排序；
  • 第三层才是完整列表和图鉴。

排序依据不是“设计者觉得重要”，而是玩家上一分钟做了什么。刚造完农田，下一个最可能是住房或第二个农田；刚被弓手射了一轮，下一个最可能是射庐或族兵。这需要程序提供上下文，不是纯设计问题。

2.6 HUD 面积预算

把屏幕上被 UI 永久占用的面积算出来，作为硬预算。以 640×360dp 为例：

640×360手机横屏逻辑画布（dp）
≤ 22%常驻 HUD 面积上限（经验值）
≤ 50,688dp²，约等于 140×360 的侧栏
≥ 78%留给战场的最低比例

本仓库 A 稿的底栏是 300px / 1080px = 27.8%，在桌面端勉强合格，但它是一张 1920 固定稿，缩到手机后并不是“按比例变小”，而是被裁切或整体缩放，实际可读性另算（第 12 章会算）。

预算不是让你死抠百分比，而是给争论一个共同的尺子。当有人要求“再加一条状态栏”，先问：它要从战场面积里扣，还是从已有信息里替换？

2.7 警报分级

RTS 的警报不是一种东西。至少分三级：

级别触发表现是否打断
致命主城被攻击、单位正在死亡、人口卡死屏幕边缘红脉冲 + 短促音 + 小地图定位点是，但只提示不夺走操作
重要资源满、人口接近上限、建造完成对应资源图标脉冲 + 轻音否，局部提示
提示新单位空闲、科技可升级图标角标 + 侧边小点否，可忽略

分级的难点不是表现，而是去重。基地被十个单位围攻，不应该响十次；应该合并成一条“主城遇袭 ×10”，并在威胁解除后自动消失。没有去重的警报系统，玩家三天就会关掉声音。

为什么这样做

RTS 的注意力是零和的：玩家看小地图的时间，就是没看战场的时间。信息架构的本质是分配注意力，而不是分配像素。频率×后果决定“是否常驻”，三层信息决定“用什么语气”，渐进披露决定“什么时候给”，面积预算决定“最多占多少”。这四件事定完，布局几乎是自然结果。

常见错误

把所有系统都挂在主界面。典型症状是顶部一排资源、左侧一列任务、右侧一列科技、底部一整块指令，最后战场只剩中间一个小窗。另一个错误是“信息对称”：敌方和我方的所有数值都显示，结果玩家被无用的精确数字淹没。RTS 需要的是可比较的差异，不是全量数据。

03

视觉层级与颜色语义

层级不是“把重要的东西放大”，而是让玩家在正确的顺序里看到东西。颜色不是装饰，是一套需要被记忆的语法；语法一旦混乱，玩家就会停止相信它。

3.1 层级手段的排序

可用的层级手段有六种，按“不依赖颜色也能成立”的顺序排列：

  1. 位置：固定位置本身就是最强提示。资源永远在左上，玩家不需要找。
  2. 尺寸：大一号就重要一号，但会挤占空间，不能无限用。
  3. 明度：暗背景上提亮，比加饱和色更稳，也不容易被色盲削弱。
  4. 颜色：最快的区分手段，但最容易被滥用，且受色觉和屏幕影响。
  5. 字重：中文在小字号下字重差异有限，只能做辅助。
  6. 装饰：边框、发光、纹理。信息量最低，最容易变成噪音。

这个排序有一个直接推论：如果一个元素只能靠颜色区分，它在强光下、色盲玩家眼里、低端屏上就会消失。所以敌我必须同时用轮廓、朝向、底座形状或头顶标记来区分，颜色只是加速器。

3.2 暗色界面不是把亮色反过来

把浅色稿反相，会得到一堆发灰的中间调和刺眼的高亮。暗色界面的正确做法是建立“明度台阶”，让不同层级的表面有稳定的亮度差：

层用途相对亮度（参考）说明
背景战场、空白区6–9%不要纯黑，纯黑会让阴影和描边失去层次
面板HUD 底板11–14%与背景保持约 1.4:1 的分离即可
浮层弹窗、tooltip16–20%靠明度而不是重阴影区分
分隔线边、槽22–28%非文本对比 ≥3:1 才可靠
次级文字标签、单位55–65%仍需 ≥4.5:1
主文字数值、命令88–94%不要用纯白，减少眩光

暗色界面的另一个陷阱是“发光补偿”：因为整体暗，设计师会不断给元素加外发光，最后每个东西都在发光，等于没有层级。发光只应该给一个元素，而且通常是当前最重要的那一个。

3.3 对比度是可以算的

WCAG 的相对亮度公式不复杂，浏览器里几行代码就能算。与其争论“这个灰能不能看清”，不如直接量：

function luminance(hex) {
  const c = hex.replace('#','').match(/../g).map(h => {
    const v = parseInt(h, 16) / 255;
    return v <= 0.03928 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);
  });
  return 0.2126 * c[0] + 0.7152 * c[1] + 0.0722 * c[2];
}
function contrast(a, b) {
  const l1 = luminance(a), l2 = luminance(b);
  return (Math.max(l1, l2) + 0.05) / (Math.min(l1, l2) + 0.05);
}
contrast('#6E6957', '#26271D'); // 2.75

正文目标 4.5:1，大字号（≥18.66px 粗体或 ≥24px）3:1，非文本 UI 边界 3:1。这三条不是“无障碍加分项”，而是强光下能不能玩的下限。

实测

对 docs/ui/ui-a.html 的现有配色计算：次级文字 #6E6957 在面板底色 #26271D 上只有 2.75:1；危险色 #9E3B32 在同底色上 2.25:1；较亮的 #D0695A 为 4.21:1；玉青 #7B9E8E 为 5.13:1。也就是说，现有稿里最需要被看见的“危险”和“说明”，恰好是最看不清的两类。

3.4 颜色要有语义表

颜色只有在“一色一义”时才能被学习。给每个颜色写清楚它允许出现在哪里、不允许出现在哪里，比调色板本身重要：

颜色唯一语义允许禁止
朱砂敌方 / 正在发生的伤害敌方单位、受击、基地警报普通按钮、资源不足、装饰印章
玉青我方 / 可交互友军、可建造、选中描边玉资源、天气、普通文本
土黄资源 / 德望数值、货币图标、进度按钮描边、标题装饰
石灰禁用 / 不足不可用命令、缺口、次要说明任何需要被读到的正文

现稿的问题是语义过载：朱砂同时表示敌方、资源不足、危险、印章红；玉青同时表示友军、玉资源、可建造、天气。玩家会形成错误预期——看到红色以为被攻击，其实只是谷不够。修复不需要换色，只需要拆分别名：印章红退到装饰层并降低饱和，资源不足改用“灰 + 数字差值 + 图标角标”。

3.5 双通道编码

任何靠颜色传达的信息，都必须再给一个非颜色通道：

  • 敌我：颜色 + 底座形状（圆/方）+ 朝向；
  • 血量：颜色 + 条长 + 数值；
  • 可建造：颜色 + 边框样式 + 缺口数字；
  • 警报：颜色 + 图标 + 位置（屏幕边缘）+ 声音。

这不是为了“照顾少数人”，而是为了让信息在战场高噪音背景上仍然成立。颜色在动态背景前最不可靠，形状和位置最可靠。

3.6 图标语言

图标是 RTS 的第二语言。一套图标要能被“读”而不是被“猜”，需要三个约束：

  1. 同一网格：24×24 设计网格，主要形状落在 20×20 内，留 2px 光学边距。
  2. 同一描边：2px 为主，圆角 2px；填充图标与线性图标不要混用，除非有明确的层级理由。
  3. 同一隐喻系统：谷用穗，木用树干截面，石用块面，玉用环；一旦确定，不要为了“好看”换隐喻。

图标里不要放文字。中文两个字在 24px 里几乎不可读，本地化后更糟。需要文字时，把文字放在图标外侧，并允许换行。

为什么这样做

玩家的视觉系统对“位置”和“形状”的编码是并行、低成本的，对“颜色名称”的编码是串行、高成本的。把最重要的信息放在位置和形状上，玩家才能在不中断操作的情况下完成识别。颜色负责加速，不负责承载。

常见错误

用低对比制造“高级感”。暗底上的中灰文字，在设计显示器上勉强能看，在户外或低亮度手机上直接消失。用发光替代层级。每个面板都描边发光，最后玩家不知道看哪。颜色语义随手扩展。今天用红色表示“不可用”，明天用红色表示“新消息”，一周后红色就等于“没有意义”。

04

状态、反馈与动效节奏

静态图回答“长什么样”，状态机回答“什么时候变成什么样”。RTS 的界面几乎一直在变，设计的重点不是某一帧，而是帧与帧之间的因果关系。

4.1 为什么是状态机，不是一堆图

一个命令按钮的真实状态至少有：默认、按下、禁用、资源不足、冷却中、选中、长按预览。如果每个组合都画一张图，七个维度会产生上百张稿，改一个颜色要改上百处。状态机的做法是先定义独立维度，再定义维度如何叠加：

维度取值视觉通道是否阻断点击
可用性可用 / 不可用 / 锁定明度 + 图标灰度 + 角标是
资源足够 / 不足缺口数字 + 石灰描边是
冷却就绪 / 冷却中扇形遮罩 + 剩余秒数是
选中否 / 是外描边 + 轻微抬升否
按压否 / 是内缩 1–2dp + 亮度变化否

叠加规则要写死：冷却遮罩永远在最上层，选中描边永远在最外层，禁用时不显示按压反馈。这样程序只需要按顺序叠层，不需要为每个组合做特判。

4.2 反馈四问

任何一个反馈，都要能回答四个问题，缺一个就会让玩家困惑：

  1. 发生了什么？——选中框、受击闪白、命令确认音。
  2. 对我有利吗？——颜色方向、数值增减、对比参照。
  3. 我能做什么？——可点击的警报、缺口提示、下一步入口。
  4. 多久消失？——自动消退、需要确认、常驻到状态改变。

RTS 里最常见的缺失是第三问：玩家知道“主城被攻击”，但不知道点哪里能回到主城。警报如果不可点击定位，就只是一条噪音。

4.3 时间尺度

反馈的时长不是审美，是感知阈值。参考 Nielsen 关于 0.1s / 1s / 10s 的经典划分，落到游戏 UI 上大致是：

反馈类型目标时长超过会怎样
按压 / 点按确认0–100ms被感知为“没点上”，玩家会重复点击
选中高亮、描边出现100–150ms操作与结果脱节
面板展开、命令盘切换150–250ms战斗节奏被打断
场景转场、结算300–500ms可以慢，但不能阻塞输入
叙事演出、胜利仪式800ms+只在安全节点使用

关键规则：动画可以慢，输入响应不能慢。面板用 250ms 展开没问题，但点击必须在 100ms 内被确认；动画期间要允许玩家继续操作，或者明确显示“不可操作”。

4.4 缓动与节奏

RTS 的动效应“短、稳、可预期”。进入用 ease-out（快起慢停），退出用 ease-in（慢起快走），位移统一用接近 cubic-bezier(.2,0,.2,1) 的曲线。不要在战术界面用回弹（bounce）和果冻效果：它们会让玩家误以为操作失败或单位被击退。

同屏持续动画不超过三个。资源脉冲、警报闪烁、单位待机动作、天气粒子，如果全都在动，玩家会失去对“异常”的敏感度。战斗特效的优先级高于 UI 动效，UI 应该在交火时主动安静下来。

4.5 危险操作要慢

“解散部队”“献祭祭司”“放弃城池”这类操作，不能和“造农人”用同一种交互。可用的手段：

  • 长按 500ms 确认，进度环可见、可取消；
  • 滑动解锁，方向与后果相关（向左滑 = 放弃）；
  • 二次确认，但只对真正不可逆的操作使用，避免确认疲劳；
  • 撤销窗口 3–5 秒，适合可回滚的操作。

选择依据是“可逆性”。可逆操作给撤销，不可逆操作给阻力。不要给所有操作都加确认框，那会让高频操作变得难以忍受。

为什么这样做

状态机把“画多少张图”变成了“定义多少个维度”，维护成本从乘法变成加法。反馈四问保证每个动效都有信息职责，而不是装饰。时间尺度则把主观的“顺滑”拆成可测的阈值：100ms 内确认，250ms 内完成面板切换，超过就必须给等待指示。

常见错误

所有东西都弹一下。按钮弹、面板弹、数字弹，最后玩家对动效脱敏，真正重要的警报也被忽略。用动画掩盖信息缺失。不知道资源为什么不够，就加一个“摇晃”动画；玩家还是不知道为什么。动效阻塞输入。胜利面板用 1.2 秒飞入，期间无法点击“再来一局”，玩家只会觉得卡。

05

数字、字体与图标

RTS 玩家读得最多的不是句子，是数字。资源从 48 变成 49 的那一下，信息量比一整段说明都大。数字排版做不好，其他部分再精致也会显得不专业。

5.1 数字必须等宽

比例字体里，1 比 8 窄。资源每秒都在变，数字宽度一跳，整行就会抖动，玩家的眼睛会被迫重新定位。解决方法是等宽数字：

.resource-value {
  font-variant-numeric: tabular-nums;
  font-feature-settings: "tnum" 1;
  min-width: 4ch;          /* 预留最大值宽度，避免布局跳动 */
  text-align: right;
}

除了等宽，还要预留位宽。谷从 99 涨到 100 时，如果容器按内容自适应，整条资源栏会向右挤。正确做法是给每项资源一个固定的最小宽度，按该资源可能出现的最大位数设计。

5.2 数值变化怎么表现

数值变化至少要传达三件事：变成了多少、变化方向、变化量。常见组合是：

  • 数字滚动：48 → 49，持续 120–180ms，让眼睛跟上；
  • 方向色：增加用玉青，减少用朱砂，但只闪 300ms 就回到主色；
  • 增量飘字：+12 从图标旁向上飘 24dp 后淡出，用于采集、战斗奖励；
  • 缺口提示：不足时直接显示 还差 24，而不是把数字变红。

不要让数字持续闪烁。资源一直在涨，如果每次变化都闪，整个资源栏会变成迪斯科灯。只在“跨越阈值”（如资源满、可升级）时给强提示。

5.3 字体的现实约束

中文字体是 UI 工程里最容易被低估的成本。一个完整的中文字库通常 5–15MB，包含两万多个字形；直接把整包塞进 APK，安装包和内存都会被拖累。实际做法：

  1. 正文用系统字体：Android 上就是 Roboto / Noto Sans CJK，零体积，渲染稳定。
  2. 标题用品牌字，做子集：只保留用到的字，通常几百个，体积降到几十 KB。
  3. 数字用专门的等宽字体或特性：如果品牌字没有 tabular 数字，单独给数字配一个字体。
  4. 动态文本必须能回退：玩家名、聊天、存档名可能包含任何字，字体缺字时要能回退到系统字体，而不是显示方框。

SDF（有向距离场）字体适合大字号和缩放，但细笔画在低分辨率下会发虚；中文的小字号尤其明显。不要把 SDF 当作万能方案，12–14sp 的正文优先用位图字体或系统字体。

5.4 字号阶梯

移动端 RTS 的字号不要超过五档，否则会失去一致性。一个可用的阶梯：

层级字号用途备注
数值16–18sp资源、人口、德望等宽，右对齐
命令14sp按钮标签最多 4 字，超出用图标
正文12–13sp说明、tooltip不低于 12sp
辅助10–11sp单位、时间只用于非关键信息
标题20–28sp面板标题、结算可用品牌字

现稿的最小字号是 9px，正文 10px。在 1920 画布上已经偏小，缩到 800×360 的 CSS 视口后只剩 4.2px 和 3.3px（第 12 章有完整计算）。这不是“风格问题”，是物理上不可读。

5.5 图标与文字的关系

图标负责快速识别，文字负责精确含义。两者不是二选一：

  • 高频、含义固定：图标为主，文字可省略（资源、人口）。
  • 低频、有歧义：图标 + 文字（建造项、科技）。
  • 危险操作：图标 + 文字 + 确认，三者都要。

图标与文字之间留 6–8dp，文字基线不要和图标中心硬对齐，按视觉重心对齐。中文标签不要放在图标内部，本地化后长度不可控。

5.6 图标一致性检查

把全部图标排成一行，眯眼直到看不清细节，问三个问题：

  1. 重量是否一致？有没有几个明显更黑或更空？
  2. 视觉尺寸是否一致？圆形图标通常需要比方形略大，才能看起来一样大。
  3. 隐喻是否在同一层？有没有一个写实、一个几何、一个像 emoji？

任何一项不通过，就先修图标，不要靠加背景板掩盖。

为什么这样做

数字是 RTS 里变化最频繁、最需要被比较的信息。等宽、定位宽、短动效，都是为了让“比较”这件事不消耗注意力。字体的约束则来自安装包和内存的真实成本：中文字库不是免费的，设计阶段就要决定哪些字用品牌字、哪些交给系统。

常见错误

给每个数字都加动画。资源每秒跳十几次，每次都滚动，玩家会晕。用红色表示“资源不足”。红色已经被敌方占用了，应该用灰色 + 缺口数字。所有文字都用品牌字。安装包膨胀、缺字、渲染发虚，三个问题会同时出现。图标里塞两个字。24px 下几乎不可读，本地化后必定溢出。

06

触屏：手指是最差的指针设备

鼠标有一个像素的精度和悬停状态，手指什么都没有：它遮住目标、落点模糊、还会和系统手势抢地盘。把桌面 RTS 的界面等比缩小，得到的不是移动版，是一张点不中的图。

6.1 先量清楚手指

成人拇指指腹的接触面直径约 10–12mm，食指约 8–10mm。按 160dp = 1 英寸换算，1mm 约等于 6.3dp，所以接触面大约是 50–75dp。这个数字常常引起误解：既然手指这么大，为什么 44–48dp 的按钮还能点中？

因为命中判定用的是触点中心，而不是整个接触面；人也会主动把指尖中心对准目标。真正决定成败的不是单个按钮多大，而是相邻目标有多近，以及按下之后手指遮住了什么。

9–12mm指腹接触面直径，约 57–75dp
44–48dp可稳定命中的最小目标（iOS / Android 建议值）
8dp相邻可点目标之间的最小间隙
15–20mm按下时实际被遮住的视觉范围

遮挡比精度更常被忽略。手指压下去，遮住的区域比触点大一圈，而且是向上偏移的——因为手指从下方伸过来。所以按钮的文字如果放在图标上方 20dp 内，按下瞬间正好被自己的手盖住。RTS 里这条尤其致命：玩家要在按下“造农人”的同时确认“谷还够不够”。

6.2 拇指热区

这张图有一个直接推论：底部通栏是最差的布局。它把最贵的一条带子平均分给了“容易点到”和“很难点到”的区域，还让整个战场下沿失效。正确做法是把命令区拆成左右两块，中间留出小地图或干脆留空。

另一个推论是竖向分区。屏幕高度只有 360dp 时，从上到下大致是三段：预警与资源（0–48dp，只看不点）、战场（48–250dp）、命令（250–360dp）。把可点元素放到最上面一行，等于要求玩家改变握持姿势。

6.3 视觉尺寸与命中区必须分开

视觉上 28dp 的图标，命中区可以做到 48dp；这在实现上就是一个透明外扩的矩形。问题只出现在“视觉小、命中区也小”的情况。判断方法很简单：把命中区画出来，如果两个命中矩形之间的距离小于 8dp，它们就会被一起点中。

元素视觉尺寸建议命中区说明
资源图标20–24dp不可点纯展示，不要给点击态
命令按钮44–56dp≥ 48dp视觉可略小，外扩补足
关闭 / 返回24dp 图标≥ 48dp必须外扩，且离边缘 ≥ 16dp
小地图96×96dp整块 + 8dp点击定位本身就是精确操作，别再做小
列表行高 44dp整行点行任意位置都算，别只让文字可点

还有一类隐形的小目标：滑动条两端的加减按钮、单位头像上的血条、建造队列里的取消叉。它们在视觉上“属于某个大组件”，实现时却各自是独立热区，最容易漏掉外扩。

6.4 系统手势先占了一块地

Android 的手势导航把屏幕左右边缘各约 20dp 划给了“返回”，底部上滑是 Home。任何放在这些区域的自定义滑动都会被系统抢走，表现为“偶尔没反应”。这不是 bug，是平台规则。

  • 可点元素距屏幕左右边缘 ≥ 24dp，距底部 ≥ 24dp；
  • 不要用“从屏幕边缘滑出”做抽屉，除非游戏处于全屏沉浸模式并且有明确把手；
  • 长按拖拽的起点不要贴边，否则会被识别成返回手势；
  • iPhone 的底部横条区域同样要避开，用 safe-area-inset-bottom 处理。

6.5 手势冲突表

触屏 RTS 的手势不多，但每一种都会和另一种打架。设计阶段就要把冲突写成表，而不是等测试时发现“拖框总是变成点选”。

手势本作用途冲突对象裁决规则
单指点按选择单位 / 确认命令拖框选择的起点位移 < 8dp 且时长 < 300ms 判为点按
长按查看详情 / 连续建造拖拽、系统长按菜单阈值 450ms，位移 < 10dp，触发时给震动反馈
拖框多选单位拖动镜头起点落在战场空地＝拖框；落在小地图＝移镜头
双指捏合缩放镜头双指旋转（不需要）只取距离变化，角度变化忽略
边缘滑动无系统返回本作不使用，全部让给系统
拖拽图标到战场放置建筑拖框、点选从建造按钮起手才进入放置态，战场起手不触发

表格右侧的“裁决规则”必须写成可以实现的条件：距离阈值、时间阈值、起手区域。写成“优先响应拖框”这种话，程序没法执行，最后就是谁先注册监听谁赢。

6.6 误触的代价不对称

误触分两种：一种是点了没反应（挫败），一种是点了不该点的（灾难）。后者需要物理隔离，而不是加一个确认框。

  • 空间隔离：把“解散”“投降”“献祭”放到需要跨屏操作的位置，或者收进长按菜单的第二层；
  • 方向约束：滑动方向与后果绑定，向左滑才是放弃，向右滑是取消；
  • 时间约束：长按 500ms，进度环可见、可中途移出取消；
  • 可逆优先：能撤销就别确认。3–5 秒的撤销条比确认框更少打断。

反过来，高频操作用户不会读确认框，只会条件反射点“确定”。当确认框出现得太多，它就变成了一个 200ms 的加载动画，防护作用归零。这是“确认疲劳”，在移动策略游戏里非常普遍。

6.7 命令盘的三种形态

形态优点代价适用
固定网格（3×4）位置永不变，能形成肌肉记忆；实现简单；易做禁用态占固定面积；图标多时显拥挤建造、生产、常驻命令
径向菜单手指不用移动，适合拇指原地操作项数受限（6–8）；文字放不下；遮挡中心技能、姿态切换
情境浮层贴着选中单位出现，空间关系清楚遮挡战场；位置随目标变化，无法形成记忆低频、与目标强相关的操作

本作的结论：建造用固定网格，技能用短按后弹出的 2×3 小面板，不做全屏径向。理由是 RTS 的命令项远多于 8 个，径向菜单要么分页要么砍功能；而建造是高频操作，位置稳定性比“手指少移动 20dp”更值钱。

固定网格还有一个隐性好处：它让“资源不足”的禁用态有地方待。玩家看到同一个格子在整局里一直是灰的，会自然去查前置条件；如果命令项随情境跳动，禁用态就没有稳定的参照物。

6.8 双手分工

横屏 RTS 最合理的分工是：左手管镜头和编队，右手管选择和下令。这条分工一旦确定，就不要让任何一只手同时承担两类任务。

  • 不要把“编队”放在右手区，否则右手要在“选单位”和“切编队”之间来回；
  • 不要让左手需要精确点选小目标，拇指在左下角的精度最差；
  • 双击编队定位、双指缩放这类操作，要允许任意一只手发起；
  • 单手模式下（例如手持地铁），所有功能必须能在右手区完成，这会牺牲效率，但比“完全不能玩”好。

6.9 用数据替代手感

触屏问题几乎都能被测量，不需要实验室：

  1. 触点热图：记录每次点击的坐标，叠加在截图上。如果某个按钮的点击点大量落在边缘，说明它太小或位置不对。
  2. 误触率：统计“点击后 500ms 内又点了相邻元素”的比例。超过 3% 就说明间距不够。
  3. 重复点击率：同一按钮 300ms 内被连点两次，通常意味着第一次没有视觉确认。
  4. 长按放弃率：长按中途抬起，说明阈值太长或进度反馈不清。

这四个指标都可以在游戏内埋点，成本很低。它们比“我觉得按钮挺大的”可靠得多。

6.10 五个人就够：无实验室可用性测试

不需要单面镜、不需要眼动仪，也不需要招募“玩家画像”。找五个没玩过这个游戏的人，给三个任务，看他们卡在哪。五个人的样本足以暴露大部分严重问题—— Nielsen 的经典结论是 5 人约能发现 85% 的可用性问题；对独立项目，这个精度远够用。

做法：

  1. 给任务，不给指令。“造出第一个农人”“找到正在被攻击的基地”“把一支部队撤回来”，不要说“点右下角第二个按钮”。
  2. 让他们出声思考，但不要提示。卡住超过 30 秒再问“你现在想做什么”，仍然不指路。
  3. 记录三件事：是否完成、用了多久、第一次卡住的位置。喜好和评价放在最后问，且不作为主要依据。
  4. 五个人做完再改。不要边测边改，否则后面的人测的是不同版本。

远程也能做：让对方共享屏幕、录屏，你只看不回。唯一的要求是“第一次接触”，所以不要找已经看你演示过的人。测试结束后按“卡点出现的次数”排序，先修出现 3 次以上的，再修只出现 1 次的。

为什么这样做

触屏的所有规范都来自两个物理事实：接触面比目标大，手指会遮住目标上方。由此推出命中区要外扩、间距要够、关键信息不能放在按钮上方、危险操作要物理隔离。理解了这两条，就不需要背具体数字；换一种屏幕或握持方式，你也能自己推出合理值。

常见错误

把桌面 HUD 整体缩放。视觉上变小了，命中区并没有按 dp 重算，结果是一排点不中的小方块。用 hover 表达状态。触屏没有悬停，所有依赖 hover 的信息等于不存在。底部通栏放满按钮。看起来整齐，实际上把最容易点的两个角和最难点的中间混在一起。给危险操作加确认框就完事。高频确认会被条件反射点掉，真正的防护是空间和方向。

07

适配：一块画布，几十种屏幕

设计稿只有一种尺寸，玩家手里有几十种。适配不是“等比缩放”，而是决定哪些东西跟着变、哪些东西永远不变、哪些东西干脆不显示。

7.1 px 不是长度单位

设计稿上的 1920×1080 是像素，手机上的 360 是 dp。两者之间隔着一个 DPR（设备像素比）。一台 2400×1080 的手机，DPR 常是 3，CSS 视口就是 800×360；也就是说，它的高度和 1080p 设计稿的 1080 之间是 1/3 的关系，而宽度不是。

2400×1080物理像素，20:9
800×360DPR 3 后的 CSS 视口
0.333按高度换算的比例（360/1080）
0.417按宽度换算的比例（800/1920）

这两个比例不一致，就是所有适配问题的源头。设计稿上 96px 高的底栏，按高度缩放后在屏幕上只有 32dp；设计稿上 10px 的说明文字，只剩 3.3dp——不是“偏小”，是物理上不可读。9px 更惨，只有 3dp。

即使在一块 CSS 宽度 1440 的大屏（平板横屏或桌面）上，1920 稿按宽度缩放是 0.75，9–10px 变成 6.75–7.5px，仍然低于可读下限。结论很直接：不要用 1920×1080 作为移动 UI 的设计基准。要么直接用 640×360 / 800×360 画，要么在 1920 稿上按“最终会缩到 1/3”来定字号，也就是正文至少 36px。

7.2 安全区不是可选项

安全区的四个值不能写死。Android 用 WindowInsets，iOS 用 safeAreaInsets，Web 用 env(safe-area-inset-*)。设计阶段的做法是在稿子上画一个 32/24/0/48 的内缩框，然后检查所有元素：资源栏有没有被刘海切、关闭按钮有没有落进圆角、底部按钮有没有被手势条盖住。

横屏还有一个反直觉的点：左右内缩常常是 0，但圆角照样会切掉角落的 20×20dp。一排放到最左边的资源图标，第一个会缺一个角。

7.3 五种适配策略

策略做法优点失效场景
等比缩放 + 黑边整块画布按短边缩放，多出的部分留黑构图绝对可控，不会错位20:9 屏上黑边很大，玩家会觉得没适配
锁高度、宽度自适应高度固定，宽度按屏幕延展纵向布局稳定，横向多出的空间可扩展超宽屏上元素被拉得很散
锁宽度、高度自适应宽度固定，纵向伸缩适合竖屏列表横屏 RTS 会把战场压扁
约束布局（锚点）元素按左右上下锚定，尺寸随容器变无黑边，利用率高锚点过多，维护成本高，容易在极端比例下重叠
分区混合HUD 用约束，战场用锁高度，弹窗用居中固定各取所需需要明确的分区规范，否则边界处会打架

本作应采用第五种：战场锁高度，HUD 分左右锚定，弹窗固定宽度并居中。战场锁高度保证单位在 16:9 和 20:9 上看起来一样大；HUD 左右锚定让资源栏贴左上、命令区贴右下；弹窗不跟着拉伸，避免“一行字横跨 800dp”的阅读灾难。

7.4 超宽屏的公平性问题

从 16:9 到 20:9，横向多出约 160dp。如果战场视野跟着变宽，宽屏玩家能更早看到侧翼进攻——这是实打实的竞技优势。RTS 不像射击游戏那样可以靠 FOV 限制解决，因为战场是俯视的，多出来的就是信息。

  • 锁战场可视范围：无论屏幕多宽，战场固定显示 40×22 格，多出的区域用装饰边框或 HUD 填充；
  • 把小地图放进多出来的区域：既填补空白，又不增加信息优势；
  • 不要横向拉伸美术：单位会变胖，地形比例失真，玩家会立刻察觉；
  • 超宽屏的 HUD 可以更疏：多出的空间用来加间距，而不是加内容。

7.5 像素对齐与细线

1dp 的描边在 DPR 2.625 的屏幕上会落在半个物理像素上，渲染成两条 40% 灰的线，看起来“发虚”。这在暗色 UI 上尤其明显，因为细线本来就靠对比度撑住。

  • 关键描边用 2dp，或者用 Math.round 对齐到物理像素；
  • 九宫格的边框不要用 1dp 发丝线，缩放后会粗细不均；
  • 图标导出时按整数倍率（1x/2x/3x），不要用 1.5x；
  • 文本基线不要落在 0.5dp 上，Phaser 里可以用 resolution 或整坐标规避。

7.6 断点怎么定

移动游戏的断点比网页少，因为握持方式只有几种。可用的四档：

区间典型设备布局调整
< 700dp 宽手机横屏（16:9–20:9）紧凑 HUD，命令区 2 行，字号取下限
700–1000dp大屏手机、小折叠展开命令区 3 列，资源栏可加文字标签
1000–1300dp平板横屏左右分栏，战场居中，侧栏常驻
> 1300dp平板 / 桌面不放大 UI，扩大战场视野或加装饰边

断点不要按设备型号定，要按“可用 dp 宽高”定。折叠屏展开后的宽度可能横跨两档，按型号写死必然出错。

7.7 竖屏要不要做

竖屏 RTS 并非不可能，但代价明确：横向视野被压缩，单位阵型难以展开，双手握持变成单手握持，拇指覆盖范围只剩屏幕下半部。对一款以“多线操作”为核心的 RTS，竖屏会改变玩法，而不只是改变布局。

场景竖屏可行性理由
对战不建议横向视野不足，双线操作无法展开
主城 / 建造可以列表与卡片天然适合竖排
图鉴 / 科技树可以可纵向滚动，单手握持更舒适
结算 / 战报可以信息为主，交互少

务实的做法是：对战锁横屏，非对战界面允许竖屏。这需要在进入对战时明确提示“请旋转设备”，并处理好旋转过程中的状态保存。最差的做法是“横竖都支持但都不优化”，两套布局都半成品。

为什么这样做

适配的本质是“哪些维度允许变”。高度决定单位大小和字号，宽度决定留白和分栏，安全区决定贴边元素的位置。把这三件事分开管理，就不需要为每种屏幕画一套稿；混在一起，才会出现“在 16:9 上刚好，在 20:9 上散架”。

常见错误

用 1920×1080 画手机 UI。缩到 1/3 后字号全部失效，这是本仓库 A 稿最根本的问题。只测一台手机。16:9 和 20:9 的差别足以让底栏压住战场。把安全区当成刘海专属。圆角、手势条、挖孔都会吃掉内容。超宽屏拉伸战场。多出来的视野就是竞技优势，必须锁住。

08

无障碍与本地化

这两件事通常被排在“上线前再说”，但它们的成本曲线是反的：设计阶段考虑，几乎不花钱；上线后补，要动布局、改图集、重做字体。更现实的是，它们同时也是“在糟糕环境下的可用性”——强光下看不清、走路时手抖、手机字号被调大，人人都遇到过。

8.1 色盲：颜色只能是第二信道

红绿色觉异常在男性中约占 6–8%，其中绿色弱最常见。RTS 恰好高度依赖红绿区分敌我、可建造与不可建造、增益与减益。如果颜色是唯一线索，这部分玩家会直接失去一半信息。

类型大约比例在本作中最先失效的地方冗余手段
绿色弱（deuteranopia）~6% 男性我方绿 / 敌方红；可建造绿 / 不可建造红形状、描边样式、位置、图标角标
红色弱（protanopia）~1% 男性血量条的红黄绿三段分段刻度 + 数值
蓝黄色弱（tritanopia）<0.01%水与浅色地形的区分纹理与明度差
全色盲极少所有依赖色相的分类完全依赖明度与形状

做法不是“换一套色盲友好的配色”，而是保证去掉颜色后信息仍然完整。具体到本作：

  • 敌我用轮廓区分：我方单位脚下实心圆环，敌方为断续圆环，颜色只是加强；
  • 可建造与不可建造用“图标 + 缺口数字 + 灰度”三重表达，不只变红；
  • 血条除了颜色，再加分段刻度，低于 30% 时出现裂纹纹理；
  • 选中态用四角括号，不用纯发光，因为发光在亮地形上几乎看不见。

验证方法极便宜：把游戏截图转成灰度，让没玩过的人指出“哪些是我方、哪些能造”。指不出来，就说明颜色承载了过多信息。

8.2 对比度：暗色界面更容易翻车

WCAG 的门槛是正文 4.5:1、大字与图形 3:1。游戏 UI 的背景不是纯色，而是不断变化的地形，所以实际要求要更高：关键数字建议按 7:1 设计，留出背景变亮的余量。

本仓库 A 稿的实测值如下，可以直接复现：

前景 / 背景用途对比度判定
#6E6957 / #26271D次要说明文字2.75:1不达标，低于 4.5:1
#9E3B32 / #26271D敌方标记2.25:1不达标，暗红压在暗底上
#D0695A / #26271D警报文字4.21:1临界，未过正文门槛

注意最后一行：5.13:1 是在纯暗底上算的。如果文字直接压在沙漠地形上，实际对比度可能掉到 2:1。所以 RTS 的关键文字几乎都需要底板或描边，而不是指望背景配合。

实用的检查顺序：先算最坏背景（最亮的地形）上的对比度，再决定要不要加底板；如果加了半透明底板，记得把底板的透明度也算进去——60% 黑底会把背景对比度拉回来，但 20% 基本没用。

8.3 字号缩放

系统字号可以调到 130%、150% 甚至 200%。如果布局是“刚好放下”的，一调大就会截断。设计时按 130% 做压力测试：

  • 按钮文字允许多行，或者允许省略号 + 完整 tooltip；
  • 不要用固定高度的容器装可变文字，用最小高度；
  • 资源栏的标签在放大后可以隐藏，只留图标与数字；
  • 列表行高随字号增长，不要裁切。

反过来，游戏内也应该提供字号档位（小 / 标准 / 大），而不是只依赖系统。因为玩家常常不知道怎么改系统字号，而游戏设置里的开关他能找到。

8.4 动效与光敏

约 3% 的人有不同程度的光敏反应，闪烁频率在 3–60Hz、且对比强烈时风险最高。RTS 里常见的危险源是：警报全屏红闪、爆炸白闪、胜利金光扫过、低血量持续脉动。

  • 全屏闪烁不超过每秒 3 次，且不要纯白 / 纯红满屏；
  • 提供“减少动效”开关，关闭屏幕震动、镜头抖动、闪烁与粒子；
  • Web 端尊重 prefers-reduced-motion，原生端读取系统无障碍设置；
  • 减少动效不等于“没有反馈”，用静态描边、图标变化替代。

引擎内实现时，把所有动效集中到一个 MotionConfig，由设置项统一控制倍率（0 / 0.5 / 1），不要让每个界面各自判断。否则一定会有漏网的闪烁。

8.5 焦点与朗读

移动游戏的菜单同样可能被 TalkBack / VoiceOver 使用，尤其是设置、商店、图鉴这类非战斗界面。最低要求：

  1. 每个可交互元素有可朗读的名称，图标按钮不能只有图形；
  2. 焦点顺序与视觉顺序一致，弹窗打开后焦点进入弹窗，关闭后回到触发点；
  3. 不要只靠拖拽完成关键操作，提供点按替代；
  4. 状态变化（如“资源不足”）要能被朗读，而不只是变灰。

战斗界面做完整朗读不现实，也不必强求；但“能不能开始一局、能不能退出、能不能改设置”这条路径必须可用。

8.6 本地化的真实成本是长度

中文是世界上最紧凑的 UI 语言之一。同一个意思，翻成欧洲语言通常膨胀 50–100%。这不是排版偏好问题，是按钮放不放得下的问题。

语言示例相对宽度对本作的影响
中文建造农人1.0×基准
英文Train Farmer约 1.5×四字按钮要放宽到 1.5 倍
德文Bauer ausbilden约 2.0×横排按钮放不下，需要两行或图标
俄文Обучить крестьянина约 2.2×说明文字行数显著增加
阿拉伯文تدريب مزارع约 1.6×，且右起布局镜像，数字仍左起

由此得出几条硬规则：

  • 按钮不写死宽度，按最长语言预留，或者根本不在按钮里放文字；
  • 图标内部不嵌文字，本地化必溢出；
  • 数字与单位分开，1,200 谷 拆成数值与单位两个文本节点，方便换序；
  • 不拼接句子，用带占位符的完整句式，否则语序一变就散架；
  • 专有名词建术语表，避免同一单位在不同界面有三个译名。

8.7 RTL：镜像布局，不镜像语义

阿拉伯语和希伯来语从右向左阅读。整体布局要镜像：资源栏到右上，返回按钮到右侧，进度条方向反转。但有几样东西不能镜像：

  • 数字与数值顺序（1,200 不会变成 002,1）；
  • 小地图方向（世界坐标不变，否则玩家会迷失）；
  • 时间轴、播放键、时钟；
  • 带方向语义的图标（箭头要镜像，“撤销”的方向要跟着语言走）。

实现上不要写 left/right，用 start/end 或逻辑属性；引擎里则用一个全局 dir 变量控制镜像，避免每个界面手动翻转。

为什么这样做

无障碍与本地化的共同点是：它们都要求“信息不依赖单一信道”。颜色不能是唯一线索，文字不能是唯一入口，布局不能写死方向。做到这三点，受益的不只是少数用户——强光下的户外玩家、单手操作的玩家、用着小屏旧机的玩家，都在同一套设计里被照顾到。

常见错误

上线前才做本地化。此时按钮宽度、图标、字体全部定死，改一处牵动十处。用颜色表示“能不能造”。色盲玩家看到的是两个一样的灰块。只测纯色背景上的对比度。战场背景比任何纯色都亮。把 RTL 理解成整体翻转。小地图和数字跟着翻，玩家会直接失去方向感。

09

生产链路：十个环节的断点

一个界面从“要做”到“上线”，中间有十个环节。每个环节都有明确的产出和下一位消费者，断在哪一环，返工就会翻倍。这一章把链路摊开，标出最常断的地方。

下面每一环都按同一结构写：输入、产出、谁需要、过关标准、常见断点。如果你只有一个人，流程可以合并，但不能跳过判断标准——那才是断点的来源。

9.1 需求与决策梳理

输入：玩法文档、胜负条件、每分钟操作次数。产出：一页决策清单，写清玩家每 30 秒要做的决定，以及每个决定需要的信息。

谁需要：设计师自己、程序、以及后面所有评审。过关标准：每条决策都能填出“信息、频率、后果、归属”四列；填不出的，说明这个界面还不该开始画。

常见断点：直接给一张参考游戏截图说“就照这个做”。参考图里没有你的玩法约束，照抄出来的第一版通常信息过密，然后在第 4 环才发现放不下。

9.2 信息架构

输入：决策清单。产出：分区图（常驻 / 情境 / 二级），每个区域的尺寸预算，以及“什么不显示”的清单。

谁需要：视觉设计、程序（决定层级与遮罩）。过关标准：能在 640×360 的框里画出所有常驻区域，且战场面积 ≥ 70%；每个二级入口都有稳定位置。

常见断点：把“信息全”当目标，常驻区吃掉 40% 屏幕。到了手机上，战场只剩一条缝，此时再砍功能，等于推翻玩法。

9.3 交互原型

输入：分区图与决策流。产出：灰盒原型，可以是 Figma 的点击流，也可以是引擎里的占位方块；重点是流程与状态，不是外观。

谁需要：程序（评估实现成本）、测试（写用例）。过关标准：从进入对局到造出第一个建筑，全程不超过 5 次点击、2 次翻页；每个状态转移都能在原型里走通。

常见断点：跳到视觉稿，直接画漂亮界面。结果是“看着有，点不通”——尤其是禁用态、资源不足、队列已满这类分支，视觉稿上根本不存在。

9.4 视觉稿

输入：灰盒与分区尺寸。产出：关键状态稿（不是全部状态），通常 6–10 张：常态、选中、禁用、警报、空列表、溢出。谁需要：所有人。

过关标准：在设计基准尺寸（如 640×360）下 100% 查看，正文 ≥ 12dp、数值 ≥ 16dp；把稿子缩到 50%，仍能读出三个资源数值。做不到，就是字号或层级有问题。

常见断点：在 1920×1080 上画，靠放大查看细节；交付时才发现缩到 1/3 全部失效。本仓库 A 稿就是这个断点的典型样本，第 12 章会逐项拆。

9.5 设计系统与组件

输入：视觉稿里重复出现的元素。产出：组件库（按钮、面板、列表行、资源项、图标），带变体与变量；一份 token 表（颜色、间距、字号、圆角、描边）。

谁需要：视觉、程序、后续所有迭代。过关标准：新增一个界面时，80% 的元素能直接复用；改主色只需要改变量，不需要逐张改图。

常见断点：组件只有“默认态”。程序实现时发现没有按下、禁用、选中，于是各自发挥，最后同一个按钮在三个界面长得不一样。

9.6 动效

输入：状态机与反馈四问。产出：动效清单，每条写清触发条件、时长、曲线、可打断性、降级方案。谁需要：程序、音频（需要对点）。

过关标准：每条动效都能回答“不做会怎样”；所有输入反馈 ≤ 100ms；动效期间输入不被阻塞，或被明确标记为不可操作。

常见断点：在 AE 里做了一个 40 层的粒子开场，引擎里只能用序列帧，一张图集 8192×8192 还不够。动效设计必须先问“用什么方式实现”，第 11 章有对照表。

9.7 切图与标注

输入：定稿视觉与组件。产出：图集、九宫格参数、锚点、字号、间距、状态说明。谁需要：程序。

过关标准：程序拿到文件后不需要再问“这个间距多少”；九宫格的四边切割位置明确；所有状态都有对应资源或明确的程序绘制说明。

常见断点：只导出 PNG，不给九宫格参数。程序凭感觉切，圆角被拉成椭圆，描边粗细不一。另一种是漏掉禁用态资源，程序用降低透明度凑合，结果在暗背景上直接消失。

9.8 引擎实现

输入：图集、标注、动效清单。产出：可运行的界面，含所有状态与适配。谁需要：测试、玩家。

过关标准：在最低目标机型上 60fps（或稳定 30fps），UI Draw Call 在预算内；三台不同比例的机器上无重叠、无截断；安全区正确。

常见断点：设计与实现各自维护一套数值。稿子改了，引擎没改；或者引擎为了省事写死坐标，换比例就错位。解决办法是单一真源 + 导出脚本，第 11 章给做法。

9.9 真机验证

输入：可运行版本。产出：截图基线、帧率记录、触屏热图、问题清单。谁需要：设计、程序、制作人。

过关标准：至少覆盖 16:9、19.5:9、20:9 三种比例，各一台真机；在户外强光下能读出资源数值；单手可完成一局的前 3 分钟。

常见断点：只在模拟器里看。模拟器没有真实 DPR、没有系统手势、没有性能上限，三个问题都测不出来。

9.10 迭代与回归

输入：验证结果。产出：修正后的组件与规范，以及一份回归清单。谁需要：下一轮的所有人。

过关标准：每个修过的问题都进入回归清单；同类问题不再出现第二次；规范文档与实现保持一致。

常见断点：修完就忘。下个版本换人做，同样的坑再踩一遍。回归清单不需要复杂，一张表、二十条、每次发版前过一遍就够。

9.11 交接单

为什么这样做

常见错误

把流程当审批。十个环节不是十个签字，而是十次信息转换；没人签字的环节照样会断。跳过灰盒直接画视觉。漂亮的界面掩盖了走不通的流程。切图只给 PNG。没有九宫格、锚点、状态说明，程序必然自由发挥。验证只看模拟器。真实 DPR、系统手势、发热降频，模拟器一个都测不到。

10

工具全景与选型

工具选型不是选“功能最强的”，而是选“能让信息在链路里少丢一次”的。同一个界面，用 Figma 做和用 Photoshop 做，差别不在画得好不好，而在状态、变量、标注能不能被下一位直接拿走。

10.1 选型的三个维度

把工具按三个问题过一遍，比列功能表有效：

  1. 它是不是单一真源？改一处，所有引用处都变。做不到，就会出现“稿子改了、引擎没改”。
  2. 它能不能表达状态与变体？游戏 UI 的交付物是状态集合，只能画静态图的工具会把状态成本推给程序。
  3. 它的产物能不能被引擎直接消费？导出的是带参数的资源，还是一张需要人工再切的图。

10.3 界面设计工具：差别在状态表达

Figma 适合这个项目的真正原因不是“免费”或“多人协作”，而是三件事：组件变体能把一个按钮的默认、按下、禁用、选中做成同一组件的四个变体；变量能把颜色、间距、圆角做成 token，改一处全变；Auto Layout能让资源栏随文本长度伸缩，而不是靠手摆。这三点直接对应第 4 章的状态机和第 9 章的组件库。

但 Figma 在游戏 UI 上有两个真实摩擦：第一，它按网页的像素思维工作，没有 dp/sp 的概念，需要自己在命名里约定；第二，它的原型交互只能验证流程，无法验证手感——按压反馈、长按时长、拖拽阈值，都得进引擎才知道。

Photoshop 仍然不可替代的地方是“画”：手绘面板、青铜纹理、宣纸底板、光效合成。它的图层样式和混合模式在 Figma 里做不出来。正确分工是：PS 产出材质与底图，Figma 组装布局与状态，而不是用 PS 画整个界面再切片。

Illustrator / Affinity Designer 负责图标与纹样。判断标准不是“好不好看”，而是“缩到 24dp 还认不认得出”。矢量工具的优势是可以导出多倍率，且在九宫格里不会糊。

Sketch / XD 在这个项目里没有理由选。Sketch 绑定 macOS，XD 已经停止功能开发（2023 年宣布），新项目用它们是给自己增加迁移成本。这不是审美判断，是维护风险。

Affinity 系列在 2025 年 10 月之后免费，对零预算的独立开发者是现实选择；代价是协作与标注能力弱，团队超过两人就会开始互相覆盖文件。

10.4 像素与序列帧

如果美术方向是像素风，Aseprite 基本是唯一合理选择：它把“画一帧”和“排一条动画”放在同一个时间轴上，导出时直接给精灵表，还能指定每帧时长。二十美元买断，是这份清单里性价比最高的一项。

非像素风也可以用 Aseprite 做小尺寸图标和特效帧，但不适合做大幅面板——它的画布管理和图层能力撑不住复杂合成。

10.5 动效：先问运行时，再问软件

动效工具的选择完全由“引擎里怎么播”决定。三种典型路线：

路线工具引擎里是什么适合代价

Blender 的用途不是“做 3D UI”，而是渲染 2D 素材：需要真实光影的青铜边框、玉璧底板、云纹浮雕，用三维渲一张再压平，比手绘快且一致。代价是资产管线变重，改一次要重渲。Spline 更轻，适合主菜单或官网的 3D 装饰，导出 Web 组件即可，不必进游戏包。

10.6 引擎侧 UI：摩擦在哪里

Unity UGUI 是最成熟的选择：锚点、九宫格、图集、遮罩都有，资料多。它的代价是 Canvas 重建——一个元素变化可能导致整块 Canvas 重绘，复杂 HUD 需要拆成多个 Canvas，并用图集控制 Draw Call。

UI Toolkit 用 USS + Flexbox，做设置、图鉴、商店这类“网页式”界面非常顺；但它在世界空间、复杂遮罩、与 3D 内容的混合上仍有短板。务实的分工是：菜单用 UI Toolkit，战斗 HUD 用 UGUI。

Godot Control 的 Theme 系统是我见过的引擎里最干净的：一个 Theme 资源管所有控件的样式，换肤就是换资源。代价是生态与中文字体处理需要自己多做一些。

Cocos Creator 的 Widget + Layout 对移动端很友好，九宫格与图集也是内建，适合小游戏与轻量 APK。它的坑在于版本升级时的 API 变动，以及复杂动效要自己写。

Phaser 本身是 Canvas/WebGL 渲染，UI 有两条路：用 Phaser 的 GameObject 画，或直接用 DOM 覆盖层。后者的排版能力（文本换行、滚动、无障碍、输入框）远强于前者，代价是层级与触摸事件要自己协调。本作选 DOM 覆盖层，理由会在第 11 章展开。

10.7 中间件：什么规模才值得

NoesisGUI 解决的是“复杂数据界面 + 美术可控动画”在引擎里做不动的问题。它用类 XAML 的描述方式，支持数据绑定、模板、样式，适合装备对比、科技树、战报这类信息密集界面。代价是学习曲线、授权费、以及多一层运行时排错。只有当中大型项目、界面数量超过几十个、且有专职 UI 程序时，它才划算。

Coherent GT 直接把 HTML/CSS/JS 渲染进游戏，适合 AAA 规模的复杂界面与网页技术栈团队。它的成本（授权、包体、性能调优）对独立项目完全不成立。

Scaleform 是 Flash 时代的方案，已经属于遗留技术。新项目不应考虑；如果接手的项目在用，优先规划迁移而不是扩展。

为什么这样做

工具的差别最终落在“信息损耗”上：能不能表达状态、能不能复用、能不能被程序直接消费。Figma 胜在状态与变量，Aseprite 胜在序列帧直出，Rive 胜在运行时可控，中间件胜在复杂数据绑定。选型的本质，是找出你这条链路上损耗最大的那一环，然后用工具补上，而不是把所有工具都买一遍。

常见错误

用 Photoshop 画整个界面再切片。没有组件、没有状态、改一个字要重切十张图。为了“专业”上中间件。Noesis 和 Coherent 解决的是几十个界面的管理问题，小项目只会被授权和排错拖住。动效先在 AE 做完再问能不能实现。顺序反了，返工的是整条动画。同时用三套工具画同一类元素。最后没人知道哪个是最新稿。

11.2 图集与内存

一张 RGBA8888 的图集，内存是宽 × 高 × 4 字节。2048×2048 就是 16MB，1024×1024 是 4MB。这个数字与文件大小无关——PNG 压缩到 300KB，进显存仍然是 16MB。手机上的 UI 图集通常控制在 2048×2048 以内，中低端机建议 1024×1024。

压缩不是无代价的：带渐变的暗色面板在 ETC2 上会出现色带，文字边缘会糊。常见做法是 UI 图集用 RGBA4444 或 ASTC 4×4，关键渐变单独用一张不压缩的小图。省下的几 MB 不值得用画质换，但 8192² 的图集一定要拆。

合图的原则是“同时出现的东西放在一起”：HUD 一张、建造面板一张、结算一张。把整局所有图标塞进一张 4096²，会导致每次打开面板都常驻一大块显存。

11.3 九宫格

切图时最容易漏的是切割位置。程序需要知道四条线在资源里的坐标（左、右、上、下各多少像素不拉伸）。只给一张 PNG，程序只能按视觉猜，于是圆角被拉扁、描边被拉粗。

另一个细节是中心区：拉伸会让中心纹理变形，平铺（tile）则保持比例但可能出现接缝。木质、石纹这类有机理的面板适合平铺；纯色或渐变适合拉伸。这个选择要写进交接单，不能留给程序临场决定。

11.6 字体落地

  • 子集化：只打包用到的字，通常几百个；用 pyftsubset 或同类工具，保留常用标点与数字；
  • 回退链：品牌字 → 系统中文字体 → 系统默认，缺字时不能显示方框；
  • 动态文本单独处理：玩家名、聊天、存档名不可预测，直接用系统字体；
  • 行高写死会截断：中文的行高与西文不同，按字体度量算，不要用固定值；
  • 数字用等宽特性：font-variant-numeric: tabular-nums，或单独的数字字体。

11.7 动效的四种实现

方式成本可控性适合坑
引擎补间最低高（可随时改参数）位移、缩放、透明度、颜色复杂形变做不了

骨骼动画（Spine 等）中高中角色、复杂 UI 装饰需要专用工具与运行时

选择依据是“这个动画需要被参数驱动吗”。需要（如进度、血量、开关状态）就用运行时矢量或引擎补间；不需要（一次性演出）就用序列帧或 Lottie。不要用序列帧做需要换色的东西，也不要用 Lottie 做每帧都在变的数值。

11.8 手机上真正贵的是什么

移动 GPU 是填充率受限的，不是三角形受限的。UI 的性能问题几乎都来自“画了多少像素”，而不是“多少个面”。

  • 全屏半透明：一层 60% 黑遮罩就是一次全屏混合，叠三层就是三次；
  • 遮罩（Mask）：通常要多一个绘制 pass，嵌套遮罩更贵；
  • 模糊（Blur）：多趟采样，低端机上直接掉帧；
  • Draw Call：图集切换、材质切换、遮罩打断都会增加；UI 建议控制在 20 个以内；
  • Overdraw：同一像素被画多次。半透明面板叠在战场特效上，是典型的 4–5 层。

优化顺序：先减层数（能合并的面板合并），再合图集（减少切换），最后才考虑降分辨率。很多“UI 卡”其实是遮罩和模糊造成的，删掉这两个比换引擎有效。

为什么这样做

常见错误

用 PNG 文件大小估内存。压缩率与显存无关，2048² 就是 16MB。整图缩放代替九宫格。圆角和描边一定变形。所有面板都加模糊和遮罩。这是手机上最贵的两件事。字号在引擎里再调。设计与实现各有一套数值，最后没人知道哪个对。

12.5 如果只改三件事

  1. 换基准尺寸。把画布改成 640×360，所有字号按 dp 重定：正文 12、数值 16、标题 20。原来的 1920 稿只保留作为风格参考，不再作为尺寸来源。
  2. 补状态机。先定义按钮的六个维度（默认、按下、选中、禁用、冷却、资源不足），再画图。每个维度只画差异，不重复画整张界面。

为什么这样做

这套稿子的问题有代表性：它把“画完六个状态”当成了完成，而游戏 UI 的完成标准是“在目标设备上，玩家能在 100ms 内得到正确反馈”。前者是视觉工作量，后者是工程与交互工作量。评分表把两者分开，就是为了避免用前者掩盖后者。

常见错误

用高保真稿代替可用性验证。越精致越容易通过评审，也越容易掩盖问题。把“有六个状态”当成状态齐全。真正的状态在组件级：按钮、列表行、资源项、小地图。用颜色区分敌我。灰度截图一试就露馅。修 UI 时只改视觉。基准尺寸、断点、安全区不改，下一版还会坏在同一个地方。

行业参照

下面这些作品不是用来“抄布局”的。它们各自解决了一个具体问题：如何在信息密集时保持可读、如何让新玩家学会操作、如何让手机上的单指操作成立。看清问题，再决定要不要借用。

13.1 星际争霸 2：把命令变成肌肉记忆

SC2 的命令卡是固定的 3×5 网格，位置永远不变，快捷键与格子一一对应。玩家不需要“找按钮”，只需要记位置。这套设计解决了 RTS 最核心的学习问题：操作的可预测性。

它还做了一件常被忽略的事：资源与人口常驻右上角，数值等宽、位置固定；选中单位的信息在底部中央，与命令卡分离。信息按“看”和“点”分成两个区域，互不干扰。

对本作的启示：固定网格 + 稳定位置，比“智能排序”更有价值。不要根据使用频率动态重排命令，那会破坏肌肉记忆。（来源：作品界面与公开设计访谈，属公开资料归纳。）

13.2 帝国时代：让新玩家知道下一步

帝国时代 2 的界面在左上角放资源，底部放命令，左下角放小地图，这套布局被很多 RTS 沿用。它真正值得学的是“空闲农人按钮”——一个会亮的图标，直接告诉你“有人没干活”。这不是信息展示，是把决策变成提醒。

帝国时代 4 在可读性上更进一步：单位卡片有明确的兵种轮廓，选中面板会显示克制关系，建筑菜单按时代分组。它把“我该造什么”从记忆变成了可见的选项。

对本作的启示：德望、祭司、闲置农人这类“容易被忘掉”的资源，需要一个会亮的入口，而不是一行静态数字。

13.3 全面战争：两套界面，两种节奏

全面战争的战役地图与战斗界面是两套完全不同的 UI。战役界面信息密集、可暂停、允许长文本；战斗界面强调单位卡片、阵型拖拽、士气与弹药。它没有试图用一套 HUD 覆盖两种节奏。

这对本作有直接参照：主城 / 建造 / 图鉴可以信息密集、允许滚动；对战必须极简、固定位置、快速响应。两套界面共享视觉语言，但不共享布局密度。

13.4 英雄连：少即是多

英雄连的 HUD 极简：左下单位面板、右下命令、顶部资源，其余全部让给战场。它用“战术地图”替代常驻小地图，用声音与边缘提示替代大量文字警报。结果是战场可读性极高，玩家能看清每一个单位的动作。

代价是学习曲线：极简 HUD 要求玩家记住更多规则。对本作的启示是，简化 HUD 的前提是玩法规则足够清晰；如果规则本身复杂，极简只会让玩家更迷惑。

13.5 Polytopia：一只手能玩完一局

Polytopia 是移动端回合制策略的参考样本：单指操作、没有常驻面板、点击单位才出现可用动作、所有信息用图标与数字表达。它证明了“策略游戏不一定要满屏 HUD”。

但它是回合制，没有实时压力，也没有多线操作。本作不能直接照搬，能借的是：情境面板（选中才出现）与单指可完成的操作路径。

13.6 手机策略游戏：可借的与不可借的

《率土之滨》《万国觉醒》《Whiteout Survival》这类产品，在移动端信息密度上做到了极致：顶部资源条、右侧活动入口、底部主功能栏、红点引导。它们的共同问题是界面被商业化目标占据：首屏要塞下充值、活动、礼包，战斗只是其中一个入口。

可以借的：资源栏的紧凑排布、图标的统一重量、红点的克制使用（只标“真的有事”）。不可以借的：多层嵌套菜单、每个入口都带角标、把关键操作藏在二级页。这些做法在长线运营里有效，但会毁掉一局 10 分钟的 RTS 节奏。

为什么这样做

参照的价值在于“它解决过什么问题”，而不是“它长什么样”。SC2 解决记忆，帝国时代解决提醒，全面战争解决节奏分离，英雄连解决可读性，Polytopia 解决单指。先认领问题，再借做法；反过来先抄布局，通常会得到一个在你的玩法里不成立的结果。

常见错误

照搬桌面 RTS 的 HUD。键鼠有三层输入，触屏只有一根手指。照搬手机策略游戏的商业化布局。那套界面服务的是付费转化，不是 10 分钟一局的节奏。把“极简”当目标。极简的前提是规则清晰，否则只是把困惑藏起来。忽略作品的时代与平台。2010 年的主机 UI 和 2026 年的手机 UI，约束完全不同。

三档训练：从临摹到定标准

能力不是靠“看完”获得的，是靠“做完并被检验”获得的。这一章把三档训练写成可勾选的清单，每一项都绑定本作的一个真实界面，并且给出可观测的过关标准。勾选状态只存在你本机。

14.1 判定原则

三档不是按“知识多少”划分，而是按你能独立承担什么划分：

档位能独立承担核心能力典型产出
入门把一个已定方向的界面做到可用尺寸、状态、对比度、触屏基本规范一版可上手机的 HUD
进阶从需求推导界面，并建立组件体系信息架构、状态机、设计系统、可用性测试一套组件库 + 验证报告
精通定标准、控成本、带评审性能预算、本地化、无障碍、流程治理规范 + 自动化管线 + 决策记录

每一项练习的括号里是过关标准。标准写成可观察的现象，不写“做好”“优化”“提升质感”这类无法判定的词。做不到就重做，不要靠增加装饰掩盖。

14.2 入门：先做到能用

能力清单：dp 与 px 的换算；44–48dp 命中区；六种按钮状态；对比度 4.5:1 的算法；等宽数字；安全区四边。投入：约 20–30 小时，集中在两周内完成，避免间隔太久。

0 / 8 项 · 0%

这一档算过关：你能在不看这本书的情况下，说出为什么按钮是 48dp、为什么数字要等宽、为什么禁用态不能只变灰，并且能在一张 640×360 的稿子上把这三点做对。

14.3 进阶：从界面到系统

能力清单：决策清单与信息架构；状态机与组合态；组件变体与变量；动效节奏与实现方式；安全区与多比例；无实验室可用性测试。投入：约 50–70 小时，建议跨一个完整的小版本迭代。

0 / 8 项 · 0%

这一档算过关：给你一个玩法需求，你能先产出决策清单与分区图，再产出组件与状态，最后用五个人的测试结果证明它可用；而不是先画一张好看的图。

14.4 精通：定标准与控成本

能力清单：UI 规范与状态维度；token 与导出自动化；性能预算与实测；本地化压力；无障碍审计；回归与评审。投入：约 100–150 小时，通常需要在真实项目中走完一个上线周期。

0 / 8 项 · 0%

这一档算过关：别人能按你写的规范做出合格的界面，你能用数据判断一版 UI 是否可上线，并且能在成本、体验、工期之间给出有理由的取舍——而不是只说“这样更好看”。

14.5 顺序与节奏

不要三档并行。入门没做完就去做设计系统，通常的结果是一套漂亮但不可用的组件。建议的顺序是：先把 b1–b5 做完（它们直接决定界面能不能用），再做 i1–i4（决定能不能扩展），最后做 m1–m3（决定能不能控成本）。

每完成一项，回到第 12 章的重做版布局对照一次：你的改动是让它更接近“可读、可点、可维护”，还是只是更好看。这个对照比任何评分都可靠。

为什么这样做

三档的分界不是知识量，而是责任范围：入门对“这一个界面”负责，进阶对“一套界面”负责，精通对“标准与成本”负责。每档的过关标准都指向可观察的结果，因为能力只有在结果里才成立；感觉自己会了，和能交付，是两件事。

常见错误

把清单当收藏。勾选不是目的，做出可检验的产出才是。跳过入门直接学工具。工具解决效率，不解决方向。只做视觉练习。不测触屏、不测真机、不做交接，做十版也不会进步。用“风格”解释失败。点不中、读不清、掉帧，都不是风格问题。
